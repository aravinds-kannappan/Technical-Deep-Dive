    Synthure: following a note from evidence to report

    I wanted the reports to change for each reader without changing what the note actually said. Following one note through Synthure shows why that requires more than four prompts.

    Two-page cheatsheet · All three cheatsheets

    ·

    The sentence that defines the problem

    “No chest pain.”

    I can locate those three words perfectly and still produce the wrong report. If I extract “chest pain,” attach a diagnosis code, and hand it to a writer as an active condition, the final prose may be polished and completely wrong.

    That is the problem I want Synthure to solve. A single encounter note needs to become useful to several readers: a patient, a physician, a hospital, and an employer. Their questions differ. The underlying account of what happened cannot change with the audience.

    It is tempting to start with four prompts. But before I can ask for a patient explanation or a hospital report, I need to decide what each writer is allowed to treat as a fact. A negated symptom must stay negated. A proposed procedure must stay proposed. An unanswered authorization question must stay unanswered.

    This gives me a way to explain the architecture from the inside out. I follow a note through redaction, extraction, coding, readiness scoring, writing, and review. At each step, I ask what information the next step needs—and what it would mean to lose it.

    I use first person here as a retrospective walkthrough of the design and my assessment of its tradeoffs. The sequence follows the dependencies in the code, rather than claiming a documented development timeline. The example note is invented; the code findings and recorded evaluations are linked to their sources.

    01

    Why I give the writers a shared record

    The central choice in Synthure is to build a shared record before writing the reports. I can change the language for each reader while keeping the extracted conditions, candidate codes, missing details, and reference values together.

    In the implementation, the browser handles OpenMed extraction and redaction. A Next.js route performs lookup, compact-model inference, hosted Claude calls, and output checks. That split keeps provider calls out of the earliest input processing and gives the server structured material to work with.

    Clinical note
  → remove identifying details
  → find and interpret medical mentions
  → retrieve and rank possible codes
  → check missing documentation and readiness
  → write audience-specific reports
  → audit, revise, then accept or request review

    Consider the alternative: four writers independently interpreting the raw note. If two reports disagree about whether surgery happened, I would have to inspect four separate interpretations. With a shared record, I can first check the procedure’s status there. If the record is wrong, every writer may inherit the mistake. If the record is right, I can narrow the problem to the writer that changed it.

    That is the tradeoff I am making. Shared input reduces inconsistent interpretation; it also creates a common failure point. Four agreeing reports are not four independent confirmations.

    The separation gives me useful experimental boundaries. I can freeze a record and compare writers. I can replace an extractor while holding lookup fixed. I can inspect a code candidate before it disappears into a paragraph. These are practical advantages over debugging one large prompt.

    The cost appears in the interfaces between stages. A span needs its source string. A feature vector needs an agreed ordering. A check needs the exact report version it evaluated. The rest of this story is largely about those small contracts—and what happens when a component assumes more than its input actually promises.

    02

    I follow one note across the boundary

    I will use this illustrative note throughout: “Patient A has type 2 diabetes and right-knee osteoarthritis. No chest pain. Knee surgery is being considered. Medication details are incomplete; prior authorization status is unknown.”

    It contains enough friction to exercise the system. There are two positive conditions, one negated symptom, a possible future procedure, and two unresolved details. I need to preserve all five kinds of information without turning the note into a longer list of diagnoses.

    The browser’s ordering matters before any server logic begins. In useSynthesis.start, local models load, deidentify(note) produces a cleaned string, and extractEntities(deid.text) finds mentions in that string. A loading or inference failure returns before the synthesis POST.

    Why extract after redaction? Imagine replacing a short name with a longer placeholder. Every later character moves. If I extracted first and sent those offsets with the cleaned note, the server could highlight the wrong text. Extracting from deid.text and sending that same string keeps the coordinates meaningful.

    The following excerpt marks the handoff into the server pipeline. Its deferred values coordinate later presentation; they are not additional extraction results.

    03

    The first difficult detail is a character offset

    Before a writer can use a condition, I need to know which words support it. OpenMed returns token predictions; the application needs character ranges it can highlight, replace, and validate. The browser runs ONNX models, with documented int8 quantization to reduce storage and potentially computation. Download size and local memory are part of whether this choice is usable.

    The aggregation code joins compatible BIO-tagged pieces, removes WordPiece’s ## prefix, and searches forward through the note for the reconstructed phrase. For a multiword mention, it takes the minimum token confidence. One weak piece therefore cannot disappear inside an average of strong pieces.

    Text:     chronic      kidney       disease
Labels:   B-DISEASE    I-DISEASE     I-DISEASE
Meaning:  beginning   continuation  continuation

Merged mention: "chronic kidney disease"
Next question: Is it current, negated, uncertain, or historical?

    I use half-open ranges, [start, end): the start belongs to the span and the end does not. A span’s length is end - start. This convention makes adjacent ranges and string slices line up, but it only helps if the positions refer to the right string.

    Redaction makes the problem tangible. Suppose I have ranges [5,10) and [20,25). Replacing the first with a twelve-character placeholder shifts the second by seven characters. The implementation avoids that shift by replacing later ranges first.

    export async function deidentify(text: string, minScore = 0.5): Promise<DeidResult> {
  const hits = await run('deid', text, minScore)
  // Replace right to left so earlier spans keep their offsets.
  let clean = text
  const types = new Set<string>()
  for (const h of [...hits].sort((a, b) => b.start - a.start)) {
    const tag = h.label.toUpperCase()
    types.add(tag)
    clean = clean.slice(0, h.start) + `[${tag}]` + clean.slice(h.end)
  }
  return { text: clean, redactions: hits.length, types: [...types].sort() }

    That solves the editing order, not the extraction accuracy. Disease and chemical extraction subsequently run with Promise.all; duplicate (start, end, type) keys keep the higher confidence. The passes can overlap, though they still share browser resources.

    The harder case is “pain improved; pain returned.” Searching forward is better than repeatedly finding the first “pain,” but reconstructed text is still a workaround for tokenizer offsets. Punctuation, normalization, or a rejected span can disturb alignment. I would distinguish “right entity, wrong location” from “entity never found” when evaluating this stage.

    The abbreviation dictionary addresses a different gap: a model may miss shorthand such as HTN even when it recognizes the expanded phrase. A dictionary is cheap to inspect, but cannot resolve every ambiguous abbreviation. Nearby negation rules have a similar limit. “Denies fever” is easier than “no fever but persistent cough,” where the scope must stop before cough.

    Back in my example, successfully locating “chest pain” is only the first result. I still need its assertion status. Family history, old diagnoses, and “rule out” language create the same problem. The minimum-token confidence is a heuristic about predicted pieces, not a calibrated probability that the final clinical interpretation is right. I therefore keep boundary accuracy, entity typing, and assertion status separate. That distinction becomes even more important when the next stage starts proposing codes.

    04

    I keep the narrow decisions small

    Once I have mentions, I still need to identify the note type and flag missing documentation. These outputs are narrow enough that I can inspect the arithmetic directly. Synthure uses exported JSON weights in TypeScript instead of invoking a hosted writer for each decision.

    For note type, classifyNoteType counts unigrams and bigrams in the exported vocabulary. A retained term receives (1 + ln count) × IDF. The sparse vector is L2-normalized, then each class adds its intercept to a weighted sum of those features.

    Here is a toy calculation I can follow all the way through. Let “refer” and “specialist” each occur once, with IDF weights 2 and 1, while “refer specialist” is absent. The vector is [2,1,0]. Dividing by √5 gives about [0.894,0.447,0], so document length alone does not scale every class score upward.

    If the resulting logits are [2,1,0], subtracting the largest produces [0,-1,-2]. Exponentiating and normalizing gives roughly [0.665,0.245,0.090]. The subtraction prevents overflow without changing the result: every exponential was scaled by the same factor. These are illustrative values, not the fitted coefficients.

    This simplicity creates a serving contract. Vocabulary indices, IDF values, coefficient order, and class order must match training. A vector can have exactly the expected length and still mean the wrong thing if its positions are reordered.

    There is also a revealing empty-input case. If no vocabulary item matches, the feature vector stays empty and the logits come entirely from the intercepts. The function still returns a class. I cannot treat an ordinary-looking confidence as proof that the model recognized meaningful evidence in the note.

    Missing-field detection uses a different output shape. structVector assembles ordered counts, lexical flags, normalized note length, and one-hot note type. detectMissing applies separate sigmoid classifiers, allowing dosage and laterality to be missing together. With an illustrative intercept of −1 and contributions of 2 and 1, the logit is 2 and sigmoid returns about 0.881.

    A naming detail matters at the caller: present means the missing-field flag crossed 0.5. It does not mean the medical detail is present. That reversal is easy to miss while reading a response.

    The larger limit is representation. “Left arm examined; knee pain” contains a laterality word, but it never specifies the knee’s side. A global lexical flag cannot attach “left” to the correct condition. Matching Python and TypeScript outputs would establish numerical parity while leaving that semantic error untouched. I get cheap, inspectable decisions here; I do not get a complete interpretation of the note.

    05

    A plausible code is not yet the right code

    The next step makes the stakes of that missing context visible. I have “right-knee osteoarthritis” in the note and need a reference match. Scanning every catalog entry for every mention would be wasteful, so the local path starts with an inverted index.

    icdCandidates expands known abbreviations and reads token-to-term postings. It first requires all unique query tokens, then relaxes to one fewer, then backs off to strong tokens. Overlap, head-word agreement, and fewer extra words determine candidate order. Strict matching narrows the list; backoff recovers wording variations at the cost of ambiguity.

    The local selector takes up to eight candidates. Its logistic reranker uses overlap, term length, billability, and retrieval rank. It accepts the best score at or above 0.15, checks the tabular reference, and deduplicates codes.

    The executable function is more informative than the source header here. The header describes Claude selecting candidates; linkDiagnoses actually calls the in-process rerankScore. I would explain this path as a small lexical reranker, not a language model reading the whole note.

    To decide whether ranking deserves more work, I first ask whether retrieval supplied the answer. Imagine 100 mentions: the correct code appears in 90 shortlists, and the reranker picks it for 72. Overall accuracy is 72%; accuracy conditional on retrieval success is 80%. No reranker improvement can recover the ten omitted answers without changing the shortlist.

    Our knee example exposes a different limit. If the note merely said “knee osteoarthritis,” a side-specific candidate could still score well. The four features do not directly represent whether a qualifier belongs to this condition. Billability describes a catalog entry, not support for a claim. The score floor lets me abstain on weak matches, but does not resolve two strong competing candidates.

    An optional neural coder adds another route. When configured, modelLinkCodes sends mentions to a remote endpoint with a 25-second timeout. Returned codes must exist in the local reference. Literal codes can overwrite lexical links; the optional service can confirm or add validated codes.

    06

    When lexical matching runs out of room

    The lexical path makes its limits easy to see. Two phrases can mean the same thing without sharing enough words. That is where the repository’s optional neural coder becomes interesting: it learns a representation for mentions and code descriptions instead of relying only on token overlap.

    The BiEncoder mean-pools token states using the attention mask and normalizes the resulting B × D vectors. I can encode the reference descriptions ahead of time. At request time, I encode the mention and compare it with those cached vectors by dot product. Because they are normalized, the dot product is cosine similarity.

    The saving comes from avoiding a fresh joint reading of the query and every description. A CrossEncoder does read each pair together. It can model interactions between their words, but needs a forward pass for each pair. That suggests a useful division: retrieve broadly with separate embeddings, then spend joint scoring on a shortlist.

    Training introduces a trap that is easy to miss. If two phrases in a batch map to the same code, treating every off-diagonal pair as a negative punishes a valid match. The loss explicitly masks those same-code collisions.

    ml/icd_coder/model.py · lines 45–58 · inspected revision a9f829bb · selected excerpt; follow the source for surrounding code

    def info_nce(anchor: torch.Tensor, positive: torch.Tensor, codes: torch.Tensor, temperature: float) -> torch.Tensor:
    """Symmetric in-batch InfoNCE.

    anchor[i] and positive[i] are the phrase and its code's description. Any j!=i
    with the same code is masked out so a true synonym is never punished as a
    negative (in-batch collisions are common in a 98k-code space).
    """
    logits = anchor @ positive.t() / temperature           # (B, B)
    same = codes.unsqueeze(0) == codes.unsqueeze(1)         # (B, B) same code
    eye = torch.eye(logits.size(0), dtype=torch.bool, device=logits.device)
    mask = same & ~eye
    logits = logits.masked_fill(mask, float("-inf"))
    target = torch.arange(logits.size(0), device=logits.device)
    return 0.5 * (F.cross_entropy(logits, target) + F.cross_entropy(logits.t(), target))

    The matrix anchor @ positive.t() contains every phrase-description similarity in the batch. Dividing by temperature changes how sharply the loss favors the strongest similarities. The diagonal provides the labeled pairs; the same-code mask removes false negatives elsewhere. Averaging cross-entropy in both directions trains phrase-to-description and description-to-phrase matching.

    This is why I would inspect batch construction alongside the model. The available negatives shape what the encoder learns. Increasing model size cannot repair a training objective that repeatedly labels synonyms as wrong.

    A longer retrieved list gives the joint scorer more chances to see the correct code, but increases work. A short list saves latency and preserves the retrieval ceiling from the previous section. The lexical and neural paths share that tradeoff even though their scoring mechanisms differ.

    The application’s optional call is the link between this training code and a live request. The presence of the model implementation does not establish that a hosted instance served a particular report. Nor does it establish payer-policy search: this revision is not evidence of a deployed IVFFlat index or a versioned policy-document retrieval system. I keep the story focused on the coder that is actually present.

    07

    A score has to become a review decision

    Return to the note. I have candidate conditions and codes, but medication details remain incomplete and authorization remains unknown. I need a way to estimate documentation readiness without pretending those gaps have disappeared.

    Synthure uses exported gradient-boosted trees, followed by a fitted calibration map. In gbmProb, I start with a bias, traverse each tree by feature thresholds, and add the selected leaf value times the learning rate. Sigmoid converts the accumulated logit into a raw score.

    frontend/lib/models/synthure.ts · lines 113–143 · inspected revision a9f829bb · selected excerpt; follow the source for surrounding code

    function gbmProb(x: number[]): number {
  const gbm = (readinessModel as { gbm: { trees: Tree[]; learning_rate: number; init: number } }).gbm
  let s = gbm.init
  for (const t of gbm.trees) {
    let node = 0
    while (t.children_left[node] !== -1) {
      node = x[t.feature[node]] <= t.threshold[node] ? t.children_left[node] : t.children_right[node]
    }
    s += gbm.learning_rate * t.value[node]
  }
  return sigmoid(s)
}
function calibrate(p: number): number {
  const { x, y } = (readinessModel as { calibration: { x: number[]; y: number[] } }).calibration
  for (let i = 0; i < x.length - 1; i++) {
    if (p <= x[i + 1]) {
      const t = (p - x[i]) / (x[i + 1] - x[i] + 1e-9)
      return y[i] + t * (y[i + 1] - y[i])
    }
  }
  return y[y.length - 1]
}
export function predictReadiness(note: string, noteType: string, nDx: number, nProc: number): {
  raw: number; calibrated: number; band: 'ready' | 'needs_work' | 'not_ready'
} {
  const raw = gbmProb(structVector(note, noteType, nDx, nProc))
  const calibrated = calibrate(raw)
  const band = calibrated >= 0.66 ? 'ready' : calibrated >= 0.4 ? 'needs_work' : 'not_ready'
  return { raw: Number(raw.toFixed(3)), calibrated: Number(calibrated.toFixed(3)), band }
}

    For a toy ensemble, let the bias be −0.4, the learning rate 0.1, and the chosen leaves 1.2 and −0.3. The logit becomes −0.4 + 0.1 × (1.2 − 0.3) = −0.31, giving about 0.423 after sigmoid. This is not the fraction of documentation rules passed. It is the output of a fitted function.

    Trees can combine structured features nonlinearly while remaining cheap to serve. They cannot recover relationships absent from the feature vector. The laterality flag from the previous chapter still does not say which condition has a side.

    Calibration then changes the score scale. With illustrative knots (0.4,0.3) and (0.6,0.5), interpolation maps a raw 0.5 to 0.4. The intended interpretation concerns groups of comparable cases: among cases near a score of 0.8, roughly 80% should meet the positive label. That requires suitable calibration data; it is not a promise about one note or insurance payment.

    The boundary behavior deserves attention too. Above the last knot, the implementation returns the last mapped value. Below the first, it enters the first interval and can extrapolate. Tests confined to the fitted interior would miss that asymmetry.

    The application assigns “not ready” below 0.40, “needs work” below 0.66, and “ready” at 0.66 or above. Those thresholds are policy choices layered on the score. Calibration can move a case between bands without changing its rank among cases.

    I would read the diagram as a staffing decision as well as a model decision. Accepting 80 of 100 cases with four errors gives 5% accepted-case error. Accepting 50 with one error lowers that rate to 2%, but sends 30 more cases to review. The larger accuracy percentage alone does not tell me whether the workflow improved.

    In my example, even a score of 0.72 cannot answer the authorization question. The numerical band, rule-based readiness checks, and final guardrail verdict remain separate. The score helps organize review; the missing evidence still belongs in the record that the writers receive.

    08

    Only now do I ask for four reports

    At this point I can explain what each writer receives. The shared record carries extracted information, coding results, and documentation gaps. claudeReport adds audience-specific instructions for the patient, physician, hospital, or employer. A forced report tool gives the response structured fields.

    That lets me vary scope and language without asking every writer to rediscover the note. The patient needs an explanation; the physician needs the unresolved clinical details; the employer view must stay within its narrower scope. Four calls buy that separation, but also cost more than one structured response.

    Model routing is explicit. writerModel selects Sonnet for physician and hospital reports in the frontier lane; other cases use Haiku. This is routing through hosted inference, not four independently trained models.

    The writers do not depend on each other, so the route starts them with Promise.all. Each optionally obtains faithfulness flags and streams its result. The completed array is sorted into stakeholder order before the combined audit.

    This creates a subtle version problem. Replacing a report changes the artifact that was audited. The route reruns deterministic guardrails on the final reports, but does not rerun the same optional faithfulness call or combined model audit after replacement.     That leaves a more useful picture than “four agents collaborating”: independent writers, one dependent audit, a limited revision budget, and final deterministic checks. The control flow explains the latency and the failure cases. It also leads directly to the next question: what does the interface do with a report that has already streamed but is later blocked?

    09

    The report can arrive before it is accepted

    Imagine the patient report has appeared while the other writers are still running. The user can see text. The system has not yet completed its combined audit. I need those to remain different states.

    The order is deliberate: a blocking finding produces block; low extraction confidence or no codes produces escalate; medium or high findings produce revise; otherwise the decision is ship. Many harmless passes cannot average away a blocker. That is why I would consume the verdict rather than derive acceptance from the displayed score.

    Still, each check has a scope. Valid fields establish structure. Supported assertions establish factuality. Appropriate audience access establishes disclosure. A perfectly formed JSON object can fail either of the latter two. Finding a number somewhere in the source also does not prove the report attached it to the correct condition.

    The route emits reports before the final verdict, then sends guardrail and harness events and continues to an overview. A block event cannot by itself retract already visible text. Enforcement belongs at the display, export, or action boundary that consumes the decision. Similarly, ship is a checker result, not evidence that an external claim was submitted.

    Revision makes exact identity matter. The final deterministic checks cover the replacement text; the earlier model audit covers the original. Counting two audits or two revisions tells me less than identifying which checks apply to the final report.

    The audit trail has a similar gap between intent and mechanism. The client calls appendAudit and catches failures because logging is best-effort in the demo. Calling the record immutable in a comment does not make it durable.

    A local hash chain can reveal some edits if a trusted earlier fingerprint survives elsewhere. If the store and hashes can be rewritten together, both can be replaced. I would therefore describe the present behavior as useful local audit information, not independently anchored history.

    The checker is valuable because it turns findings into explicit decisions. The remaining work is to bind those decisions to the right version and make every consequential consumer enforce them. Before deciding how much confidence to place in that design, I need to look at what was actually measured.

    A finished animation is not a finished request

    The note has now traveled through local models, server analysis, writers, and checks. Even with parallel writers, the user waits on several dependencies. I want to show progress during that wait, so the browser reads server-sent events from the synthesis POST.

    The stream carries stage updates, reports, audits, and gates. It lets a report appear before the final checked result, but it does not remove the dependency order. In the toy timeline below, two seconds locally, one for analysis, five for writing, and two for auditing still form a ten-second critical path.

    That is why I would measure first-visible output and final acceptance separately. Streaming can improve the first without improving the second.

    At the byte level, the client does something important correctly. A network read is not necessarily an event. It can contain half a message or several messages. The parser accumulates decoded bytes and extracts complete double-newline-delimited messages.

    12

    What I would build next

    Following the note makes my priorities clearer. I would keep the staged architecture. It gives me places to inspect evidence, replace a model, and compare outputs. My next changes would strengthen the contracts between those stages before adding another writer.

    First, I would make completion explicit. The server would emit a terminal result, and the client would distinguish success, failure, cancellation, and unexpected disconnection. Releasing animation waits would only unblock presentation. Drafts would stay provisional until the decision for their exact version arrived, and exports would consume that same decision.

    I would then give the shared record stronger provenance. A condition would retain its source span and assertion status. A code would retain its retrieval route and acceptance reason. Visit suggestions and prices would carry their assumptions. Every draft and check would identify the record and report revisions it consumed.

    For the example note, that would let me trace a claim back through “right-knee osteoarthritis,” inspect the selected code, and see whether any writer introduced a new qualifier. A revision would invalidate earlier checks, rather than silently inheriting them. I would prioritize revision targets by severity and expose any that exceeded the budget.

    The extraction work would focus on tokenizer offsets where available and fixtures for repeated mentions, punctuation, negation scope, history, and relatives. Redaction tests would retain both strings so I could verify changed offsets. A review of the cleaned note would also make missed identifiers visible before submission.

    For coding, I would measure recall@8 before changing the reranker. I would compare context-aware acceptance and near-tie handling on the same holdout. For missing fields, I would evaluate per-field thresholds and recall against the current 0.5 baseline. Numerical parity tests would compare Python and TypeScript logits before rounding.

    The central evaluation would follow whole notes through the system. I would use a patient- or source-disjoint real-note holdout and keep related synthetic templates together. Each case would retain reference answers, spans, candidates, selected routes, report versions, and final decisions. Accepted-output error, coverage, review effort, and sample counts would appear together.

    I would also compare one structured writer with four audience prompts, and a consolidated audit with separate calls. That would test whether the added calls and consolidation deliver their intended tradeoffs. The ledger would record code, model, data, and threshold revisions instead of leaving their relationship implicit.

    Operationally, cancellation should propagate where supported, optional-service outcomes should be recorded per request, and concurrency should respect dependency capacity. Shared atomic counters would enforce deployment-wide budgets. If disconnections justify durable jobs, clients would reconnect to a persisted state rather than start duplicate work.

    None of these are features claimed by this revision. They are the next steps suggested by following one note all the way through. My goal is a system where I can explain not only why a report sounds plausible, but where each important assertion came from, what checked it, and why the application allowed it to leave the draft state.
