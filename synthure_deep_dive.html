    Synthure: what it takes to turn a clinical note into a trustworthy report

    A clinical note can support several useful reports. The difficult part is keeping its meaning intact as the text becomes entities, codes, scores, and generated explanations.

    Two-page cheatsheet · All three cheatsheets

    Why start with the evidence?

    Consider the sentence “No chest pain.” A model can correctly find the words “chest pain” and still make the system less accurate. If those words become an active diagnosis, every later stage can do its job correctly—retrieve a valid code, write a fluent explanation, produce well-formed JSON—and the final report will still be wrong.

    This is the central problem in Synthure. The application turns one encounter note into reports for a patient, a physician, a hospital, and an employer. Each reader needs a different level of detail. All four need an account consistent with the same encounter.

    A language model makes the writing possible, but writing comes relatively late in the design. First, the application has to establish what was documented, which details are missing, and which interpretations are only suggestions. That work combines browser-based extraction, small classifiers, catalog retrieval, and explicit review decisions.

    The first part follows a note through extraction and coding. The second explains readiness scoring and report generation. The last examines evaluation and serving: what the recorded numbers establish, and what happens when a request fails halfway through. The examples are invented; the implementation details refer to the source revision listed at the end.

    One record, several readers

    A useful way to understand Synthure is to separate the evidence record from its presentations. A physician may need terminology and unresolved documentation details. A patient may need plain-language explanations. An employer-facing view has a narrower disclosure scope. Those are transformations of a common account, rather than invitations to reconstruct the encounter independently.

    The browser runs OpenMed models for redaction and entity extraction. The Next.js server combines the cleaned note with reference lookups and compact predictors, then calls hosted writers and checks their outputs. The main dependency chain looks like this:

    Clinical note
  → remove identifying details
  → find and interpret medical mentions
  → retrieve and rank possible codes
  → check missing documentation and readiness
  → write audience-specific reports
  → audit, revise, then accept or request review

    The shared ExtractionResult makes errors easier to locate. If every report incorrectly says a procedure occurred, inspect the procedure in the shared record first. If only one report makes that claim, inspect its transformation of the record. This also makes experiments possible: freeze extraction and compare writers, or freeze the writer and compare coding strategies.

    There is a tradeoff. Shared evidence reduces independent reinterpretation, but it also distributes an extraction mistake to every writer. Agreement among reports is therefore weaker evidence than it initially appears. The reports share a source of error.

    The interfaces between stages carry much of the design’s value. An entity needs its source span; a candidate code needs its retrieval provenance; a readiness score needs the meaning of its target label. Without those contracts, an output can become more polished while becoming harder to verify.

    Following one note through the system

    We will use this note throughout: “Patient A has type 2 diabetes and right-knee osteoarthritis. No chest pain. Knee surgery is being considered. Medication details are incomplete; prior authorization status is unknown.”

    There are two positive conditions, a negated symptom, a possible future procedure, and unresolved documentation. Flattening this into a list of medical phrases would lose most of the distinctions that matter.

    The browser first loads its models, runs deidentify(note), and then runs extractEntities(deid.text). A model-loading or inference failure stops the normal browser path before the synthesis POST. Extracting after redaction matters because replacing a name with a placeholder can move every later character. Entity offsets must describe the same cleaned string the server receives.

    From token predictions to clinical assertions

    Named-entity recognition identifies spans such as conditions, medications, or identifiers. OpenMed produces token-level predictions; the application needs character ranges that can be highlighted, redacted, and checked. The browser uses ONNX models with int8 quantization, which reduces weight storage relative to higher-precision weights. Actual runtime benefits still depend on the browser and execution backend.

    Text:     chronic      kidney       disease
Labels:   B-DISEASE    I-DISEASE     I-DISEASE
Meaning:  beginning   continuation  continuation

Merged mention: "chronic kidney disease"
Next question: Is it current, negated, uncertain, or historical?

    BIO tags mark the beginning and continuation of an entity. The aggregation code joins compatible pieces, removes WordPiece’s ## marker, and searches forward for the reconstructed phrase. It assigns the minimum token score to a merged span. This conservative aggregation prevents a weak token from being hidden by an average, although it is not a calibrated probability of correct clinical interpretation.

    Character ranges use the half-open convention [start, end). If a name at [5,10) is replaced by twelve characters, a later span moves seven positions. Applying edits from right to left preserves the offsets of earlier spans that are still waiting to be replaced:

    frontend/lib/openmed.ts · lines 175–185 · source revision a9f829bb · selected excerpt

    export async function deidentify(text: string, minScore = 0.5): Promise<DeidResult> {
  const hits = await run('deid', text, minScore)
  // Replace right to left so earlier spans keep their offsets.
  let clean = text
  const types = new Set<string>()
  for (const h of [...hits].sort((a, b) => b.start - a.start)) {
    const tag = h.label.toUpperCase()
    types.add(tag)
    clean = clean.slice(0, h.start) + `[${tag}]` + clean.slice(h.end)
  }
  return { text: clean, redactions: hits.length, types: [...types].sort() }

    The default redaction threshold is 0.5; disease and pharmaceutical extraction use 0.6. The latter passes run in parallel, and duplicate (start,end,type) spans retain the higher confidence. Those thresholds trade missed mentions against false detections. Their numerical values alone do not establish the best operating point.

    Two failure types deserve separate tests. “Pain improved; pain returned” tests whether the extractor locates the intended occurrence. “No fever but persistent cough” tests whether negation stops at the right boundary. Tokenizer offsets, where available, help with the first. Assertion modeling helps with the second. A forward text search and nearby negation rules address only parts of these problems.

    Abbreviation expansion and RxNorm lookup add useful vocabulary support. They cannot resolve every ambiguous abbreviation or determine whether a medication is current. A stronger record would attach assertion status—current, historical, negated, uncertain, proposed—to each supported mention. This is a proposed extension, and it becomes especially valuable when mentions enter the coding stage.

    Why some decisions fit small models

    Identifying a note category or checking for missing documentation is a narrower task than writing a patient explanation. Synthure serves these decisions using exported weights in TypeScript. This avoids a hosted generation call and makes the computation inspectable.

    Note type: TF-IDF and a linear classifier

    The classifier counts unigrams and bigrams from an exported vocabulary. For an observed term with count c, its unnormalized weight is (1 + ln c) × IDF. The vector is L2-normalized before applying class coefficients and intercepts:

    zj = bj + wjTx
    pj = exp(zj − max z) / Σk exp(zk − max z)

    Here x is the normalized feature vector, and z contains class logits. Subtracting the largest logit prevents numerical overflow without changing the softmax ratios.

    For example, raw features [2,1,0] become approximately [0.894,0.447,0]. Illustrative logits [2,1,0] then produce probabilities near [0.665,0.245,0.090]. Normalization reduces sensitivity to vector magnitude; it does not make the model understand which condition a qualifier belongs to.

    The training and serving implementations must agree on vocabulary indices, IDF values, class order, and feature construction. Equal vector lengths are insufficient. Swapping two feature positions still produces valid arithmetic with the wrong meaning. If no vocabulary term matches, intercepts alone determine the output, which is another reason to track evidence coverage alongside confidence.

    Missing fields: several labels can be true

    Missing-field detection uses an ordered structural vector: counts, lexical flags, normalized note length, and one-hot note type. Each field has a sigmoid classifier, σ(z)=1/(1+exp(−z)). Separate sigmoids allow dosage and laterality to be missing simultaneously; a softmax would unnecessarily force the labels to compete.

    The returned present flag means the missing-field prediction exceeded 0.5. It does not mean the medical detail was supplied. There is also a representational limit: “Left arm examined; knee pain” contains a side, but not the knee’s side. Numerical parity with training cannot repair a feature representation that loses this association.

    Retrieving a code is easier than establishing that it applies

    A catalog makes coding a constrained selection problem. Instead of allowing the writer to invent an identifier, Synthure retrieves candidate terms and ranks their codes. This guarantees a more useful kind of output space, but a valid code can still be wrong for the note.

    The lexical path uses an inverted index: tokens point to catalog terms containing them. icdCandidates expands abbreviations, tries all unique query tokens, relaxes to one fewer, and finally backs off to strong tokens. Ordering accounts for overlap, agreement with the head word, and extra words in the candidate.

    The route requests up to eight candidates. A logistic reranker scores overlap, term length, billability, and retrieval rank; the best candidate must clear 0.15. Codes are then checked against the reference and deduplicated.

    frontend/app/api/synthesize/route.ts · lines 228–248 · source revision a9f829bb · selected excerpt

    const LINK_FLOOR = 0.15 // reranker probability below which we abstain

function linkDiagnoses(diagnoses: Entity[]): LinkedCode[] {
  const out: LinkedCode[] = []
  const usedCodes = new Set<string>()
  for (const e of diagnoses) {
    const cands = icdCandidates(e.text, 8)
    if (!cands.length) continue
    let best: { c: IcdCandidate; s: number } | null = null
    for (const c of cands) {
      const s = rerankScore({ overlap: c.overlap, termlen: c.termLen, billable: c.billable ? 1 : 0, rank: c.rank })
      if (!best || s > best.s) best = { c, s }
    }
    if (!best || best.s < LINK_FLOOR) continue // abstain -> entity stays uncoded
    const key = best.c.code.replace('.', '').toUpperCase()
    if (usedCodes.has(key)) continue
    usedCodes.add(key)
    out.push({ code: best.c.code, label: best.c.description, billable: best.c.billable, source: 'linked', entity: e.text, score: Number(best.s.toFixed(3)) })
  }
  return out
}

    This path calls the local rerankScore, despite a source comment describing language-model selection. The distinction matters: these four features do not give the scorer a full reading of the encounter.

    Retrieval places a ceiling on reranking. Suppose the correct code enters the shortlist for 90 of 100 mentions, and the reranker selects it for 72. Overall accuracy is 72%; conditional accuracy among successful retrievals is 80%. The remaining ten retrieval misses require a better candidate set, regardless of reranker capacity.

    For “right-knee osteoarthritis,” laterality is supported. For “knee osteoarthritis,” a side-specific result needs evidence the phrase lacks. Billability and a high overlap score do not supply it. Useful improvements would measure recall@8 first, then test qualifier-aware acceptance and abstention on ambiguous near-ties.

    Learning similarity when words do not overlap

    Lexical retrieval is easy to inspect, but synonymous phrases may share few tokens. The optional neural coder learns vectors for mentions and code descriptions so that matching meanings can receive high similarity even when their surface wording differs.

    A bi-encoder processes the mention and description separately. It mean-pools token states with the attention mask and normalizes the resulting vectors. Catalog descriptions can be embedded ahead of time; a request only needs a query embedding and comparisons with the saved catalog vectors. For unit vectors, their dot product equals cosine similarity.

    A cross-encoder instead processes each mention–description pair together. This permits richer word interactions, but incurs a model pass per pair. A common division of labor is therefore cheap broad retrieval followed by expensive joint scoring on a shortlist.

    The training objective

    Let ui be mention i’s vector and vj description j’s vector. For a batch of paired examples, the similarity matrix is Sij=uiTvj/τ, where temperature τ controls how sharply scores compete. The correct pairs occupy the diagonal.

    Lmention→code = −(1/B) Σi log [exp(Sii) / Σj allowed exp(Sij)]

    Usually, off-diagonal examples serve as negatives. But two mentions in a batch may map to the same code. Penalizing those pairs would teach the model to separate legitimate synonyms. This implementation masks same-code collisions and averages cross-entropy in both retrieval directions:

    ml/icd_coder/model.py · lines 45–58 · source revision a9f829bb · selected excerpt

    def info_nce(anchor: torch.Tensor, positive: torch.Tensor, codes: torch.Tensor, temperature: float) -> torch.Tensor:
    """Symmetric in-batch InfoNCE.

    anchor[i] and positive[i] are the phrase and its code's description. Any j!=i
    with the same code is masked out so a true synonym is never punished as a
    negative (in-batch collisions are common in a 98k-code space).
    """
    logits = anchor @ positive.t() / temperature           # (B, B)
    same = codes.unsqueeze(0) == codes.unsqueeze(1)         # (B, B) same code
    eye = torch.eye(logits.size(0), dtype=torch.bool, device=logits.device)
    mask = same & ~eye
    logits = logits.masked_fill(mask, float("-inf"))
    target = torch.arange(logits.size(0), device=logits.device)
    return 0.5 * (F.cross_entropy(logits, target) + F.cross_entropy(logits.t(), target))

    Batch construction is consequently part of the learning problem. Hard negatives can improve discrimination between related codes; false negatives can damage the very equivalence the encoder should learn. Increasing the encoder’s size does not resolve incorrect labels.

    The neural route still inherits the retrieval ceiling. More candidates increase the chance that the correct code reaches a joint scorer and increase scoring cost. The repository contains the training and optional serving path; that does not establish that a trained endpoint served every request. It also should not be confused with an implemented retrieval system over payer-policy documents. Those would require their own corpus, versioning, retrieval evaluation, and evidence links.

    Turning a model score into a review policy

    Our example still has incomplete medication details and an unknown authorization status. A readiness predictor can help prioritize review, but cannot turn those unknowns into facts. Its job is to estimate a labeled documentation outcome from the features available.

    Synthure evaluates exported gradient-boosted trees. Starting from a bias, it traverses each tree to a leaf and adds that leaf’s value multiplied by the learning rate. A sigmoid converts the accumulated logit into the raw score:

    praw = σ(b + η Σm leafm(x))

    For a toy ensemble with bias −0.4, learning rate 0.1, and selected leaves 1.2 and −0.3, the logit is −0.31 and the score is about 0.423. This is a fitted prediction, not the fraction of documentation rules that passed.

    frontend/lib/models/synthure.ts · lines 113–143 · source revision a9f829bb · selected excerpt

    function gbmProb(x: number[]): number {
  const gbm = (readinessModel as { gbm: { trees: Tree[]; learning_rate: number; init: number } }).gbm
  let s = gbm.init
  for (const t of gbm.trees) {
    let node = 0
    while (t.children_left[node] !== -1) {
      node = x[t.feature[node]] <= t.threshold[node] ? t.children_left[node] : t.children_right[node]
    }
    s += gbm.learning_rate * t.value[node]
  }
  return sigmoid(s)
}
function calibrate(p: number): number {
  const { x, y } = (readinessModel as { calibration: { x: number[]; y: number[] } }).calibration
  for (let i = 0; i < x.length - 1; i++) {
    if (p <= x[i + 1]) {
      const t = (p - x[i]) / (x[i + 1] - x[i] + 1e-9)
      return y[i] + t * (y[i + 1] - y[i])
    }
  }
  return y[y.length - 1]
}
export function predictReadiness(note: string, noteType: string, nDx: number, nProc: number): {
  raw: number; calibrated: number; band: 'ready' | 'needs_work' | 'not_ready'
} {
  const raw = gbmProb(structVector(note, noteType, nDx, nProc))
  const calibrated = calibrate(raw)
  const band = calibrated >= 0.66 ? 'ready' : calibrated >= 0.4 ? 'needs_work' : 'not_ready'
  return { raw: Number(raw.toFixed(3)), calibrated: Number(calibrated.toFixed(3)), band }
}

    The second function maps the raw score through calibration knots. Between (0.4,0.3) and (0.6,0.5), for example, interpolation sends 0.5 to 0.4. Calibration aims for agreement between predicted scores and observed frequencies on comparable cases. It requires separate fitting and evaluation data, and can deteriorate when the input distribution changes.

    The implementation returns the last mapped value above the last knot, but can extrapolate below the first. Boundary tests therefore matter as much as interior examples. A model can rank cases well while producing misleading probability values; AUROC and calibration measure different properties.

    The application turns calibrated scores into three bands: below 0.40 is “not ready,” 0.40 to below 0.66 is “needs work,” and 0.66 or above is “ready.” Those are policy thresholds on top of the predictor. Changing a threshold changes both accepted quality and review workload.

    In the illustrative comparison, accepting 80 cases with four errors gives a 5% accepted-case error rate. Accepting 50 with one error gives 2%, while sending 30 additional cases to review. Reporting the second percentage alone hides the cost. Coverage, error among accepted outputs, and review effort belong together.

    A score of 0.72 still cannot answer our authorization question. Readiness bands, missing-evidence rules, and the final report decision remain separate parts of the workflow.

    Four writers and a dependent audit

    Once the evidence record exists, audience-specific writing becomes a more bounded task. claudeReport combines the shared input with patient, physician, hospital, or employer instructions. A forced report tool constrains the response structure. It does not verify the contents of those fields.

    The route chooses Sonnet for physician and hospital reports in the frontier lane and Haiku otherwise. These are hosted model calls with different instructions, rather than four independently trained models. Since each writer depends on the shared record rather than another writer, their calls can run concurrently:

    Why a high score can still produce a block

    The guardrail system collects findings across input, grounding, policy, consistency, style, and quality. It reports an aggregate score, but decides what to do using precedence rules. Those two outputs serve different purposes.

    display score = 1 − flagged severity weight / total severity weight
    decision order: block → escalate → revise → ship

    A blocking finding wins immediately. Otherwise, extraction confidence below 0.6 or the absence of both diagnosis and procedure codes produces escalation. Medium or high findings request revision; the remaining cases receive ship. Many low-risk passes cannot average away one blocking violation.

    This is useful because factual support, audience permissions, and JSON structure are different requirements. A report may satisfy the schema while assigning a correct value to the wrong condition. A physician report may contain supported information that does not belong in an employer view. One aggregate confidence number cannot express all of these relationships.

    For our note, “surgery is being considered” becoming “surgery was completed” is a useful adversarial case. The words remain related, yet the assertion changes. A stronger checker would compare source-linked claims with fields for subject, relation, value, and status. That is a proposed improvement over relying on token overlap or general model agreement.

    The verdict also needs an enforcing consumer. The route has already streamed reports before the final gate. A later block event cannot erase what was displayed. Display, export, or downstream action code must decide what a blocked artifact may do. Likewise, ship is an application verdict, not clinical validation or evidence of an external submission.

    Audit durability has its own boundary. The demo’s appendAudit is best-effort and catches failures. A local hash chain can help detect alterations only when a trusted earlier fingerprint survives independently; rewriting both records and hashes defeats that protection. Durable storage and anchored history would be separate engineering additions.

    Top-k accuracy asks whether the correct answer appears in the first k results. Mean reciprocal rank also rewards earlier placement: ranks 1, 2, and 5 contribute 1, 0.5, and 0.2. A miss contributes zero under the usual convention. Retrieval coverage and ordering should be examined separately.

    Precision and recall distinguish another pair of failures. If twelve supported entities exist, the extractor finds eight and adds two incorrect entities, precision is 8/10=0.80 and recall is 8/12≈0.667. Their harmonic mean, F1, is about 0.727. High precision can coexist with substantial missing evidence.

    precision = TP/(TP+FP)
    recall = TP/(TP+FN)
    F1 = 2 × precision × recall / (precision + recall)

    Perfect synthetic note-type accuracy needs particular care because the ledger records a template-label leakage caveat. More samples from the same template would not necessarily remove that shortcut. Similarly, 100% identifier recall on 90 seeded spans describes those spans, rather than a guarantee for unrestricted clinical text.

    Readiness reports AUROC 0.839 and ECE 0.054 on the synthetic evaluation. Abstaining on roughly the least-confident fifth raises accuracy from 88.3% to 91.7% at about 80% coverage. This is a useful operating-point result, provided both quality and coverage remain visible.

    Ignoring the old response does not cancel its server work or provider bill. Cancellation must propagate through the client and supported server operations, with a defined response when a provider cannot stop an already-running call.

    The animation introduces a separate completion issue. Deferred promises wait for both a minimum display interval and a stage event. Error and end-of-stream paths call releaseAll to prevent hanging. The presentation loop can then mark stages complete even while an error remains. Unblocking a wait and establishing success need distinct state transitions.

    A robust terminal contract would distinguish success, failure, cancellation, and unexpected disconnection. It would also identify which report versions passed which checks. Durable jobs become useful when a disconnected client needs to recover that state, but persistence should follow a defined lifecycle rather than substitute for one.

    Operational limits are process-scoped in this revision. Rate-limit maps and the daily counter reset on restart and are not shared across server instances. The configured limits—six requests per IP per hour and 200 per day—therefore do not establish deployment-wide quotas. Shared atomic counters would be required for that guarantee.

    For performance work, separate cold model download, warm extraction, retrieval, writer fan-out, audit, and revision. Measure first-report latency, final-gate latency, provider failures, and cost per accepted run. A single elapsed-time average would obscure the stage responsible for the wait.

    Where the next improvements belong

    Synthure’s useful architectural choice is to make the intermediate evidence visible. The application can inspect a span before it becomes a code, a score before it becomes a review decision, and a draft before it becomes an accepted report. That structure gives model improvements somewhere precise to take effect.

    The next improvements follow those boundaries. Offset-aware extraction and assertion status would reduce semantic loss early. Contextual code acceptance would distinguish a valid catalog entry from a supported assignment. Versioned report checks and explicit terminal states would connect the final verdict to the artifact the user actually sees.

    Evaluation should then follow whole notes through that path. Compare writers on identical records, compare audits on identical drafts, and compare accepted quality at matched coverage. A real-note holdout with appropriate grouping would address a different question from another synthetic component benchmark.

    Return to “No chest pain.” The important success is not that a report sounds careful. It is that the original negation survives extraction, coding, writing, revision, and export. A trustworthy system makes that preservation inspectable.
