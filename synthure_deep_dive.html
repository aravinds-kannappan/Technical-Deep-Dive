    Synthure: the engineering behind a note-to-report system

    How Synthure extracts a note, selects candidate codes, and writes four reports—and where the implementation still loses track of evidence or state.

    Two-page cheatsheet · All three cheatsheets

    ·

    The constraint that shapes the system

    The easiest version of this product would send a note to a language model and ask for four reports. Synthure takes a longer route. It extracts mentions, looks up codes, scores documentation, and builds a shared record before asking a model to write. That gives the application places to inspect and reject intermediate results.

    One example explains the constraint: “No chest pain.” Extraction can correctly locate “chest pain” while a later stage incorrectly treats it as an active symptom. The characters are present; the diagnosis is not. The same problem appears when “surgery is being considered” becomes “surgery occurred,” or an unknown authorization status becomes an approval.

    Evidence preservation means retaining those distinctions as data moves between stages. A source span establishes where wording occurred. Context establishes what it asserts. A candidate code proposes a reference match. A readiness score estimates a particular label. None substitutes for the others. Their scores also have different targets, so multiplying them would not yield a meaningful probability that the report is correct.

    This is the central design constraint for the rest of the article. The implementation already carries spans and validates reference codes. It does not establish a complete provenance system for every generated assertion. I’ll describe the implemented path first, including its failure modes. The final section collects the changes I would make next.

    01

    Why split extraction, coding, and writing?

    Synthure turns an encounter note into four audience-specific reports. The browser runs OpenMed extraction and redaction. A Next.js route handles reference lookup, small-model inference, hosted Claude calls, and output checks. This separates the expensive writing step from decisions that can use local rules or compact models.

    Clinical note
  → remove identifying details
  → find and interpret medical mentions
  → retrieve and rank possible codes
  → check missing documentation and readiness
  → write audience-specific reports
  → audit, revise, then accept or request review

    The shared record is the useful architectural choice here. Each writer starts from the same extracted conditions, code candidates, documentation gaps, and reference values. A patient explanation and a physician report can differ in language without starting from different interpretations of the note.

    Compared with a single prompt, the staged design makes failures easier to locate. A wrong code can originate in extraction, candidate retrieval, or ranking. A report can also introduce an error after those steps succeed. Inspecting the intermediate result tells us which component to investigate instead of treating the entire response as one opaque failure.

    The separation also supports controlled comparisons. An extractor can change while lookup and writing stay fixed. A writer can be evaluated against frozen records. That makes it easier to tell whether a change improved the component or merely changed the inputs it received.

    There is a cost: every boundary needs a stable contract. An offset is meaningless without its source string. A feature vector is unsafe without its ordered feature names. A report check applies to a particular draft. Several issues below come from those contracts being weaker than the component-level logic.

    02

    Follow one note across the browser boundary

    Consider this illustrative input, not a recorded run: “Patient A has type 2 diabetes and right-knee osteoarthritis. No chest pain. Knee surgery is being considered. Medication details are incomplete; prior authorization status is unknown.”

    The browser first redacts identifying information. It then extracts medical mentions from the cleaned string. The positive conditions, negated symptom, proposed procedure, and missing details exercise different parts of the workflow. A successful extraction cannot collapse them into one list of active diagnoses.

    The important ordering is visible in useSynthesis.start: load the local models, call deidentify(note), then call extractEntities(deid.text). Only after those operations does the browser POST the cleaned text, entity spans, and redaction metadata. A local model-loading or inference failure returns before this request.

    Redaction can change string length. Replacing a name with a placeholder moves every later character if their lengths differ. Because extraction runs afterward, its offsets refer to deid.text. Sending that same string lets the server check whether each submitted phrase occurs at the stated position. Using the original note with those offsets would produce false mismatches or incorrect highlights.

It cannot infer from the request alone that a browser performed redaction, and identifiers missed locally can still reach the server.

    After lookup and documentation checks, the resulting record becomes input to the four writers. The physician report can identify missing medication details. The patient report can explain the need for clarification. The employer report has a narrower information scope. The diagram traces that one missing item through these transformations.

    The example gives us a useful debugging sequence: inspect the cleaned text, verify its spans, inspect the structured result, then compare each report against that result. An HTTP success response says little about whether the note survived these transformations correctly.

    03

    Recover spans without losing their context

    OpenMed’s token predictions must become character ranges that the application can highlight and validate. The browser uses ONNX models, with documented int8 quantization to reduce model storage and potentially computation. That is a practical browser constraint: download size, startup time, and local memory all affect whether extraction is usable.

    The aggregation code joins compatible BIO-tagged pieces and strips WordPiece’s ## prefix. It then searches forward through the note to recover the phrase’s position. For a multiword entity, the merger takes the minimum token confidence rather than allowing strong tokens to hide one weak prediction.

    Text:     chronic      kidney       disease
Labels:   B-DISEASE    I-DISEASE     I-DISEASE
Meaning:  beginning   continuation  continuation

Merged mention: "chronic kidney disease"
Next question: Is it current, negated, uncertain, or historical?

    The range convention is [start, end): the start is included and the end is excluded. A span’s length is therefore end - start. Adjacent spans can meet at one boundary without sharing a character. The convention matters when the same ranges drive slicing, replacement, and validation.

    Redaction is a string-editing problem too

    deidentify replaces accepted ranges from right to left. Consider ranges [5,10) and [20,25). Replacing the first five characters with a twelve-character placeholder would shift the second range by seven. Replacing the later range first leaves the earlier coordinates intact.

    frontend/lib/openmed.ts · lines 175–185 · inspected revision a9f829bb · selected excerpt; follow the source for surrounding code

    export async function deidentify(text: string, minScore = 0.5): Promise<DeidResult> {
  const hits = await run('deid', text, minScore)
  // Replace right to left so earlier spans keep their offsets.
  let clean = text
  const types = new Set<string>()
  for (const h of [...hits].sort((a, b) => b.start - a.start)) {
    const tag = h.label.toUpperCase()
    types.add(tag)
    clean = clean.slice(0, h.start) + `[${tag}]` + clean.slice(h.end)
  }
  return { text: clean, redactions: hits.length, types: [...types].sort() }

    Disease and chemical extraction subsequently run with Promise.all. Duplicate (start, end, type) keys retain the higher confidence. These independent passes can overlap, although they still compete for browser compute and memory.

    Where the current approach loses information

    Searching for reconstructed text is a workaround for missing tokenizer offsets. In “pain improved; pain returned,” identical surface text refers to two occurrences. A forward cursor is better than repeatedly taking the first match. Punctuation, normalization, and rejected spans can still disturb alignment. A correctly typed entity at the wrong position is a different failure from a missed entity.

    The minimum-token score is similarly a useful heuristic, not a calibrated span probability. It favors the weakest piece, but it does not account for whether the merged boundary is correct. A threshold can suppress uncertain spans while still retaining confidently misplaced ones.

    The abbreviation dictionary addresses another concrete weakness: models trained on spelled-out terms can miss shorthand such as HTN. A dictionary is cheap and easy to inspect. Its weakness is ambiguity; the same abbreviation may mean different things in different contexts.

    The route also uses nearby negation rules. They can catch “denies fever,” but scope matters in “no fever but persistent cough.” Family history, past diagnoses, and “rule out” language create further distinctions. Literal occurrence checks protect the request’s integrity; they do not resolve these contextual relationships.

    These failures point to separate evaluation targets: boundaries, entity types, and assertion status. Combining them into one extraction score would make it difficult to tell whether a change fixed localization or merely changed which mentions survived the threshold.

    04

    Serve small models as explicit arithmetic

    Synthure uses compact models for note type and missing documentation. Their outputs are small and structured, so sending every decision through a hosted language model would add latency and cost. Exported JSON weights let the TypeScript request path reproduce the fitted arithmetic without loading Python or another transformer.

    classifyNoteType counts unigrams and bigrams found in the exported vocabulary. Each retained term receives (1 + ln count) × IDF. The resulting sparse vector is L2-normalized. Each class then computes an intercept plus its weighted feature sum.

    Walk through the numbers

    Take an illustrative vocabulary with “refer,” “specialist,” and “refer specialist.” Suppose the first two occur once, the bigram is absent, and their IDF weights are 2 and 1. The raw vector is [2,1,0]. Dividing by √5 gives approximately [0.894,0.447,0]. Normalization prevents document length alone from scaling every score upward.

    Suppose the class logits are [2,1,0]. Subtracting their maximum gives [0,-1,-2]. Exponentiation and normalization produce approximately [0.665,0.245,0.090]. Subtracting the maximum preserves the result because it scales every exponential by the same factor. It also avoids overflow for large logits.

    These values explain the calculation; they are not the exported coefficients. The useful implementation detail is that the same vector feeds all note-type classes. Each class has its own weights and intercept, and softmax produces mutually exclusive class scores.

    An input with no recognized vocabulary terms exposes an edge case. The vector stays empty, the normalization denominator falls back to one, and the logits come entirely from the intercepts. The function still returns a class. Its confidence can therefore look ordinary even though the note contributed no recognized lexical evidence.

    Missing fields use a different output contract

    structVector produces ordered counts, lexical flags, normalized note length, and one-hot note type. detectMissing applies a separate sigmoid classifier to each field. This allows dosage and laterality to be flagged together instead of forcing them into competing categories.

    For a toy binary classifier, an intercept of −1 and feature contributions of 2 and 1 produce a logit of 2. Applying 1 / (1 + exp(-2)) gives about 0.881. The numerical operation is straightforward; the meaning depends on the target label.

    Here the returned property present means the missing-field flag is present at a probability of at least 0.5. It does not mean the medical detail was documented. The route filters on this property to construct its missing-fields list. That naming is easy to misread when debugging the caller.

    The feature design also limits what the model can distinguish. “Left arm examined; knee pain” contains a laterality word, but it does not specify the knee’s side. A global lexical flag cannot express that relationship. Reproducing Python’s output exactly would verify serving parity while leaving this semantic weakness untouched.

    The tradeoff is explicit: cheap, inspectable inference handles narrow decisions, while context-sensitive relationships remain difficult. The next section shows the same pattern in coding, where retrieval narrows the search before a small model ranks candidates.

    05

    Retrieve codes, then inspect the selection path

    The local coding path starts with an inverted index over reference terms. icdCandidates expands known abbreviations and looks up token-to-term postings. It first requires every unique query token, then relaxes to one fewer token, then backs off to strong tokens. Candidates are ordered using overlap, head-word agreement, and fewer extra terms.

    This avoids a full catalog scan for each mention. Strict matching keeps the initial list focused. Backoff helps when wording differs from the reference, but admits more ambiguity. A qualifier such as laterality can matter more than another shared word, even when an overlap score treats both as similar evidence.

    linkDiagnoses takes up to eight candidates. Its logistic reranker uses four features: overlap, term length, billability, and retrieval rank. The route keeps the best candidate above 0.15, validates codes against the tabular artifact, and deduplicates accepted codes.

    frontend/app/api/synthesize/route.ts · lines 228–248 · inspected revision a9f829bb · selected excerpt; follow the source for surrounding code

    const LINK_FLOOR = 0.15 // reranker probability below which we abstain

function linkDiagnoses(diagnoses: Entity[]): LinkedCode[] {
  const out: LinkedCode[] = []
  const usedCodes = new Set<string>()
  for (const e of diagnoses) {
    const cands = icdCandidates(e.text, 8)
    if (!cands.length) continue
    let best: { c: IcdCandidate; s: number } | null = null
    for (const c of cands) {
      const s = rerankScore({ overlap: c.overlap, termlen: c.termLen, billable: c.billable ? 1 : 0, rank: c.rank })
      if (!best || s > best.s) best = { c, s }
    }
    if (!best || best.s < LINK_FLOOR) continue // abstain -> entity stays uncoded
    const key = best.c.code.replace('.', '').toUpperCase()
    if (usedCodes.has(key)) continue
    usedCodes.add(key)
    out.push({ code: best.c.code, label: best.c.description, billable: best.c.billable, source: 'linked', entity: e.text, score: Number(best.s.toFixed(3)) })
  }
  return out
}

    The source header describes Claude selecting candidates, but this function calls rerankScore in process. That difference matters when explaining the architecture. At this revision, the executable local path is a small lexical reranker, not a language model reading the entire note to make the selection.

    Retrieval and ranking fail differently

    Suppose retrieval includes the correct answer for 90 of 100 mentions. A reranker cannot recover the missing ten. If it selects correctly on 72 of those 90, overall top-1 accuracy is 72%, while accuracy conditional on successful retrieval is 80%.

    That decomposition tells us where to spend effort. Better ranking cannot fix absent candidates. A broader candidate set can improve recall but increase cost and make discrimination harder. Evaluation at the actual shortlist size is more informative than a single final score.

    The four-feature reranker has no direct representation of the relationship between a condition and its qualifiers. For “knee osteoarthritis,” a candidate requiring a side can score well even if the note never supplied one. Billability is catalog metadata, not evidence that this encounter supports a billable claim. The evidence distinction established at the start applies at this acceptance boundary.

    The 0.15 floor lets the route abstain on weak matches. It does not measure ambiguity between two strong candidates. Nor does a large gap between scores prove the winner is supported: both candidates can be wrong. Threshold behavior needs evaluation against accepted error and review volume.

    When configured, modelLinkCodes sends mentions to a remote endpoint with a 25-second timeout. Every returned code is checked against the local reference before it can be added. Literal codes can overwrite lexical links, and the optional service can confirm or add validated codes.

    06

    What the optional neural retriever actually trains

    The repository also contains a neural coding model. It is worth explaining directly rather than treating every lookup as “RAG.” The current route combines lexical reference lookup, optional neural coding, and report generation from a shared record. That does not establish a deployed payer-policy document search system or an IVFFlat index.

    The BiEncoder mean-pools token states using the attention mask and normalizes the resulting B × D vectors. Code descriptions can be encoded ahead of time. At request time, a query vector retrieves candidate descriptions by dot product. With normalized vectors, that comparison measures cosine similarity.

    Caching reference embeddings is the efficiency gain. The model does not jointly read the query with every description on every request. A CrossEncoder does read each query-candidate pair together, which allows interactions between their words but costs a forward pass per pair.

    The staged alternative is therefore broad retrieval followed by joint scoring of a short list. A longer list can improve candidate coverage while increasing inference work. A short list saves work but makes missed candidates unrecoverable, as the preceding example showed.

    Avoid treating synonyms as negative examples

    The training loss builds a B × B similarity matrix and divides it by temperature. Each phrase-description pair supplies a positive example. Other items in the batch provide negatives, except that same-code off-diagonal pairs are masked.

    ml/icd_coder/model.py · lines 45–58 · inspected revision a9f829bb · selected excerpt; follow the source for surrounding code

    def info_nce(anchor: torch.Tensor, positive: torch.Tensor, codes: torch.Tensor, temperature: float) -> torch.Tensor:
    """Symmetric in-batch InfoNCE.

    anchor[i] and positive[i] are the phrase and its code's description. Any j!=i
    with the same code is masked out so a true synonym is never punished as a
    negative (in-batch collisions are common in a 98k-code space).
    """
    logits = anchor @ positive.t() / temperature           # (B, B)
    same = codes.unsqueeze(0) == codes.unsqueeze(1)         # (B, B) same code
    eye = torch.eye(logits.size(0), dtype=torch.bool, device=logits.device)
    mask = same & ~eye
    logits = logits.masked_fill(mask, float("-inf"))
    target = torch.arange(logits.size(0), device=logits.device)
    return 0.5 * (F.cross_entropy(logits, target) + F.cross_entropy(logits.t(), target))

    That mask addresses a concrete labeling problem. Two different phrases can map to the same code. Without masking, the loss could push a phrase away from another valid description merely because it occupies a different batch position. Symmetric cross-entropy trains both phrase-to-description and description-to-phrase directions.

    Temperature controls the sharpness of the similarity distribution used by the loss. The batch composition also matters: the learning signal depends on which alternatives appear together. This is why the training objective cannot be understood from the encoder architecture alone.

    These mechanics describe the model code. They do not prove that a hosted instance served any particular request. The route’s optional-service behavior, described above, is the link between this training implementation and application use.

    For policy retrieval, further machinery would be necessary: source passages, document versions, effective dates, and applicability checks. That remains a separate design question. Adding a generic tutorial about chunking and vector indexes obscured the code that this prototype actually uses.

    07

    Turn tree outputs into a review decision

    Readiness estimates whether documentation resembles the model’s ready examples. Its target is not insurance payment. The implementation combines exported gradient-boosted trees with a fitted calibration mapping, then assigns an application band.

    gbmProb starts with a bias. For every tree, it reads a feature index, compares that value with a threshold, and follows one child until it reaches a leaf. The leaf value is multiplied by the learning rate and added to the score. After all trees, sigmoid produces the raw output.

    frontend/lib/models/synthure.ts · lines 113–143 · inspected revision a9f829bb · selected excerpt; follow the source for surrounding code

    function gbmProb(x: number[]): number {
  const gbm = (readinessModel as { gbm: { trees: Tree[]; learning_rate: number; init: number } }).gbm
  let s = gbm.init
  for (const t of gbm.trees) {
    let node = 0
    while (t.children_left[node] !== -1) {
      node = x[t.feature[node]] <= t.threshold[node] ? t.children_left[node] : t.children_right[node]
    }
    s += gbm.learning_rate * t.value[node]
  }
  return sigmoid(s)
}
function calibrate(p: number): number {
  const { x, y } = (readinessModel as { calibration: { x: number[]; y: number[] } }).calibration
  for (let i = 0; i < x.length - 1; i++) {
    if (p <= x[i + 1]) {
      const t = (p - x[i]) / (x[i + 1] - x[i] + 1e-9)
      return y[i] + t * (y[i + 1] - y[i])
    }
  }
  return y[y.length - 1]
}
export function predictReadiness(note: string, noteType: string, nDx: number, nProc: number): {
  raw: number; calibrated: number; band: 'ready' | 'needs_work' | 'not_ready'
} {
  const raw = gbmProb(structVector(note, noteType, nDx, nProc))
  const calibrated = calibrate(raw)
  const band = calibrated >= 0.66 ? 'ready' : calibrated >= 0.4 ? 'needs_work' : 'not_ready'
  return { raw: Number(raw.toFixed(3)), calibrated: Number(calibrated.toFixed(3)), band }
}

    For illustration, use an initial score of −0.4, a learning rate of 0.1, and selected leaf values of 1.2 and −0.3. The final logit is -0.4 + 0.1 × (1.2 - 0.3) = -0.31. Sigmoid gives approximately 0.423. The result is an ensemble sum, not a count of documentation rules that passed.

    Trees can capture nonlinear interactions among the structured features while keeping serving inexpensive. They still inherit the limits of those features. A lexical laterality flag does not become condition-specific merely because a tree uses it.

    Calibration changes the scale, not the input

    calibrate interpolates between exported isotonic mapping knots. For illustrative knots (0.4,0.3) and (0.6,0.5), a raw score of 0.5 maps to 0.4. The mapping preserves order while changing how the score relates to observed outcomes.

    Calibration is a population property. Among comparable cases scoring near 0.8, approximately 80% should meet the specified positive label. That interpretation depends on the calibration data and may fail on a different note distribution. It is not a guarantee for the individual case.

    The implementation returns the last mapped value above the final knot. Below the first knot, it enters the first interval and can extrapolate. That boundary behavior is easy to miss if tests exercise only scores inside the fitted range.

    predictReadiness assigns “not ready” below 0.40, “needs work” from 0.40 to below 0.66, and “ready” at 0.66 or above. Calibration can move a case across one of these thresholds without changing its rank relative to other cases. The thresholds belong to the application policy, rather than to the tree structure.

    Readiness and review volume must be measured together

    Suppose a policy accepts 80 of 100 cases and makes four errors. Accepted-case error is 5%, with 80% coverage. A stricter policy might accept 50 cases and make one error: 2% error with 50% coverage. It also sends 30 additional cases to review.

    The tradeoff cannot be summarized by accuracy alone. The recorded evaluation later in this article reports a similar coverage change after abstention. It needs to be read alongside the work transferred to people.

    The implementation also has rule-based readiness checks and a final guardrail decision. These remain separate from the numerical band. A score of 0.72 cannot answer an unresolved authorization question. The model ranks documentation patterns; the workflow still has to account for missing evidence.

    08

    Four writers, one shared input, two revisions

    The route calls claudeReport for patient, physician, hospital, and employer audiences. Each call receives the shared record and role-specific instructions. A forced report tool supplies structured fields. This makes the output easier to parse and inspect, though factual checks happen separately.

    The concrete reason for separate writers is audience control. Each prompt can define its scope and presentation requirements. Four calls also cost more than one structured response, and all four inherit errors in the common record. Agreement between their outputs is therefore not independent verification.

    writerModel selects Sonnet for physician and hospital writers only in the frontier lane. Other cases use Haiku. This is task routing through hosted inference; the application is not training four independent models or controlling the provider’s GPU scheduler.

    Fan out the independent calls

    The route launches the writers with Promise.all. Each writer optionally obtains faithfulness flags and streams its report when ready. Sorting afterward restores a stable stakeholder order for the combined audit.

    The audit cannot start until the group resolves because it consumes all four reports. A slow faithfulness call can therefore delay that dependency even after its writer finishes. A rejected promise fails the group; this implementation does not isolate each writer’s failure or define partial success through allSettled.

    Streaming improves visibility during the wait, but the emitted drafts precede the final gate. This creates a product-state issue discussed in the next section: receiving text is not the same event as accepting it.

    Consolidation reduces duplicated context and request overhead. It also makes both judgments depend on one model response. That is an engineering tradeoff, not a quality result that follows from reducing the call count.

    After the audit, the route groups issues by report target and iterates through them. The revision budget is two report revisions for the entire run. It is not two attempts per report.     This is the most useful way to explain the orchestration: independent writing, a dependent combined audit, a limited repair budget, and final deterministic checks. “Four agents” hides these details. The actual control flow explains both the latency benefit and the remaining failure cases.

    Make the verdict distinct from the score

    The output checker evaluates a new artifact: the generated report. It combines model findings with deterministic checks for input, grounding, policy, consistency, style, and quality. The important implementation choice is that the final decision uses priority rules rather than a simple average.

    runGuardrails computes a displayed score as one minus flagged severity weight divided by total severity weight. The decision follows a separate order: a blocking violation produces block; low extraction confidence or no codes produces escalate; medium or high findings produce revise; otherwise the function returns ship.

Finding an allowed number or phrase somewhere in the source does not establish that the report attached it to the correct person, condition, or status.

    Three properties need separate treatment. Structural validation checks required fields and types. Factual validation checks the assertions inside them. Disclosure validation checks whether the audience should receive those assertions. Valid JSON can fail either of the latter two.

    A computed block does not retract a streamed draft

    The route emits reports before the final verdict. It later sends guardrail and harness events and continues to synthesize an overview. A block event is therefore a decision in the stream; the route alone does not prove that earlier text was withheld or that every downstream export enforces it.

    The same distinction applies to ship. It is the checker’s verdict for its rules, not evidence that a claim was submitted or that a separate consequential action was authorized. The code path that consumes the verdict determines what happens next.

    Revision adds a versioning issue. The final deterministic pass checks the replaced text, while the earlier model checks applied to the original draft. Counting audit calls or revision attempts does not tell us which checks cover the artifact the user ultimately sees.

    The audit store has a weaker guarantee than its comment

    The client calls appendAudit and catches failures because logging is best-effort in the demo. Calling a record “immutable” in a comment does not change that storage behavior.

    A local hash chain can expose some edits if a trusted earlier fingerprint is retained. If the store and its hashes are writable together, both can be replaced. The implementation therefore does not establish durable, independently anchored audit history.

    These are specific limits, not reasons to discard the checker. Priority gates provide useful control logic. The remaining questions concern where those decisions are enforced, which report version they cover, and whether the audit survives failure. Those become concrete follow-up work in the final section.

    Streaming exposes progress, and a completion bug

    The browser submits a POST to the synthesis route and reads server-sent events from the response. Events carry stages, reports, audits, and gates. This lets the interface show useful progress while dependent work continues.

    The request’s duration follows that dependency graph. Local model loading and extraction precede the POST. Server analysis precedes writing. The combined audit waits for the writers, and revisions add further work. Overlapping the four writers shortens one phase without removing these serial dependencies.

    The figure uses toy timings: two seconds locally, one for analysis, five for parallel writers, and two for auditing. The critical path is about ten seconds. Measuring first-visible output separately from the final checked result would capture the benefit of streaming without confusing it with faster completion.

    Network chunks are not application events

    The client appends decoded bytes to a buffer and looks for a double-newline delimiter. A read can end halfway through an event or contain several events. Parsing one JSON object per network chunk would therefore be incorrect.

    Presentation completion can diverge from request success

    The hook gates its stage animation on deferred promises. In the normal path, it waits for both a minimum display interval and the relevant event. This keeps a fast stage readable without treating a timer as proof that work finished.

    The error and end-of-stream paths call releaseAll to avoid leaving those promises unresolved. The presentation loop can then mark stages done and set the phase to complete while an error remains in state. This is a concrete failure in the state model: releasing waits and declaring success are different operations.

    A closed stream can mean successful completion, failure, cancellation, or disconnection. The current presentation behavior does not reliably preserve that distinction. It can make the interface look finished even though the request did not reach a successful terminal result.

    Process-local limits do not provide a shared budget

    The rate limiter stores maps and a daily counter inside one serverless process. It uses limits of six requests per IP per hour and 200 per day in that process. Another instance gets another counter, and a restart loses the old one. Naming the daily counter global does not make it deployment-wide.

    Cached artifacts have a similar scope. Reusing them in a warm process avoids repeated loading there, but says nothing about a second process. Browser model downloads, remote service wake-up, writer latency, and revision calls contribute differently to cold and warm requests.

    SSE also provides no durable job state. A disconnected browser can lose presentation while inference continues. Cancellation, deduplication, and reconnectable jobs address different parts of that problem. Adding a queue without defining those states would merely move the ambiguity elsewhere.

    The operational story is therefore more specific than “the app streams.” It frames partial messages correctly and suppresses stale UI updates. It still needs explicit terminal states and stronger ownership of in-flight work. Those are more immediate issues than speculative scaling infrastructure.

    What I would change next

    The implemented design has a useful division of labor: local extraction, reference lookup, cheap predictive models, hosted writing, and priority-based checks. I would keep that structure. The next work should strengthen its contracts and measure the final result. The changes below are proposals, not features claimed by the current revision.

    First, make completion and report acceptance explicit

    I would fix the stream state model before adding more generation features. The server should emit an explicit terminal result, and the client should distinguish success, failure, cancellation, and unexpected disconnection. Releasing animation promises should only unblock presentation; it should not mark the job successful.

    Drafts should remain visibly provisional until the final decision. Every export or action boundary should consume that decision for the exact report version. Revisions should invalidate earlier checks, with required checks rerun against the replacement. A severity-based revision policy would also make better use of the two-report budget and expose unrevised targets.

    Then, make unsupported inferences inspectable

    I would attach source spans, assertion status, and transformation provenance to the shared record. Candidate codes would retain their retrieval route and acceptance reason. Visit suggestions and fee estimates would carry explicit assumptions. Each writer draft would identify the record revision it consumed.

    For extraction, tokenizer-provided offsets would remove much of the reconstruction ambiguity when available. Fixtures should cover repeated mentions, punctuation, negation scope, historical conditions, and relatives. Redaction tests should retain the original and cleaned strings so offset changes can be checked directly. A review of the cleaned note would make missed identifiers visible before submission.

    For coding, I would measure recall@8 before changing the reranker. I would then evaluate context-aware acceptance and near-tie handling on the same holdout. For missing fields, I would compare per-field thresholds and recall against the current 0.5 baseline. Neither change should be justified by a better aggregate percentage alone.

    Evaluate the complete path before claiming production quality

    I would build a patient- or source-disjoint real-note holdout, with related generation templates kept together where synthetic data is used. Each case should retain reference answers, extracted spans, candidates, selected routes, report versions, and final decisions. That makes it possible to attribute an end-to-end failure to the stage that introduced it.

    The report should include accepted-output error, coverage, review effort, and sample counts. Readiness calibration needs reliability checks on that holdout, including behavior outside the fitted knot range. Fixed-input Python/TypeScript fixtures should compare logits before rounding to protect numerical parity independently of semantic quality.

    I would also compare one structured writer with four audience prompts, and compare the consolidated audit with separate calls. Those experiments would test whether the additional generation cost and audit consolidation deliver the intended quality tradeoffs. The ledger should identify exact code, model, dataset, and threshold revisions.

    Add operational machinery in response to measured failures

    Cancellation should propagate from the browser through server work and provider calls where supported. Optional coder outcomes should be recorded per request rather than inferred from configuration. Bounded retries and explicit failed-writer states would make recovery understandable without silently treating partial output as complete.

    If disconnects and duplicate work justify it, a durable job ID and persisted transitions would let clients reconnect to the same computation. Deployment-wide budgets need shared atomic counters; bounded concurrency controls simultaneous expensive calls. These solve different constraints and should be measured separately.

    Finally, a production audit trail would need durable access-controlled storage and an independently retained anchor if tamper evidence is required. I would measure cold and warm latency, first-report time, final-gate time, abandoned work, and cost per accepted report. Those measurements would tell us which infrastructure change solves an observed problem.
