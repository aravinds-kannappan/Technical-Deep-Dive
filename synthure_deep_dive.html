    Synthure: following a note through the system

    A clinical note becomes extracted spans, candidate codes, readiness estimates, and four reports. Following that journey exposes where the system preserves evidence, where it makes a prediction, and where a human still needs to decide.

    The difficult part of Synthure is keeping the meaning of a note intact as it crosses several different kinds of software. A disease detector can locate a phrase without understanding its negation. A code can exist in a reference table without being supported by this encounter. A report can be fluent and still convert a proposal into a fact. This article follows those boundaries in the implementation, then examines the models, evaluation results, and serving decisions that determine whether the final explanation is trustworthy.

    The terms, through one example

    Span. In “No chest pain,” the words “chest pain” occupy a particular character range. That range is a span. Saving it lets the program point back to the actual evidence; it does not make the symptom present.

    Entity. The extractor labels that span as a clinical mention. Context must still determine whether it is negated, historical, uncertain, or current.

    Candidate. A reference lookup returns possible codes for a supported mention. A candidate is an option to check, not an approved coding decision.

    Reranker. A small scoring model orders those candidates using features such as word overlap and initial retrieval rank. Its highest score can still be too weak to accept.

    Abstention. The program leaves a mention uncoded when it cannot meet its threshold. Preserving an unresolved field is preferable to silently inventing specificity.

    Report and verdict. A writer turns the shared record into audience-specific prose. Separate checks then decide whether the output should ship, be revised, be blocked, or be escalated. A readiness score and a final verdict answer different questions.

    01

    The problem: turning a note into checkable information

    A note is written for people. It may mix symptoms, past conditions, abbreviations, uncertainty and administrative details in one paragraph. Other software needs separate fields: which condition is mentioned, whether it is present, which code might describe it, and which information is missing.

    Synthure’s documented prototype breaks this problem into stages. It first identifies information in the note, then looks up possible codes, checks documentation, and finally writes explanations for different audiences. This order matters: a fluent explanation is only useful if its underlying information is correct.

    Clinical note. The text describing an encounter. An encounter is a particular interaction with a patient, rather than the patient’s entire history.

    Structured record. Information stored in named fields, such as condition, source_text and missing_fields. Explicit fields let later steps check what each value means.

    Pipeline. A sequence of processing steps. Each step receives something, changes or checks it, and passes an output to the next step.

    Model. A program with numerical settings learned from examples. A rule is different: a programmer specifies exactly what to do when a condition is met.

    Clinical note
  → remove identifying details
  → find and interpret medical mentions
  → retrieve and rank possible codes
  → check missing documentation and readiness
  → write audience-specific reports
  → audit, revise, then accept or request review

    The browser is the program on the user’s device. The server is the remote program receiving requests. The documented design runs OpenMed extraction models in the browser, then sends the processed note to a Next.js server route. That route combines lookups, small models and hosted Claude writing calls.

    The pipeline only becomes concrete when the same piece of evidence is followed through every transformation. Start with a short example, then inspect the boundary where the browser hands its work to the server.

    02

    One note, followed from beginning to end

    Illustration — not a clinical recommendation or recorded run

    “Patient A has type 2 diabetes and right-knee osteoarthritis. No chest pain. Knee surgery is being considered. Medication details are incomplete; prior authorization status is unknown.”

    Protect identifiers. Replace information that can identify the person. Keep the relevant medical wording. The output is a less identifiable note, not a guarantee that every identifying clue has disappeared.

    Locate mentions. Highlight “type 2 diabetes,” “right-knee osteoarthritis” and “chest pain.” Save where each phrase occurs. At this point, the system has found phrases; it has not decided that all three describe active conditions.

    Interpret context. “No chest pain” negates that mention. “Surgery is being considered” is a proposal, not evidence that surgery occurred. “Right-knee” supplies a side that must remain attached to the knee condition.

    Look up candidate codes. Search the official diagnosis terminology for each supported condition. Keep several plausible entries if the note is ambiguous. Never fill a missing detail just to obtain a more specific code.

    Check documentation. Medication details and authorization status remain unknown. A model can flag these gaps, but it cannot convert “unknown” into “approved.”

    Build a shared fact record. Give every writer the same supported conditions, unresolved questions and reference entries. This avoids four writers inventing four different versions of the encounter.

    Generate reports. A patient explanation uses everyday language. A physician view emphasizes evidence and missing clinical detail. A hospital view focuses on administrative checks. An employer view must respect its more restricted information scope.

    Check the output. If a writer invents a dose or states that authorization is approved, the report must be corrected or withheld. Correct earlier stages do not make every generated sentence correct.

    The important output may therefore be a request for clarification, rather than a finished claim. This is useful behavior: the system makes a missing fact visible instead of disguising it with confident language.

    03

    How extraction works: spans, tokens, abbreviations and negation

    A token is a piece of text used by a model. It may be a word, part of a word or punctuation. A token classifier assigns a label to each piece. For example, it can mark the beginning and continuation of a disease name. Named entity recognition (NER) is the task of locating meaningful mentions and identifying their types.

    A span is a continuous stretch of the original text, described by its start and end positions. If “chronic kidney disease” occupies characters 12 through 33, preserving those positions lets the application show exactly what was extracted. Several token predictions may need to be joined into this one span.

    Text:     chronic      kidney       disease
Labels:   B-DISEASE    I-DISEASE     I-DISEASE
Meaning:  beginning   continuation  continuation

Merged mention: "chronic kidney disease"
Next question: Is it current, negated, uncertain, or historical?

    The documented implementation describes OpenMed models saved in ONNX, a format for running trained models in different environments. The browser runtime performs the numerical calculations. Quantization stores some numbers with fewer bits; the documented int8 models use eight-bit representations for relevant model values, reducing storage and potentially computation. That is an efficiency choice, not a promise of identical accuracy.

    A confidence score is the model’s numerical preference for a prediction. The described merger uses the lowest token score within a span as a conservative span score. If one word is uncertain, the whole phrase should not appear more certain simply because the other words were easy. However, this is a rule for combining scores; it does not prove that a score of 0.8 corresponds to an 80% real-world success rate.

    Why rules still matter

    A regular expression, often shortened to regex, matches a specified text pattern. Rules can recognize familiar abbreviations such as HTN and expand them to hypertension. They are fast and inspectable. They can also fail when the same abbreviation has several meanings.

    Negation means that the text says something is absent. A nearby-word rule can catch “denies fever,” but a short search window is not a complete understanding of a sentence. “No fever but persistent cough” should negate fever only. “Rule out infection” expresses uncertainty, which is different from both confirmed infection and confirmed absence.

    Inspect the original phrase, its position, its surrounding clause and the reason it was retained or suppressed. A later coding error may begin with a missed “no,” not with a bad code lookup.

    De-identification uses related extraction techniques to find identifying details. A missed identifier can remain in the processed note. The seeded tests discussed later are evidence about those examples, not proof of perfect privacy for all possible text.

    BIO tags become character spans, then redactions

    aggregate joins B-/I- tagged word pieces, strips the WordPiece ## prefix, finds the resulting phrase with a forward-moving cursor, and uses the minimum token confidence for the entire span. deidentify replaces accepted spans from right to left. For spans [5,10) and [20,25), replacing the latter first leaves the former's offsets valid. Disease and chemical extraction then run with Promise.all; duplicate (start,end,type) keys retain the higher confidence.

    export async function deidentify(text: string, minScore = 0.5): Promise<DeidResult> {
  const hits = await run('deid', text, minScore)
  // Replace right to left so earlier spans keep their offsets.
  let clean = text
  const types = new Set<string>()
  for (const h of [...hits].sort((a, b) => b.start - a.start)) {

    types.add(tag)

    Offsets are part of the evidence contract

    De-identification happens before clinical extraction in the browser flow. That order has a consequence beyond privacy: the entity offsets now refer to the cleaned string. If a name is replaced by a shorter placeholder, every later character can move. A server checking a span against the original note would reject valid results or attach them to the wrong phrase. The request must therefore carry the same cleaned text on which extraction ran, and any highlight on the original document needs an explicit offset mapping.

    The server checks literal occurrence because a client-supplied confidence score is not trustworthy evidence by itself. Literal occurrence is a useful integrity check, but it is only the first check. “Family history of diabetes” contains the word diabetes. A phrase copied exactly from the note can still refer to a relative, a past diagnosis, or an excluded possibility. This is why entity detection, context interpretation, and code selection remain separate stages.

    The abbreviation pass addresses a specific weakness described in the comments: models trained on spelled-out language miss common shorthand. A deterministic dictionary makes those cases inspectable and inexpensive to repair. The tradeoff is context dependence. An abbreviation expansion should retain the source span and the expansion rule, so a reviewer can see whether the system recognized a supported condition or overextended a familiar acronym.

    Once mentions and context have been extracted, the application also needs decisions about the note as a whole. These smaller models operate on explicit features, which makes their mechanics different from the report writer’s.

    04

    How small models classify notes and flag missing information

    A classifier chooses a category from a defined set. A note-type classifier might choose “referral,” “discharge summary” or “radiology report.” A missing-field classifier answers a narrower question such as whether a required detail appears to be absent. These tasks have short outputs and can often use inexpensive, inspectable models.

    Training finds numerical settings from labeled examples. A label is the desired answer for a training example. Inference applies the learned settings to a new input. Loading a saved classifier and asking it to classify a note is inference; the classifier does not learn anew on every request.

    Step 1: turn wording into numerical features

    A feature is a number used as evidence by a model. TF-IDF is a method that gives weight to words according to how often they appear in a document and how unusual they are across documents. A common word such as “the” is usually less informative than a phrase such as “discharge instructions.” A unigram is one word; a bigram is a two-word sequence.

    The result is a list of word-related numbers. Most possible words are absent from any one note, so most entries are zero. This is called a sparse representation. Unlike a human reader, this representation alone does not reliably capture long-range context or the difference between every negated and positive sentence.

    Step 2: combine the evidence

    Logistic regression combines features with learned weights. A positive weight increases a category’s score when the feature is present; a negative weight decreases it. A bias is a starting offset before the features contribute.

    Illustrative arithmetic — not the project’s fitted coefficients

    Suppose a referral detector starts at −1, adds 2 when “refer to” appears, and adds 1 when a specialist is named. With both features present, its raw score is −1 + 2 + 1 = 2.

    The sigmoid function converts any raw score into a number between 0 and 1. A raw score of 2 becomes about 0.881. That smooth conversion is useful for ordering cases and setting thresholds, but a score still needs evaluation before it is treated as a reliable probability.

    s = b + w₁x₁ + w₂x₂
    p = 1 / (1 + exp(−s))

    Here x₁ and x₂ are feature values; w₁ and w₂ are their learned weights; b is the bias; s is the raw score; and p is the transformed score. exp is the exponential function. The subscripts merely distinguish the first and second feature.

    For several mutually exclusive note types, softmax converts one raw score per category into positive scores that sum to one. For several independently missing fields, separate binary classifiers make more sense: dose and laterality can both be missing.

    Portable inference is explicit numerical computation

    classifyNoteType creates unigram and bigram counts, keeps tokens in the exported vocabulary, computes (1 + ln count) × IDF, and L2-normalizes that sparse vector. Each class logit is its intercept plus a weighted feature sum; subtracting the largest logit makes softmax numerically stable. structVector separately emits ordered counts, lexical flags, normalized length, and one-hot note type. detectMissing applies one sigmoid classifier per field.

    05

    From a phrase to a code: retrieval, ranking and validation

    ICD-10-CM is a standardized diagnosis coding system. CPT describes medical procedures and services. Knowing that a code exists is different from establishing that it applies to this encounter. The note may lack a necessary qualifier, and billing requirements involve more than string matching.

    Retrieval gathers plausible entries from a reference collection. Ranking orders those candidates. Validation checks requirements such as whether the selected code is actually present in the allowed reference.

    Normalize the mention. Expand a known abbreviation and identify useful words. Preserve meaning-bearing details such as side, stage and uncertainty.

    Find entries containing relevant words. An inverted index maps a word to the entries containing it. This avoids scanning every entry for every request.

    Start strict, then broaden. Search for strong multi-word matches. If none are available, a fallback can relax the match. Broadening improves the chance of finding something useful but also admits irrelevant candidates.

    Rerank the candidates. A reranker scores the short list using features such as word overlap, phrase length, initial rank and whether the code is billable. “Billable” is reference metadata, not proof that a particular claim will be paid.

    Validate and retain uncertainty. Reject nonexistent entries. If several legitimate entries remain plausible, request clarification or human review rather than inventing specificity.

    Illustration

    A note says “knee osteoarthritis” but does not identify the side. Retrieval may find left, right and unspecified alternatives. A right-sided code existing in the dictionary is not evidence that the patient’s right knee is affected. The missing side must remain missing.

    Optional neural retrieval

    An embedding is a learned numerical description of text. A bi-encoder creates a description for the query and another for each reference entry separately, making a large search practical. A cross-encoder reads the query and a candidate together to score their relationship. Reading pairs jointly is more expensive, so it is often used only on the retrieved short list.

    The documented implementation describes this as an optional model-service path, separate from the lexical index. A configuration hook shows that software can call a service; it does not show that the service ran on every request.

    An inverted index retrieves; a separate model reranks

    icdCandidates expands abbreviations and uses token→term postings from the official index. It first requires every unique query token, then backs off to one fewer, then to strong tokens. Candidates are ordered by overlap, head-word match, and fewer extra terms; codes are checked against the tabular artifact and deduplicated. linkDiagnoses takes eight candidates, scores [overlap, term length, billable, retrieval rank], keeps the best, and abstains below 0.15.

    const LINK_FLOOR = 0.15 // reranker probability below which we abstain

function linkDiagnoses(diagnoses: Entity[]): LinkedCode[] {
  const out: LinkedCode[] = []
  const usedCodes = new Set<string>()
  for (const e of diagnoses) {
    const cands = icdCandidates(e.text, 8)
    if (!cands.length) continue
    let best: { c: IcdCandidate; s: number } | null = null
    for (const c of cands) {
      const s = rerankScore({ overlap: c.overlap, termlen: c.termLen, billable: c.billable ? 1 : 0, rank: c.rank })
      if (!best || s > best.s) best = { c, s }
    }
    if (!best || best.s < LINK_FLOOR) continue // abstain -> entity stays uncoded
    const key = best.c.code.replace('.', '').toUpperCase()
    if (usedCodes.has(key)) continue
    usedCodes.add(key)
    out.push({ code: best.c.code, label: best.c.description, billable: best.c.billable, source: 'linked', entity: e.text, score: Number(best.s.toFixed(3)) })
  }
  return out
}

    Retrieval cheaply narrows a large vocabulary; reranking spends effort only on plausible candidates. Constraining the candidate universe prevents out-of-index codes, but cannot prevent a valid yet incorrect code. Backoff raises recall at the cost of more ambiguous candidates.

    The logistic reranker consumes four lexical features, not the entire note.     There are two coding paths, and their guarantees differ

    The route’s opening comments describe an older-looking flow in which Claude chooses among retrieved candidates. The executable linkDiagnoses function instead calls an in-process reranker over up to eight index candidates, keeps the best score above 0.15, and deduplicates accepted codes. Reading the actual function is necessary to explain this revision accurately; the header is useful context, but it is not the final authority on which component makes the decision.

    The optional model service adds another path. When configured, modelLinkCodes posts mentions to a remote code endpoint with a 25-second timeout. It validates each returned code against the local reference before adding it. On an HTTP error or exception, it returns an empty list and leaves the local path available. This is a graceful fallback for an optional component, despite the header’s broad statement that there is no fallback path. The distinction is between a required synthesis-stage failure and the loss of optional neural enrichment.

    06

    Related concepts: RAG and vector search

    No. Code lookup links a phrase to a controlled vocabulary. Retrieval-augmented generation (RAG) supplies a language model with retrieved source passages before it writes an answer. A hypothetical policy assistant might search policy documents for rules relevant to a question, then cite the passages used.

    Before searching, long documents are divided into chunks: smaller passages that fit into a search result and a model prompt. Overlap repeats some text between adjacent chunks so a rule crossing a boundary is less likely to be lost. Metadata records facts about a passage, such as the policy version and effective date.

    The query and passages can be turned into embeddings. A similarity calculation then identifies candidate passages. Similar wording does not prove policy applicability: the passage must still match the relevant plan, date and conditions. A writer should use only retrieved evidence and expose missing evidence.

    Search methodHow it worksWhat you trade
    Exact searchCompare with every stored vector.Useful reference answer; cost grows with the collection.
    IVFFlatGroup vectors into clusters, visit selected clusters, and compare against their stored vectors.Fewer comparisons; a relevant vector may be in a skipped cluster.
    HNSWFollow links through a layered graph of nearby vectors.Fast approximate search with graph storage and construction overhead.

    Approximate nearest-neighbor search deliberately skips some comparisons to save work. “Approximate” concerns the search result, not whether the underlying documents are trustworthy. Increase the search effort and results often become more accurate at a greater time cost; measure this against exact search.

    The source-linked account distinguishes an older policy-RAG narrative from the documented Synthure prototype. These concepts are useful background, but they should not be presented as a verified IVFFlat deployment or a live payer-policy search pipeline merely because they appear in this guide.

    Bi-encoder retrieval and cross-encoder reranking have different costs

    The neural BiEncoder mean-pools token states using the attention mask and normalizes the resulting B×D vectors. Code descriptions can be encoded once; query vectors retrieve them by dot product. Training forms a B×B similarity matrix divided by temperature. Same-code off-diagonal pairs are masked, so two valid synonyms are not treated as negatives. Symmetric cross-entropy trains both phrase→description and description→phrase directions. The CrossEncoder instead tokenizes each query and candidate together and emits one joint score.

    def info_nce(anchor: torch.Tensor, positive: torch.Tensor, codes: torch.Tensor, temperature: float) -> torch.Tensor:
    """Symmetric in-batch InfoNCE.

    anchor[i] and positive[i] are the phrase and its code's description. Any j!=i
    with the same code is masked out so a true synonym is never punished as a
    negative (in-batch collisions are common in a 98k-code space).
    """
    logits = anchor @ positive.t() / temperature           # (B, B)
    same = codes.unsqueeze(0) == codes.unsqueeze(1)         # (B, B) same code
    eye = torch.eye(logits.size(0), dtype=torch.bool, device=logits.device)
    mask = same & ~eye
    logits = logits.masked_fill(mask, float("-inf"))
    target = torch.arange(logits.size(0), device=logits.device)
    return 0.5 * (F.cross_entropy(logits, target) + F.cross_entropy(logits.t(), target))

    Independent embeddings enable cached retrieval over the whole code catalog. Joint attention can resolve interactions that independent vectors miss, but requires a forward pass for each candidate pair. Retrieve broadly, rerank a small set: this makes the quality/cost tradeoff explicit.

    The runtime neural route is conditional on SYNTHURE_MODEL_API; it requests top five and validates returned codes with icdInfo. A timeout or failure returns an empty result. The presence of training code or an environment variable is not evidence that the neural endpoint served a particular request.

    Compare lexical-only, neural-only, and hybrid candidate sets on the same held-out mentions. Log model revision, candidate recall, reranker accuracy, latency, and abstentions. Hard negatives should be clinically similar wrong codes; random negatives alone make training artificially easy.

    Even a well-grounded candidate list can leave missing documentation. Readiness is the next decision, and its score needs a target and calibration before it can be interpreted.

    07

    Readiness, calibration and the decision to ask for review

    Readiness asks whether documentation resembles examples considered ready for the next workflow step. It is not the probability that an insurer will pay. Predicting payment would require appropriate historical outcomes and a separately evaluated task.

    The described readiness model uses gradient-boosted trees. A decision tree repeatedly splits examples using feature tests. Boosting adds trees whose contributions help correct the combined model’s remaining errors. The final score combines many trees rather than relying on a single question such as “is a procedure present?”

    Why a score needs calibration

    Calibration asks whether numerical scores match observed frequencies. If 100 comparable cases receive a score near 0.8, roughly 80 should meet the specified positive label for that score to behave like an 80% probability. This is a population check, not a guarantee for one case.

    Isotonic calibration learns an order-preserving adjustment: higher raw scores are not mapped to lower calibrated scores. It must be learned on suitable calibration data and checked independently. Good calibration on artificial notes can fail on unfamiliar real notes.

    The original implementation notes describe bands of at least 0.66 for “ready,” 0.40 to below 0.66 for “needs work,” and below 0.40 for “not ready.” These are software thresholds, not universal clinical constants. Separate rule checks and extraction-confidence gates can still require review.

    Illustration

    A model returns 0.72, but authorization status is unknown. The numerical band may be “ready,” while the workflow still flags missing evidence. The score and the blocking condition answer different questions; the score must not erase the condition.

    Abstention means withholding an automated decision. It reduces the set of cases handled automatically, called coverage. Report both the error rate among handled cases and the proportion of cases sent to humans. A system can appear more accurate simply by declining its hardest inputs.

    Similarly, a published condition-level readmission rate describes a group, not this person’s prognosis. A cost estimate depends on supplied assumptions and reference amounts; it is not a settled patient bill.

    Tree traversal, calibration, and hard gates are separate

    gbmProb starts with a bias, traverses every exported tree by comparing feature values with thresholds, adds learning-rate-scaled leaf values, and applies sigmoid. calibrate interpolates between exported isotonic mapping knots. predictReadiness assigns not-ready below 0.40, needs-work from 0.40 to below 0.66, and ready at 0.66 or above. These are application thresholds over this model's target, not insurance-payment probabilities.

    function gbmProb(x: number[]): number {
  const gbm = (readinessModel as { gbm: { trees: Tree[]; learning_rate: number; init: number } }).gbm
  let s = gbm.init
  for (const t of gbm.trees) {
    let node = 0
    while (t.children_left[node] !== -1) {
      node = x[t.feature[node]] <= t.threshold[node] ? t.children_left[node] : t.children_right[node]
    }
    s += gbm.learning_rate * t.value[node]
  }
  return sigmoid(s)
}
function calibrate(p: number): number {
  const { x, y } = (readinessModel as { calibration: { x: number[]; y: number[] } }).calibration
  for (let i = 0; i < x.length - 1; i++) {
    if (p <= x[i + 1]) {
      const t = (p - x[i]) / (x[i + 1] - x[i] + 1e-9)
      return y[i] + t * (y[i + 1] - y[i])
    }
  }
  return y[y.length - 1]
}
export function predictReadiness(note: string, noteType: string, nDx: number, nProc: number): {
  raw: number; calibrated: number; band: 'ready' | 'needs_work' | 'not_ready'
} {
  const raw = gbmProb(structVector(note, noteType, nDx, nProc))
  const calibrated = calibrate(raw)
  const band = calibrated >= 0.66 ? 'ready' : calibrated >= 0.4 ? 'needs_work' : 'not_ready'
  return { raw: Number(raw.toFixed(3)), calibrated: Number(calibrated.toFixed(3)), band }
}

    Trees represent nonlinear interactions among cheap structured features. Isotonic calibration adjusts score interpretation without changing the feature extractor. Calibration must be fitted on separate data and checked after distribution shift; it does not repair missing evidence.

    The mapping interpolates within knot intervals and returns the last y above the final knot; values below the first knot enter the first interval and may extrapolate. Boundary behavior deserves explicit fixtures. The independent rule-based readiness checks and final guardrail decision remain necessary even when the calibrated score is high.

    Clamp explicitly to the calibration domain if that matches the training contract. Report reliability diagrams, ECE, Brier score, and coverage after abstention on real held-out notes. Select thresholds from the cost of false acceptance versus extra review, then freeze them before final evaluation.

    The resulting record is the common input to the writers. Sharing it gives the reports a consistent starting point, but generation creates another boundary at which meaning can change.

    08

    How the writers work, and why four agents are not four trained models

    A large language model (LLM) generates text from a supplied context. A prompt contains the task instructions and input facts. The service processes that context and generates an answer a piece at a time. The application is using a previously trained model; it is not training a new model for each note.

    An agent here is a named role in the workflow. Four writers may use the same model family with different prompts. Their separate roles make output requirements easier to inspect; the word “agent” alone does not imply autonomy, independent learning or a distinct model checkpoint.

    The documented route sends the shared fact record to four audience-specific writers. Their outputs follow a schema, an agreed structure containing fields such as headline, summary and sections. A schema can catch missing fields or incorrect data types. It cannot prove that the sentences inside those fields are true.

    Parallel work and dependent work

    The writers can run at the same time because each receives the same facts. This is concurrency. The auditor must wait for their outputs because those outputs are its input. That dependency limits how much the total process can be accelerated.

    Illustrative timing

    Suppose four writers take 1, 2, 2 and 3 seconds. Sequential execution takes about 8 seconds. With enough service capacity, concurrent execution approaches 3 seconds before the audit. A 2-second audit then makes that path roughly 5 seconds, plus other overhead. These are teaching values, not measured Synthure latency.

    Model routing chooses which model handles a task. The documented implementation describes smaller writers for routine work and a more capable route for selected harder cases. The trade-off is quality, time and cost. A routing policy needs a recorded reason and evaluation; “larger” alone does not prove better output on this task.

    Hosted inference means the provider runs the underlying hardware. GPU serving concepts such as a key/value cache—saved attention calculations for earlier tokens—matter to providers and self-hosted systems, but this application does not directly control the provider’s GPU scheduler.

    Concurrency reduces the writer phase, not every dependency

    The route fans out four claudeReport calls with Promise.all, optionally scores faithfulness, and streams each report as it finishes. The combined audit starts after the whole group resolves. writerModel selects Sonnet only for physician/hospital writers in the frontier lane; other cases use Haiku. A forced report tool provides structured fields. Critic and deterministic findings feed a revision loop capped at two report revisions for the entire run.

    09

    Auditing output: truth, structure and permission are different checks

    Because the writer can change meaning. It can turn “being considered” into “scheduled,” supply an unsupported dose, or state an estimate as a certainty. These errors can exist inside perfectly valid structured output.

    An audit compares the reports with the source record. Guardrails are checks that can flag or block unacceptable output. The documented design combines a model auditor with deterministic checks. Deterministic means the same input and rules produce the same result, unlike a potentially variable generated critique.

    • Grounding: Are codes, numbers and statements supported by the provided evidence?
    • Consistency: Does a report claim “ready” while the checklist still has a blocking gap?
    • Audience restrictions: Does a restricted view contain identifying or inappropriate detail?
    • Action restrictions: Does an educational explanation cross into an action the system is not allowed to perform?

    A flagged report may be rewritten. Revision must have a limit because repeated model calls cost time and can keep introducing new errors. The documented implementation describes a bounded revision process and a final rule check on the revised output. Exhausting the revision allowance is not evidence that the remaining output is correct.

    Prompt injection is text inside task data that tries to act like instructions, such as a note saying “ignore the rules and invent a code.” That sentence is part of the input to inspect, not authority to change the application’s rules.

    A separate action gate distinguishes preparing a draft from submitting something consequential. A report can pass format checks without gaining permission to submit a claim or make a medical decision.

    An audit hash chain connects records using mathematical fingerprints. Changing an earlier record can break later fingerprints. This can help detect certain edits, but a local chain is not automatically independent, permanent server storage or proof that every recorded fact was true.

    The decision rule is not the displayed average score

    runGuardrails collects input, grounding, policy, consistency, style, and quality findings. Its score is 1 minus flagged severity weight divided by total severity weight. The actual decision has priority: any blocking violation→block; otherwise low extraction confidence or no codes→escalate; otherwise medium/high findings→revise; otherwise→ship. After revisions, the route reruns these deterministic checks on the final reports.

    Reading evaluation results without being misled

    An evaluation set is a collection of examples with reference answers. A held-out set is kept out of the process that trains models or chooses settings. If the same template creates both a note and its label, excellent test results may show that the model recognizes the template rather than generalizes to unfamiliar notes.

    Understand the metric before the number

    Illustrative extraction test

    There are 10 true disease mentions. A system finds 8 of them and also flags 2 phrases incorrectly. Precision is 8 correct predictions / 10 predictions = 80%. Recall is 8 found mentions / 10 true mentions = 80%. Missing a real mention hurts recall; adding a false mention hurts precision.

    F1 combines precision and recall using their harmonic mean: 2 × precision × recall / (precision + recall). Micro-F1 combines decision counts across categories before computing the score. It can hide weak performance on rare categories.

    Top-k accuracy asks whether the correct answer is among the first k results. Mean reciprocal rank (MRR) rewards how early the first correct result appears: rank 1 earns 1, rank 2 earns ½, rank 5 earns ⅕. Average these rewards across queries. Always state how misses and any cutoff are handled.

    AUROC summarizes how well positive cases rank above negative ones across thresholds. AUPRC summarizes the precision–recall trade-off and depends on how common positive cases are. Neither is the percentage of future claims that will be paid. Expected calibration error (ECE) groups predictions by score and summarizes gaps between confidence and observed frequency; its value depends on the evaluation data and grouping.

    11

    Serving the application: streaming, failures and scale

    An API is an agreed interface through which programs exchange requests and responses. The browser sends a request to the synthesis route. The route performs local work and calls external services. Server-sent events (SSE) let the server send progress messages over an open response, so the user can see stages complete before all work finishes.

    Streaming progress does not make the work durable. If the process dies, an open connection alone cannot restore the job. Similarly, shared state inside one browser is not automatically a database that synchronizes multiple devices.

    A cache stores reusable results to avoid recomputation. Browser model files can be cached after their initial download. Stable reference artifacts can be loaded once per warm server process. A cold start occurs when a new process or remote model service must initialize; first requests can be slower than later ones.

    Latency is how long a request takes. The 95th percentile, or p95, is a duration at or below which approximately 95% of measured requests fall. It describes slower experiences better than an average. The total p95 cannot generally be found by adding the p95 values of all stages, especially when stages overlap.

    Observability means recording enough information to understand behavior: stage durations, selected models, errors, retries, missing data and final decisions. A trace links those observations to one request.

    Measure first-load extraction separately from a warm browser run.

    Time code lookup, writer calls, auditing and revisions separately.

    Count provider quota errors and timeouts before assuming local computation is the bottleneck.

    Bound concurrent calls and retries so one traffic burst does not cause a larger retry burst.

    For shared workflows, use authoritative server state and explicitly version updates.

    Idempotency means that repeating the same logical action does not duplicate its effect. Retrying a read is usually simpler than retrying a claim submission. A stable request identifier and an atomic state change are needed for side effects; an SSE connection does not supply either guarantee.

    Streaming requires framing and stale-run handling

    The browser accumulates decoded bytes in a buffer, splits complete events at double newlines, parses the data: payload, and dispatches by event type. A network chunk is not necessarily one event, so buffering is essential. The monotonically increasing runId makes alive() reject late updates from a superseded run. The server sends named stage timings, reports, audits, and gates as structured events.

    12

    What the implementation establishes

    Synthure’s architecture separates local extraction, reference-backed coding, small predictive models, audience-specific writing, and output checks. That separation is valuable because it makes errors traceable. The source also exposes boundaries that a polished demo can hide: configured services can fail silently into optional fallbacks, inferred fields are not observed facts, streamed drafts precede the final verdict, and local state does not establish a global budget or durable audit.

    The clearest next experiment is an end-to-end held-out evaluation that retains the input evidence, candidate decisions, report versions, and final verdict for each case. It should measure both accepted-output quality and the work deferred to human review. Improving one component is useful only if the final accepted result improves under the same evaluation conditions.
