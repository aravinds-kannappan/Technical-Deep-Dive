    Replays AI: from a game record to a story worth watching

    A sports recap is a small data pipeline with an editorial problem inside it: decide what matters, preserve the facts, and deliver the result before the fan loses interest.

    Two-page cheatsheet · All three cheatsheets

    The story begins before the writer

    A 104–101 score tells us who won. It leaves out the lead changes, the late possession, and the reason the final minute was worth watching. Replays AI tries to close that gap by turning sports records into recaps, broadcasts, reels, and personalized newsletters.

    The obvious starting point is a language model: supply the game data and ask for a story. But suppose the prompt contains an early dunk and omits the final defensive stop. Even an excellent writer has received the wrong evidence for explaining the finish. The first editorial decision happened in the selector, before generation began.

    That observation explains much of the architecture. Provider data becomes normalized records; rules analyze and select events; writers or templates turn those facts into language; caches, playback code, and persistent state determine the experience the fan receives.

    We will follow an invented Owls–Foxes game through these stages, then examine personalization, LoRA training, and the state transitions behind fan predictions. The goal is to understand both the models and the surrounding software that determines when their outputs are useful.

    A shared game record supports several products

    Replays uses a React frontend and a FastAPI backend. The backend reads ESPN data on demand and converts it into consistent fields. Redis, when configured, supports shared storage for artifacts and fan state. The live request path should be distinguished from historical ingestion or PostgreSQL code elsewhere in the repository.

    Fan chooses teams and players
  → browser requests a feed or game
  → backend obtains ESPN data
  → adapter converts it into consistent fields
  → rules select and analyze important events
  → writer or template produces a story
  → interface displays facts, media and source labels

    The products diverge after this common beginning. A recap needs a coherent account of one game. A newsletter first chooses which games belong in a fan’s feed. A reel needs available video and narration that fits its scenes. A broadcast needs structured turns that a player can schedule.

    Keeping these responsibilities separate makes failures easier to diagnose. A wrong score in several products suggests an adapter or source issue. A correct score attached to an irrelevant newsletter suggests selection or ranking. Correct narration over the wrong clip suggests media alignment.

    Sharing facts also creates dependencies. A corrected game record can invalidate several generated artifacts. A preference change affects personalized selection without changing the game itself. A missing clip breaks one presentation while leaving a text recap usable. Each artifact therefore needs an identity and freshness policy appropriate to what it depends on.

    Fallbacks make the design practical. Known scores can still become deterministic prose when generation fails. Newsletter and broadcast routes can attempt a configured trained writer, a general model, and then a template. The successful route needs to remain visible: a training script in the repository does not establish that a particular response used its saved adapter.

    One request, from cache miss to recap

    Suppose the Harbor Owls beat the Valley Foxes 104–101. A fan opens the game, and the browser requests its recap. The backend checks a process-local memo and a shared cache. Assume both miss, so the request continues to the provider.

    {
  "game_id": "illustrative-game",
  "status": "final",
  "home_team": "Harbor Owls",
  "away_team": "Valley Foxes",
  "home_score": 104,
  "away_score": 101
}

    This simplified record is enough to describe the result, but not the game’s turning points. The backend also obtains a summary, extracts plays and leaders, selects a smaller set of events, and packages a fact sheet for the writer.

    Different claims need different evidence. “The Owls won 104–101” requires a final result. “They won in overtime” also requires period information. “A final stop secured the win” requires an event sequence supporting that interpretation. The presence of a score does not supply the missing relations.

    If generation fails, a template can return known facts. The response records which route supplied the text. Displaying that fallback and caching it are separate decisions: a useful response now is not necessarily the artifact we want to reuse for the next six hours.

    This request trace gives three possible explanations for an omitted final stop. The source may not have supplied it; the selector may have discarded it; or a cache may have returned a story from an earlier snapshot. These look similar in the UI but require different fixes. Preserving source identity, selected event IDs, and generation route would make the distinction observable.

    Normalize the provider without erasing uncertainty

    Provider responses are nested around their own concepts: competitions, competitors, team records, and status objects. Repeating that parsing in every feature would spread the same assumptions across the application. _event_to_game centralizes the conversion.

    The adapter rejects records without a competition, home and away participants, or an event ID. Accepted records expose consistent identifiers, teams, sport, date, status, and nullable scores. The score helper preserves missing or invalid values as None.

    That choice is small but consequential. Zero is a valid observed score. An unknown score is missing evidence. An empty result says a query completed without matches. A timeout says the system did not obtain a result at all. Collapsing those states can turn an operational problem into an incorrect sports claim.

    The source-fetch helper caches URL-plus-query responses locally, uses a twelve-second timeout, and raises on HTTP failure. This bounds a particular attempt; it does not establish that the upstream data is complete or final. A freshly fetched response can still contain delayed or corrected facts.

    A useful adapter test set includes missing participants, invalid IDs, postponed games, live scores, final ties where the sport permits them, and corrections after publication.     Caching is a decision about which result remains valid

    After one fan has paid the latency and compute cost of generation, the next fan should usually reuse the recap. The route checks an in-process memo and then Redis using recap:v2:{game_id}:

    played = game.get("away_score") is not None and game.get("home_score") is not None

    # configured — a transient provider error would pin the lesser recap.
    if played and game.get("status") != "live" and (result["generated_by"] == "llm" or not llm_configured):

    The write policy requires both scores, a status other than live, and either successful LLM generation or no configured LLM. A temporary model failure can therefore return a template without pinning it as the preferred recap. This favors recovery on a later request, although a prolonged outage can trigger repeated attempts.

    The local memo lasts six hours. Its size guard clears the dictionary when exceeded; this is not an LRU policy. Redis shares completed results across processes, while the local memo belongs to one process.

    Two misses can still mean two generations

    A lock around dictionary access prevents conflicting dictionary operations. It does not cover the interval between a miss and the completed generation. If two fans arrive together, both can miss and both can call the writer.

    Holding one global lock through generation would block unrelated games. A better proposed design is per-key single-flight: one task owns generation for a game while equivalent callers await it. Across processes, that ownership requires a shared lease or job mechanism, including timeout and failure handling.

    A game ID does not identify a fact snapshot

    Suppose the provider corrects the score after the recap is cached. The key still names the same game and output format. A TTL limits reuse duration but does not prove freshness.

    A fact fingerprint plus prompt and model revisions would identify the inputs behind an artifact. The system would still need polling or another invalidation signal to discover corrections. Artifact identity answers “what produced this?”; refresh policy answers “when should we look again?” Both are needed.

    Personalized outputs add preferences to that identity. Shared game facts can be cached broadly, while a newsletter may depend on a particular fan’s selected teams, candidate set, and ranking version.

    What the play-analysis agents actually compute

    The play-analysis modules consume structured events and textual cues such as “dunk,” “3pt,” “sack,” and “touchdown.” They do not inspect video. Scout, Stat, Ref, and Predict are deterministic modules behind an analyze(ctx) → AgentRead interface.

    PlayContext includes the description, period, clock, current and previous scores, and optional field position. The interface is useful because a learned implementation could later replace a rule. The current rules should still be evaluated according to the fields they actually receive.

# ── Transparent statistical proxies (heuristics, not learned) ───────────────────
def fg_make_probability(distance: Optional[int]) -> float:
    """Logistic approximation of NFL field-goal make rate by distance. Heuristic
    eyeballed to public make-rate curves (~99% at 20y, ~80% at 45y, ~50% at 53y)."""
    if not distance:
        return 0.0
    return 1.0 / (1.0 + math.exp((distance - 53.5) / 6.5))


def seconds_remaining(period: int, clock: Optional[str], sport: str) -> int:
    quarter = 15 * 60 if sport.upper() == "NFL" else 12 * 60
    in_quarter = 0
    if clock and ":" in clock:
        try:
            mm, ss = (int(x) for x in clock.split(":")[:2])
            in_quarter = mm * 60 + ss
        except ValueError:
            in_quarter = 0
    return max(0, (4 - min(period, 4)) * quarter + in_quarter)


def win_probability(margin: int, secs_left: int, sport: str) -> float:
    """Time-decayed logistic on score margin — a WP *proxy*, not a trained model.
    Margin matters more as time runs out."""
    total = (4 * 15 * 60) if sport.upper() == "NFL" else (4 * 12 * 60)
    frac_left = max(0.02, secs_left / total)
    scale = 7.0 * math.sqrt(frac_left)
    return 1.0 / (1.0 + math.exp(-margin / max(0.5, scale)))


_POINTS = {"touchdown": 7, "field_goal": 3, "safety": 2}

    The field-goal proxy is a sigmoid with midpoint 53.5 yards and scale 6.5. It gives 0.5 at the midpoint, approximately 0.787 at 45 yards, and 0.994 at 20 yards. These values follow from hand-set constants; they are not measured calibration results.

    Multiplying 0.787 by three gives about 2.36 expected kick points under this simplified proxy. It omits possession after a miss, return outcomes, penalties, and alternative plays. That calculation is not a complete strategic value estimate.

    The win proxy increases the effect of a score margin as remaining regulation time shrinks. A three-point lead at scale seven produces about 0.606; near the time floor it produces about 0.954. Possession, timeouts, and team strength are absent, and overtime has no separately fitted model. A number between zero and one is not automatically an empirical probability.

    Defaults also affect meaning. Missing kick distance returns 0.0, conflating unknown with impossible. Malformed clocks can become zero seconds within the quarter. Stat rules can substitute two or three points when the observed delta is zero. Scout language can assert tactical causes that an event description does not reveal.

    These are good candidates for small, explicit fixtures: a missed shot, an absent distance, an overtime period, and an event with no visible tactical evidence. Representing unknown values and limiting prose to supported observations would improve fidelity before introducing any new model.

    Selecting events is a form of information compression

    A game may contain hundreds of plays, while a useful recap has room for a handful. Selection compresses the source into the evidence the writer will see. This saves context and reduces distraction, but any omitted fact becomes unavailable to the downstream writer.

    The implementation assigns weights to recognizable highlights: touchdown 10, dunk 9, three-pointer 8, with penalties for misses. It also adds late plays to preserve the finish:

    api/recaps.py · lines 180–189 · source revision a867fdab · selected excerpt

    def _key_plays(plays: list[dict], limit: int = 16) -> list[dict]:
    interesting = [play for play in plays if play.get("play_type") not in (None, "other")]
    if not interesting:
        interesting = [play for play in plays if play.get("description")]
    if len(interesting) <= limit:
        return interesting
    late = interesting[-max(4, limit // 3):]
    best = sorted(interesting, key=lambda play: (-_play_weight(play), play.get("id") or 0))[:limit]
    selected = {id(play): play for play in best + late}
    return sorted(selected.values(), key=lambda play: play.get("id") or 0)[:limit]

    There is a revealing edge case. With limit 16, the late set contains five plays. Suppose the sixteen highest-weight plays are earlier and do not overlap those five. The union contains 21 entries. If IDs follow time, sorting by ID and taking the first sixteen discards every late play the union added.

    This is a counterexample implied by the code, not a measured production frequency. It illustrates why selection must be evaluated after every transformation. An intermediate set can satisfy an intended property that the final truncation removes.

    A proposed repair separates membership from presentation order. Reserve slots for required late events, deduplicate by stable provider ID, fill remaining slots by relevance, and only then sort the selected set by period and clock. The resulting invariant is testable: required events survive and the set never exceeds its budget.

    The current code deduplicates by Python object identity, so separately parsed dictionaries representing the same event can survive. It also assumes ID order is chronological. Stable identity and event time express different concepts and deserve different fields.

    The selected plays join teams, scores, period totals, lead changes, and leaders in _game_facts. General recap generation tries configured Anthropic models, then OpenAI, then deterministic prose. generated_by identifies the successful route. The cv_classifications count in this path counts selected plays; it does not establish visual recognition.

    For the Owls, retaining a late three-pointer supports a score-change claim. Calling it the decisive shot also requires what happened afterward. Evidence selection and sentence-level support are related evaluations, but one cannot replace the other.

    A broadcast is text with a timing contract

    Turning a recap into a reel adds constraints that prose alone does not have. Replays uses existing video URLs, scene metadata, overlays, and narration; it does not generate the original footage. Speech synthesis converts text to audio, while speech recognition serves a separate input role.

    The two-host broadcast format assigns each turn a speaker, text, scene type, and duration hint. Requested two-, five-, and ten-minute tiers target 12, 26, and 44 turns, with token budgets of 2,400, 5,200, and 8,000 respectively.

    Illustrative turn:
{
  "host": "play",
  "text": "The Owls finish with a 104–101 win.",
  "scene_type": "title",
  "duration_hint": 8
}

    A turn count is a planning target, not a measured duration. At 150 words per minute, a 45-word turn takes approximately eighteen seconds. An eight-second scene needs shorter speech, longer visuals, or a different cut.

    The parser first attempts an array parse, then salvages flat JSON objects when generation is truncated. Cleanup normalizes enums, truncates text to 400 characters, and clamps duration hints to 4–20 seconds:

    A schema-constrained response with explicit validation would reduce structural failures. Evidence IDs could associate each turn with an event and clip. Tactical commentary should be allowed to say that a cause was not observed; an analyst role does not add evidence to the fact sheet.

    Playback should be evaluated separately from text. The sum of duration hints can differ from actual synthesized speech. Accurate narration can also be paired with the wrong clip. Real audio completion, source alignment, factual support, and structural validity are four distinct checks.

    Choose the newsletter before writing it

    A recap asks what happened in one game. A newsletter first asks which games matter to this fan. Replays makes that decision with a separate relevance scorer, so changing the writer does not silently change the ranking policy.

    s(x) = σ(b + wTx)
    x = [followed team, followed player, recency, magnitude, upcoming]
    recency = exp(−max(age in days, 0)/7)

    api/curation.py · lines 60–82 · source revision a867fdab · selected excerpt

    def _features(item: dict) -> dict:
    recency_days = float(item.get("recency_days", 3.0))
    return {
        "followed_team": 1.0 if item.get("followed_team") else 0.0,
        "followed_player": 1.0 if item.get("followed_player") else 0.0,
        "recency": math.exp(-max(0.0, recency_days) / 7.0),  # 1.0 today, decays weekly
        "magnitude": min(1.0, max(0.0, float(item.get("magnitude", 0.0)))),
        "upcoming": 1.0 if item.get("upcoming") else 0.0,
    }


def score_item(item: dict) -> float:
    w = _weights()
    feats = _features(item)
    z = float(w.get("bias", 0.0)) + sum(w["weights"].get(k, 0.0) * v for k, v in feats.items())
    return 1.0 / (1.0 + math.exp(-z))


def rank_items(items: list[dict], limit: int | None = None) -> list[dict]:
    """Return items sorted by learned relevance, each annotated with `_score`."""
    scored = [{**it, "_score": round(score_item(it), 4)} for it in items]
    scored.sort(key=lambda it: it["_score"], reverse=True)
    return scored[:limit] if limit else scored

    The fallback weights are 2.2, 2.0, 1.3, 1.1, and 0.6, with bias −0.5. The loader can use an exported weight artifact, but the inspected source tree did not contain it. A version label and a loader establish support for learned weights, not evidence that a deployed instance used them.

    Consider a current followed-team item with magnitude 0.8, no followed player, and no upcoming flag. Under the fallback weights, its logit is −0.5 + 2.2 + 1.3 + 1.1×0.8 = 3.88, giving a score near 0.980. The high value reflects this hand-designed score scale; it is not a measured click probability.

    Sigmoid preserves ordering. If ranking is the only use, applying it does not change which logit wins. Rounding before sorting can change the order, however: rank_items rounds to four decimals and therefore creates avoidable ties. Sorting full-precision values and rounding for display would preserve more information.

    Recency has a seven-day time constant. At seven days the feature is about 0.368; its half-life is 7 ln 2≈4.85 days. Unknown age defaults to three days, future dates receive age zero, and magnitude is clipped to [0,1]. These are meaningful editorial choices even though they occupy only a few lines of code.

    Training a ranker would require a relevance signal and attention to exposure: users can click only what the existing system shows them. Synthetic labels generated from the same weights merely reproduce those assumptions. Useful comparisons include recency and popularity baselines on fixed candidates, with cold-start fans evaluated separately.

    Candidate coverage remains the first limit. No scorer can promote an Owls game that never entered the list, and no newsletter writer can recover that omission from polished prose.

    Adapting the writer with LoRA

    The offline writer pipeline begins with facts, generates teacher drafts, applies a grounding filter, and formats accepted pairs for supervised training. This is a form of distillation: the student learns from teacher-produced examples. Errors accepted by the filter become part of the target behavior.

    LoRA makes adaptation cheaper by freezing a base matrix and learning a low-rank update. For a weight matrix with output width dout and input width din:

    W′ = W + (α/r)BA
    A ∈ ℝr×d_in, B ∈ ℝd_out×r
    trainable parameters = r(din + dout)

    A 4,096-by-4,096 matrix has 16,777,216 entries. Rank 16 adapters have 131,072 parameters, approximately 0.78% as many. This compares trainable parameters for one matrix, not total GPU memory. The frozen base still has to be stored and used.

    The recipe uses rank 16, alpha 32, dropout 0.05, and attention plus MLP projections. The usual scale α/r is therefore two. Defaults include three epochs, learning rate 2e−4, microbatch one, sixteen accumulation steps, a 4,096-token sequence cap, bf16, and gradient checkpointing.

    These settings address different costs. On one device, accumulation gives a nominal sixteen examples per optimizer update without retaining all their activations simultaneously. It does not make a single overlong example fit. Checkpointing stores fewer intermediate activations and recomputes them during backpropagation.

    The optional QLoRA path stores frozen base weights in four-bit NF4 with double quantization and bf16 compute. Adapters still train. Activations, optimizer state, and workspaces do not all become four-bit, so memory estimates must include them separately.

    The split can matter more than the rank

    The script performs a random 95/5 record split with seed 7. Multiple drafts from the same game can therefore cross the boundary. A model familiar with the game facts may look better on validation without generalizing to unseen games. Grouping by game before generation and keeping a final time-disjoint test would provide a stronger comparison.

    The excerpt does not explicitly set an evaluation cadence, best-checkpoint policy, or assistant-only loss mask. Those depend on the installed training library and configuration and should be checked before making claims about the learning objective. Long fact sheets also need truncation inspection so the sequence cap does not remove the desired answer.

    Saving an adapter establishes an artifact. Serving additionally requires the matching base revision, tokenizer, chat format, and endpoint configuration. The meaningful comparison is template, base writer, and adapted writer on identical unseen facts, measuring factuality, coverage, structure, latency, and cost.

    One correct pick should produce one award

    Fan predictions introduce correctness that has little to do with language modeling. A resolved pick should update a profile and leaderboard once, even when requests race or a worker fails.

    The browser stores an anonymous UUID and sends it as X-Device-Id. That provides browser continuity rather than authentication. Redis hashes hold picks and profile counters, and a sorted set holds leaderboard points. Without REDIS_URL, storage operations are no-ops rather than durable success.

    The resolution function reads the pick, checks whether it is unresolved, writes a resolved marker, and then increments counters. Two requests can both read “unresolved” before either writes. Each increment is atomic, but the logical read–check–award operation is not.

    A crash produces the opposite failure. If the resolved marker is written before the points update, a retry sees the marker and returns without awarding. Moving the marker after the increment would create a duplication window instead. Reordering alone cannot provide the desired guarantee.

    A proposed fix is one atomic transition using a Redis script or an optimistic transaction with conflict retries. The transition must protect every affected counter, not just the marker. Another design records an idempotent award under a logical device-and-game key and derives counters with reconciliation.

    Corrected results require their own policy: reverse an earlier award, apply a versioned adjustment, or freeze an explicitly documented outcome. Authentication remains separate from atomicity; knowing an award happened once does not establish who owns a client-supplied identifier.

    Useful tests race two resolutions and inject failures at each write boundary. Responses should distinguish “already resolved,” “no award due,” and “store unavailable.” Returning zero for all three hides exactly the information recovery needs.

    A sentence can contain the right tokens and the wrong fact

    The teacher-data filter checks whether generated names and numbers occur in serialized facts. This is a useful inexpensive screen for some inventions. Its acceptance rule shows why it cannot be treated as a factuality guarantee:

    training/grounding.py · lines 41–62 · source revision a867fdab · selected excerpt

    def check(facts: dict, target: str) -> tuple[bool, list[str]]:
    blob = _blob(facts)
    ok_numbers = _facts_numbers(blob)
    ok_tokens = _facts_tokens(blob)
    reasons: list[str] = []

    for num in _NUM.findall(target):
        n = int(num)
        if n < 13:              # small counts, quarters, list markers: ignore
            continue
        if 1900 <= n <= 2099:   # a year, not a stat
            continue
        if num not in ok_numbers:
            reasons.append(f"invented number {num}")

    for first, last in _NAME.findall(target):
        # A person reference is grounded if the surname appears in the facts.
        if last.lower() not in ok_tokens and first.lower() not in ok_tokens:
            reasons.append(f"invented name {first} {last}")

    # Allow a tiny amount of noise (e.g. an idiom that reads like a name).
    return (len(reasons) <= 1, reasons)

    Numbers below 13 and values in the year range are ignored. A detected two-word name passes if either token is present. Up to one detected violation is accepted.

    Suppose Player A scored 30 points and Player B scored 12. “Player B scored 30” uses an available player and an available number while stating the wrong relationship. A fabricated twelve-point statistic can bypass the numeric threshold entirely. Token membership does not establish subject–statistic agreement.

    The filter therefore needs a labeled audit of false accepts and false rejects. Its acceptance rate alone measures neither. Errors that pass are especially consequential when their text becomes training supervision.

    Evaluate each transformation against its own target

    Selection needs key-event recall and precision. Writing needs supported-claim rate and important-fact coverage. Broadcasts need schema validity, factuality, clip alignment, and measured playback timing. State needs concurrent-resolution and crash-recovery checks.

    Ranking can use normalized discounted cumulative gain on a fixed set of judged candidates:

    DCG@K = Σi=1…K (2relevance_i − 1) / log2(i+1)
    NDCG@K = DCG@K / ideal DCG@K

    The denominator is the best ordering of those same candidates; a convention is needed when every relevance label is zero. NDCG rewards placing useful items early, but its interpretation depends on the labels and candidate pool. It does not directly measure user satisfaction.

    Writer comparisons should freeze source facts and selected events. Otherwise, an adapted writer given a more complete snapshot may appear better for a reason unrelated to adaptation. Include provider failures and template deliveries in product-level reporting, with quality broken down by route.

    The source material does not establish production factuality, trained-ranker uplift, cache-hit rate, or p95 latency. Those remain measurements to collect. The architecture identifies where to measure them; it does not supply absent results.

    Find the bottleneck before adding workers

    At the final buzzer, many fans can request the same uncached game. More API workers create more application capacity, but also more independent local caches and potential calls to the same sports and model providers.

    with _recap_lock:
        hit = _recap_cache.get(key)
        if hit and time.monotonic() - hit[0] < _RECAP_TTL_SECONDS:
            return hit[1]
    return None


def _memo_set(key: str, value: dict) -> None:
    with _recap_lock:
        if len(_recap_cache) > 128:
            _recap_cache.clear()
        _recap_cache[key] = (time.monotonic(), value)

    These locks protect memo operations, not in-flight generation. A warm recap hit bypasses both fetching and writing; a source-cache hit may still require generation. Reporting one blended “cache latency” would hide the distinction.

    The async endpoint directly calls a synchronous recap function. Blocking network or model work inside that call can occupy the event loop. An async declaration does not automatically make its callees yield. A suitable thread path or durable job path, selected according to the task lifecycle, would isolate that blocking work.

    Diagnostics also need request scope. A module-global last-error value can be overwritten by another request before a fallback reads it. The displayed reason could then belong to a different game. Returning errors with the attempt result avoids this shared mutable state.

    Capacity planning starts with arrival rate and service time. In an illustrative stable system, two uncached jobs per second with ten seconds of average time in the system imply about twenty concurrent jobs by Little’s law. If a dependency can complete only one job per second, that workload cannot remain stable without reducing admitted work, deduplicating, or changing the service path.

    Measure same-game bursts separately from many-game bursts. The former exposes duplicated work; the latter exposes aggregate upstream capacity. Trace queueing, source fetching, selection, each provider attempt, and storage. Sequential fallback means the fan’s latency includes failed attempts as well as the successful one.

    Bounded concurrency, shared deadlines, jittered retries, and per-key coalescing are proposed improvements with direct relevance to this design. Buying inference hardware would address a different bottleneck unless measurement first shows that hosted generation is what needs replacing.

    What makes the recap dependable

    The Owls’ 104–101 win passes through several judgments before it reaches a fan: which source record to trust, which events to retain, which writer to use, which cached artifact remains valid, and which scene can carry the narration.

    The most useful next steps strengthen those boundaries. Preserve source revisions, repair late-event retention, represent unknown inputs explicitly, validate broadcast turns against evidence, and make pick resolution atomic. Then compare writer adaptations on fixed, game-disjoint evidence.

    A better writer can make the story clearer. It cannot recover a discarded final stop, invalidate an obsolete cache entry, or repair a duplicated award. Replays becomes easier to improve when each of those responsibilities has its own observable contract and evaluation.
