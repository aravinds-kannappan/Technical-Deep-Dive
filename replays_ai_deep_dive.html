    Replays AI: from a game record to a story

    A sports story starts with changing facts. The interesting engineering happens between fetching those facts and presenting a recap, a broadcast, or a feed that a fan can trust.

    A fan sees one product, but Replays AI contains several systems with different failure modes. The data adapter has to preserve missing information. The selector has to keep the important play. The writer has to stay within the supplied evidence. The cache has to know when yesterday’s answer is no longer valid. We can understand the architecture by following one game through those decisions, including the places where the source comments describe an intention more strongly than the code guarantees it.

    Following the system through one example

    One value can change meaning at every boundary

    The score 104–101 is initially an observation supplied by an external provider. Normalization converts it into typed fields. Selection decides whether it belongs in a particular fact sheet. A writer turns it into a sentence. A cache preserves that sentence for later reuse. None of these transformations independently proves that the game is final; finality needs its own evidence.

    This distinction makes debugging concrete. If the UI shows the wrong winner, inspect the normalized scores before blaming the writer. If the scores are correct but the story omits the deciding play, inspect selection. If a corrected provider record still produces an old recap, inspect cache identity and invalidation. The architecture is easier to understand when every visible statement can be traced to one of these transformations.

    Throughout the article, the invented Owls–Foxes game is a running example. Code excerpts describe the pinned implementation; arithmetic examples explain the mechanism; proposed changes describe how the design could be strengthened. Keeping those categories separate prevents a plausible architecture explanation from turning into an unsupported claim about a production deployment.

    01

    The problem: useful sports stories from changing facts

    Raw sports data can contain scores, schedules, player statistics, hundreds of plays and links to clips. A fan usually wants a smaller answer: what happened, which moments mattered, and what is relevant to the teams they follow. Replays AI separates collecting facts, selecting relevant material and writing an explanation.

    An API is a defined way for programs to request information from another program. Replays reads sports data from ESPN endpoints. An endpoint is a particular address serving a particular kind of request, such as a game summary. These responses are structured data; they are not a language model’s recollection of a game.

    The frontend is the browser interface built with React. The backend is the Python application built with FastAPI that handles requests and organizes data. Redis is used when configured to store shared information and reusable results. Writing services turn selected facts into prose.

    Fan chooses teams and players
  → browser requests a feed or game
  → backend obtains ESPN data
  → adapter converts it into consistent fields
  → rules select and analyze important events
  → writer or template produces a story
  → interface displays facts, media and source labels

    The product has several outputs: a single-game recap, a narrated reel using real clips, a two-host broadcast, a personalized newsletter and prediction-game leaderboards. They share factual inputs but have different output requirements.

    The project README describes live ESPN access, optional Redis and conditional trained-writer paths. It explicitly says general models, templates and heuristic ranking are used until trained models are available and configured. A supported path is not proof that a trained checkpoint served a particular request.

    The product is a dependency graph over changing evidence

    A recap depends on a source snapshot and a selection policy. A personalized newsletter also depends on preferences. A narrated reel additionally depends on clip availability and speech timing. These outputs can share facts without sharing identical cache keys or validation rules. Treating all of them as “generate content” hides the inputs that determine whether an old result is still usable.

    For example, a correction to a final score should invalidate a recap that mentions the old score. A preference change should invalidate a personalized ranking even when the game facts are unchanged. A removed clip should invalidate a reel's media plan while leaving a text recap intact. Dependencies provide a principled way to identify affected artifacts instead of expiring everything on the same schedule.

    The source currently exposes several useful boundaries—provider adapter, play analysis, recap building, and shared storage—but a complete dependency manifest is a proposed extension. It could record source revision, selected event IDs, prompt version, model route, and preference version for each output. Such a manifest makes regeneration explainable and helps separate a content bug from stale reuse.

    The central design problem is therefore preserving meaning while reducing information. Thousands of provider fields become a small internal record; hundreds of plays become a few moments; those moments become a paragraph. Every reduction must retain the details required by the next stage. A writer can improve presentation only after that information has survived.

    Following one game makes the division of responsibility visible. At every step, ask whether the value was fetched, normalized, selected, inferred, or generated.

    A complete recap request, using one imaginary game

    Illustration — invented teams, score and events

    A fan follows the Harbor Owls. The Owls finish a game against the Valley Foxes, winning 104–101. The fan opens the game page and requests a recap.

    Identify the request. The browser sends the game identifier. A game ID is a stable reference to that event; the backend should not guess the game from a team name alone.

    Look for reusable work. If an eligible, sufficiently fresh recap is already saved, the backend can return it. If not, it obtains the source facts.

    Read the source response. The backend requests teams, scores, status, plays and available leaders. A missing score means unknown, not zero.

    Normalize the data. Regardless of how the supplier nested its fields, the application produces an internal record with named fields such as home team, away team, score and game status.

    Select important moments. Suppose the event list contains a late three-pointer and a final defensive stop. Rules can choose these events for the recap while keeping their original descriptions and order.

    Build the fact sheet. The writer receives the final score, selected plays and any available player lines. It must not infer a player’s statistics if those statistics are missing.

    Write or fall back. A configured language model may write the recap. If it is unavailable, a deterministic template can state the known result and selected events.

    Return the story and its source. The response indicates which path generated the text. An eligible final-game result may be cached for later requests.

    Replaying the request as a sequence of state changes

    At the start of the example, the only trusted identifier is the requested game ID. The server resolves that ID to provider data, normalizes the teams and scores, and constructs the fact sheet. Suppose the final defensive stop is missing from the provider's play list. The system can describe the verified score but should not manufacture a dramatic closing possession to complete the narrative.

    Now suppose the provider returns the stop but the selector drops it. The output omission has a different cause: ingestion succeeded, selection failed. Saving selected event IDs makes this visible. Without that record, a reviewer sees only a prompt and a fluent answer and may incorrectly conclude that the language model ignored an event it never received.

    A later score correction creates a third case. The original story may have been faithful to the snapshot used at generation time and still be wrong now. The response needs an evidence timestamp or revision so that “correct when generated” is distinguishable from “current.” A cache entry's creation time alone does not establish the source snapshot's age.

    A deterministic replay fixture would freeze the provider response and run the same normalization and selection again. Generation can then be evaluated separately with the frozen fact sheet. This division is valuable because live provider data can change between tests; otherwise an apparent regression may actually be a changed input rather than changed code.

    The first technical boundary is the provider response. Before ranking or writing can help, the adapter must make that response predictable without manufacturing missing facts.

    03

    Ingestion and normalization: making outside data usable

    Because external formats can vary by sport and endpoint, and they can change. A data adapter sits between the supplier and the rest of the application. It translates source-specific responses into a consistent internal shape. When a supplier changes a field, the repair can be concentrated in one place.

    Ingestion means bringing external data into the system. It does not always mean permanently inserting it into a database. In the documented Replays path, many reads happen on demand: a request triggers a fetch, normalization and a response, with caches reducing repeated work.

    A schema specifies expected fields and types. For example, a score might be a number or explicitly absent; a game status should be one of the supported states. Checking the schema prevents an unexpected string or missing nested object from silently flowing into later arithmetic.

    Duplicate event IDInvestigate or deduplicate according to a defined rule.Count the same scoring play twice.

    A timeout stops waiting after a defined period. An HTTP 429 response means the service is limiting request volume. A successful HTTP response still needs content checks: the response might lack a score or contain a changed format.

    The documented implementation describes a 12-second upstream timeout, a short process-local cache and typed helper functions in api/espn_public.py. These implementation details explain the intended behavior; they are not measurements of supplier reliability.

    Keep enough provenance to trace an error

    Provenance means where information came from. Preserve the game ID, play ID when available, source description, game clock, period and fetch time. If the final score is corrected later, provenance helps identify which derived recaps need refreshing.

    Unknown, zero, empty, and unavailable require different types

    A score of zero is a real measurement. A missing score is an absence of measurement. An empty schedule is a valid response containing no matching events. A timeout is a failure to obtain a response. Converting all four states into a convenient empty dictionary makes the application simpler temporarily but destroys information needed for truthful output and correct retries.

    A useful conceptual result type is either a valid normalized record or a structured failure reason. Within the record, nullable scores preserve absence. Outside it, a timeout or schema error remains an operational failure. This is a proposed contract rather than the exact current API schema. It lets the frontend say “data unavailable” instead of falsely presenting “no games.”

    Normalization also needs stable identity. Provider event IDs should remain attached to plays after sorting, filtering, and summarization. If two events have identical descriptions, text alone cannot establish that they are duplicates. Conversely, an updated event with the same ID may be a correction rather than a new play. A revision-aware ingest process can distinguish replacement from accumulation.

    The current adapter's integer conversion is another boundary worth testing. A string identifier that no longer parses as an integer can fail before a record reaches the writer. A provider-contract fixture should therefore exercise missing nested objects, unexpected types, duplicate IDs, and corrected records. These are interface tests; they do not require a language model and should fail close to the source of the problem.

    04

    Caching: faster responses without pretending old data is new

    A cache keeps a reusable answer so the system can avoid repeating an expensive fetch or generation. A cache hit means a suitable stored answer was found. A cache miss means fresh work is needed.

    A time to live (TTL) is how long an entry remains eligible for reuse. The documented source-data cache uses a short lifetime, while the original guide describes a six-hour local recap memo for eligible completed games. Different information needs different freshness policies: a live score can change within seconds; a finished game’s summary changes less often but can still require correction.

    Two storage locations, two guarantees

    A process-local cache exists inside one running backend process. It is quick to access, but another process cannot automatically see it. When that process stops, its memory disappears. A shared cache in Redis can be consulted by multiple processes, which helps them reuse the same work.

    Serverless hosting starts and reuses managed processes as demand changes. A warm process may have cached results; a new process may not. Therefore, one successful local cache hit does not establish consistent caching across every user request.

    Illustration

    One hundred fans request the same finished game. If all requests see an empty cache at once, all may try to fetch and generate. This is a cache stampede. A proposed “singleflight” mechanism lets one request do the work while the others wait for that same result.

    A cache key identifies the saved answer. It should include the inputs that determine the answer: game, sport, content version, and personalization when relevant. Saving a personalized Owls recap under a generic game-only key could give another fan the wrong perspective.

    The original recap description includes an important fallback rule: if an LLM is configured but temporarily fails, do not freeze its template fallback in a long-lived cache as though that were the preferred final output. A temporary outage should not unnecessarily affect hours of later requests.

    Stale-while-revalidate is a possible design in which a labeled older answer is returned while a background job refreshes it. It helps availability but requires an explicit freshness contract. It is an improvement option here, not proof of an implemented production feature.

    Why locking a dictionary does not deduplicate a computation

    Picture two requests arriving before any recap exists. Request A acquires the memo lock, sees a miss, and releases it. Request B then does the same. Both begin the slow network and model work outside the lock. The dictionary remains internally consistent, yet the expensive work is duplicated. A mutex around get and set protects storage operations, not the whole logical operation.

    Holding one global lock across generation would prevent the duplicate, but would also make unrelated games wait behind the same slow request. A per-key in-flight promise is more selective: requests for the same key wait for one computation, while different games proceed independently. Across multiple processes, that coordination requires shared ownership or a job service rather than a Python-only object.

    The cache key must describe the answer's dependencies. A conceptual key could include game ID, fact fingerprint, prompt revision, and output kind; a personalized output would also include a preference revision. This is a design proposal, not the current recap key. Hashing a stable serialization of facts can detect corrections, but only if irrelevant ordering and timestamps are handled deliberately.

    Expiry and identity solve different problems. A six-hour TTL limits how long an entry is reused; it cannot prove that the entry corresponds to the newest corrected facts. A content-derived key ties output to a particular snapshot but requires a way to discover the current snapshot. Combining provenance, invalidation, and bounded expiry produces a clearer freshness policy than merely making the TTL shorter.

    The current cache already treats degraded generation differently

    get_recap checks an in-process memo and then Redis under recap:v2:{game_id}. It fetches game and summary on a miss and builds a response with generated_by. Cache writes require both scores, status other than live, and either successful LLM output or no configured LLM. The local memo uses a six-hour TTL and clears when its size exceeds 128 entries.

    Walking through a miss, an outage, and a correction

    Suppose the illustrative 104–101 game is requested for the first time. The local memo misses, Redis misses, and the backend fetches the game and summary. If the writer succeeds and the game meets the cache condition, the response is stored. A second request can now avoid both upstream work and generation. On a different warm process, the local memo may still miss while Redis hits; without Redis, that process may generate again.

    Now suppose a writer is configured but temporarily fails. The code returns a data recap and intentionally declines to cache that degraded answer under the normal condition. A later request gets another chance to use the preferred writer. This is a quality-aware cache policy, but it increases repeated work during a sustained outage. A short-lived failure state or circuit breaker could reduce retry pressure while keeping the degradation visible. Such a state should be distinct from a long-lived successful recap.

    Finally, suppose the provider corrects the final score. The existing key contains the game ID and a format version, not a fingerprint of the source facts. The cache cannot detect the correction merely from that key. Adding a source revision or fact digest makes invalidation more precise, at the cost of obtaining or tracking that revision. Time-based expiry is simpler but accepts a window of staleness. The product should choose that window deliberately rather than equating a final game with immutable data.

    The memo’s small size guard clears the whole dictionary after it exceeds its limit; it is not a true least-recently-used policy. A clear can produce a burst of misses. The nearby “generated once per game per instance” comment describes the intended benefit, but locks around individual get and set operations do not coalesce the entire generation interval. Two simultaneous misses can both call the writer. A per-key in-flight future would address this within a process; shared leases or jobs would address it across processes.

    A cache can reuse a story, but it cannot decide which moments deserve to be in it. That starts with the play analysis and the information its rules actually receive.

    Play analysis: rules, features and the meaning of “agent”

    No. Classification means choosing a category. A programmer can write a rule that labels a description containing “interception” as an interception. A trained classifier learns decision settings from examples. Both classify; only the second requires learning.

    The documented implementation describes the play parser as text rules checking cues such as “3pt,” “dunk,” “sack” and “touchdown.” This is not the same as a computer-vision model reading video frames. It is also not proof that a historical vision-based system never existed; those are separate implementations requiring separate evidence.

    A feature is a usable value derived from input: score margin, time remaining, play type or whether a review was mentioned. A heuristic is a deliberately chosen rule of thumb. A heuristic can be sensible and useful without having been fitted to labeled examples.

    The Scout, Stat, Ref and Predict roles described in api/play_analysis.py are deterministic calculations. “Agent” names organize the outputs. They do not demonstrate four independently trained neural networks.

    Illustration

    A description contains “three-point shot,” and the home score rises from 101 to 104. A rule can assign a three-pointer category, calculate a three-point change and describe the score impact. It cannot conclude that the shot was unusually difficult unless that information is supplied or separately analyzed.

    A plausible probability is not a calibrated probability

    A heuristic can map lead and time remaining into a smooth number between 0 and 1. It may rise when a team leads late, which feels plausible. But calling 0.8 an 80% win probability requires testing whether similar historical cases actually win about 80% of the time.

    The source-linked account identifies the displayed win-probability calculation as a proxy. That label matters. A chosen formula is not automatically a trained predictive model, and an attractive visualization is not an evaluation.

    When would learning be justified?

    Collect real descriptions with human-assigned play labels, identify where rules fail, and compare alternatives on games excluded from training. If a simple word-based classifier reliably fixes enough costly errors, it may justify the extra training and maintenance. The decision should follow evidence rather than the desire to use a more elaborate model.

    Calculating the proxy reveals what its comments cannot guarantee

    The field-goal function uses p = 1 / (1 + exp((distance − 53.5)/6.5)). At 53.5 yards the exponent is zero, so the proxy returns 0.5. At 45 yards it returns about 0.787. At 20 yards it returns about 0.994. These are calculations from the inspected formula, not measured make rates. The constants define the midpoint and how quickly the curve falls; they were not fitted by a training loop in this module.

    Multiplying a three-point reward by this proxy gives an illustrative expected score for the attempt. At 45 yards, 3 × 0.787 is about 2.36. That quantity is not a complete possession-value model: it leaves out field position after a miss, blocked returns, penalties, game strategy, and other outcomes. A compact proxy is useful when its scope is visible, but calling it expected points without that scope can imply more than the formula models.

    The win-probability proxy similarly turns margin into a sigmoid, with a scale that shrinks as time runs out. A three-point lead at the start gives about 0.606 under the seven-point scale. At one percent of regulation time remaining, the code's two-percent floor makes the scale about 0.990 and the proxy about 0.954. This encodes the intuition that a late lead matters more, but does not incorporate possession, team strength, timeouts, or a separately learned overtime model.

    The deterministic prose deserves the same scrutiny. Some templates describe a late defensive closeout or the absence of a whistle without observing video or a complete officiating record. Those sentences are generated by rules rather than hallucinated by a model, but can still assert unsupported specifics. Determinism makes a result repeatable; it does not make the inferred explanation true. A stronger output would separate observed facts from explicitly labeled generic context.

# ── Transparent statistical proxies (heuristics, not learned) ───────────────────
def fg_make_probability(distance: Optional[int]) -> float:
    """Logistic approximation of NFL field-goal make rate by distance. Heuristic
    eyeballed to public make-rate curves (~99% at 20y, ~80% at 45y, ~50% at 53y)."""
    if not distance:
        return 0.0
    return 1.0 / (1.0 + math.exp((distance - 53.5) / 6.5))


def seconds_remaining(period: int, clock: Optional[str], sport: str) -> int:
    quarter = 15 * 60 if sport.upper() == "NFL" else 12 * 60
    in_quarter = 0
    if clock and ":" in clock:
        try:
            mm, ss = (int(x) for x in clock.split(":")[:2])
            in_quarter = mm * 60 + ss
        except ValueError:
            in_quarter = 0
    return max(0, (4 - min(period, 4)) * quarter + in_quarter)


def win_probability(margin: int, secs_left: int, sport: str) -> float:
    """Time-decayed logistic on score margin — a WP *proxy*, not a trained model.
    Margin matters more as time runs out."""
    total = (4 * 15 * 60) if sport.upper() == "NFL" else (4 * 12 * 60)
    frac_left = max(0.02, secs_left / total)
    scale = 7.0 * math.sqrt(frac_left)
    return 1.0 / (1.0 + math.exp(-margin / max(0.5, scale)))

    06

    Selecting evidence and generating the recap

    A long game record contains repeated and low-value information. Sending all of it increases input length and may distract from the events a recap should explain. Selection creates a smaller evidence set. Ranking orders candidates by a score, whether that score comes from rules or a learned model.

    A key-play selector may favor scoring events, lead changes or late-game moments. After selection, chronological order helps the writer explain the sequence accurately. A high-scoring event is not necessarily the decisive event, so selection quality should be compared with human editorial judgments.

    A prompt gives the language model its instructions and facts. Inference is the act of running an already trained model. The model converts the prompt into tokens—pieces of text—processes them, then generates more tokens. No new sports knowledge is validated merely because the next sentence sounds natural.

    What belongs in the fact sheet?

    • Teams, game status and verified scores.
    • Relevant period information and selected source play descriptions.
    • Player statistics only when those values were actually obtained.
    • Explicitly missing fields, rather than guessed replacements.

    The documented recap path tries configured Anthropic models, may try OpenAI, and can fall back to a deterministic data-based recap. Newsletter and broadcast paths have an additional conditional trained-model route. These paths should not be collapsed into a claim that every output uses the same engine.

    A deterministic template inserts supplied values into a known structure. For the imaginary game, it could say “The Harbor Owls defeated the Valley Foxes 104–101.” The prose is limited, but it can still deliver useful known facts when a writer is unavailable.

    A response field such as generated_by or source records which path ran. These labels help diagnose behavior and compare quality. A fallback should be honestly labeled even when its output reads well.

    Remove a player’s points total from the input. If the generated recap still supplies a number, inspect whether it came from another valid source or was invented. Prompt instructions alone do not demonstrate factual reliability.

    Selection sets an upper bound on what the writer can know

    Suppose an evidence budget allows five plays. Choosing the five highest-scoring events and then restoring chronological order solves two different problems: relevance determines membership, while chronology determines presentation. Sorting first and taking the earliest five can miss the decisive late play. Adding a late event and then truncating the combined list can accidentally remove the very event the special case intended to preserve.

    A useful selection invariant would say that the final chosen lead-changing event must survive all later deduplication and size limits, if such an event is present and eligible. That invariant should be tested against the final list passed to the writer, not an intermediate candidate list. This is a proposed strengthening of the source behavior discussed below.

    The prompt then acts as a constrained communication interface. It should provide the selected facts with stable IDs and distinguish known values from missing ones. If a player line is absent, the writer can omit it or state the limitation; it should not infer a season average or a career milestone from the game score. Style instructions cannot replace this evidence boundary.

    A useful evaluation decomposes the output into assertions: winner, final score, named scorer, event timing, and causal interpretation. “The basket made it 104–101” is a different assertion from “the basket secured the win.” The latter depends on what happened afterward. Relation-level checks are necessary because every number and name can be individually present while their combination remains wrong.

    Selection can drop the decisive event before the writer sees it

    _key_plays keeps classified plays, scores categories (touchdown 10, dunk 9, three-pointer 8), penalizes descriptions containing “miss,” combines highest-weight and late plays, deduplicates by Python object identity, then sorts by ID and truncates to the limit. _game_facts supplies scores, period totals, lead changes, selected plays, and leaders to the writer. General-model fallback tries configured Anthropic models and then OpenAI; deterministic prose is the final fallback.

    A concrete counterexample to the late-play guarantee

    Take a limit of 16. Suppose the 16 highest-weight events are early in the game and the five late events are different objects. The union contains 21 entries. The function sorts that union by event ID and then takes the first 16. If IDs increase with time, the final slice can remove all five late events. The code tried to improve coverage, but the last operation undoes the earlier decision.

    The fix is a selection policy, not a stronger writing prompt. Reserve a defined number of slots for required late events, remove those stable event IDs from the remaining pool, and fill the remaining slots by score. Only then sort the chosen set chronologically. A useful test asserts both the size limit and retention of the required late events. A separate test can check that two independently parsed records with the same provider ID do not appear twice; Python object identity is not a durable event identity.

    This matters because evidence compression is lossy. A model cannot reliably recover an omitted final stop from the final score alone.     A recap is prose; a reel or broadcast also has a timeline, media, speakers, and interruption. The same factual foundation must survive those additional structures.

    07

    Reels and broadcasts: connecting facts, clips and speech

    The documented reels use real clip URLs obtained through the data source. The application selects clips, organizes scenes and produces narration or overlays. It is not generating the original game footage. Availability through an endpoint also does not by itself establish unrestricted rights to reuse a clip.

    An overlay is information drawn over a video, such as a score label. A timeline determines when scenes and narration appear. A correct number shown at the wrong moment can still mislead—for example, displaying the final score as if it were already known halfway through the game.

    Text to speech (TTS) turns written narration into audio. The described browser uses speech synthesis. Speech recognition converts spoken input into text for follow-up questions. These are different tasks, and browser support, interruption and playback timing need handling.

    Why broadcast output needs structure

    A two-host broadcast needs more than a paragraph. Each turn must identify who speaks, what they say and which scene it accompanies. JSON provides a machine-readable list that the player can follow.

    Illustrative turn:

  "host": "play",
  "text": "The Owls finish with a 104–101 win.",
  "scene_type": "title",
  "duration_hint": 8

    The documented implementation describes target turn counts of 12, 26 and 44 for two-, five- and ten-minute tiers. A turn count is a planning device; it does not guarantee exact audio duration because voices and speaking rates vary.

    A long model response can stop before its JSON is complete. The documented parser attempts to recover complete objects. Recovery should still validate required fields and factual content. Syntactically recovered text is not automatically a coherent or correct broadcast.

    • For missing media, show an honest unavailable state rather than inventing a clip.
    • For duplicate clips, avoid repeatedly showing the same moment as different events.
    • For interrupted speech, stop stale narration before starting the next answer.
    • For missing score context, omit the overlay rather than manufacture a value.

    A playable story has both semantic and temporal constraints

    A text recap can be read at any pace. A narrated reel must fit speech onto a timeline and associate each segment with available media. If a sentence describes the final shot while the clip shows an earlier possession, the output is misleading even when the sentence itself is factual. Clip-event alignment is therefore a separate validation problem from language quality.

    For an illustrative planning calculation, 45 words spoken at 150 words per minute require about 18 seconds. That is only an estimate: pauses, names, emphasis, and synthesized pronunciation affect actual duration. If the chosen clip lasts eight seconds, the system must shorten narration, extend the visual plan, or choose another presentation. Silently truncating audio can remove the qualifier that made a statement accurate.

    A proposed scene manifest would bind event ID, clip URL, intended time interval, narration text, generated audio duration, and fallback behavior. Schema validation can ensure fields exist; media checks can verify availability; timing checks can detect overrun; factual checks can verify the description. No single “valid JSON” result establishes all four properties.

    Two-host broadcasts introduce turn-taking rather than independent truth sources. Both hosts usually speak from the same fact sheet. Alternating speakers can improve pacing, but agreement between them is not corroboration. A robust renderer needs bounded turn counts, valid speaker IDs, and recoverable behavior when a voice or clip fails. These are product constraints that should remain explicit alongside the writing prompt.

    Personalization: ranking first, writing second

    A personalized newsletter has two jobs. First, choose and order relevant events. Second, write a readable digest from those events. A good writer cannot repair a selection process that ignored the fan’s teams or omitted the week’s important games.

    The ranking features described in the original guide include followed-team match, followed-player match, recency, event importance and whether the event is upcoming. Each is a number. The scorer multiplies each feature by a weight, adds the contributions and a starting offset, then transforms the result.

    Illustrative ranking calculation — simplified weights

    Give a followed-team match weight 2, recency weight 1 and importance weight 1, with starting offset −1. For a recent important followed-team event, values of 1, 1 and 1 yield −1 + 2 + 1 + 1 = 3. An old unrelated event with values 0, 0 and 0.2 yields −0.8. The first ranks above the second.

    A sigmoid maps those raw scores into the interval from 0 to 1 while preserving their order. It does not magically turn chosen weights into learned weights or a calibrated probability that the fan will click.

    Heuristic weights are selected by the developer. Learned weights are fitted using examples and target labels. The checked README explicitly allows heuristic ranking until the trained artifact is supplied. The source-linked account reported that the reviewed repository did not contain the exported curation weights; deployment-specific files still require separate verification.

    Recency and cold starts

    A recency feature decreases as an item becomes older. Exponential decay makes the value shrink smoothly rather than abruptly disappear at a cutoff. The decay speed is a design choice that should reflect the product’s purpose.

    A cold-start fan has little or no preference history. The system needs a defined default rather than inventing preferences. A fan who follows many teams also has more candidates, so deduplicating game IDs prevents the same game from appearing multiple times.

    The newsletter writer then receives the ranked facts. A shared newsletter issue may be stored under a share token with an expiration. A token identifies a saved issue; it should not silently cause a different fan’s preferences to be used when that issue is opened.

    Ranking and writing should be evaluated independently

    Personalization begins with a candidate set. If the candidate set contains no Owls game, even a perfect relevance model cannot rank it first. This mirrors the retrieval problem in the other article: candidate coverage limits the best possible ranking. After candidate construction, a scorer can combine team preference, recency, event importance, and diversity.

    Consider a toy score with two points for a followed team, one for freshness, and one for a close finish. An Owls story may rank above a more globally important game because it matches the fan. These weights are illustrative, not fitted project parameters. The example shows what a transparent rule does and why its weights are product choices rather than learned evidence of user satisfaction.

    Writing should then use the selected stories and the intended perspective. If the writer independently changes which stories matter, it becomes difficult to attribute a poor feed to ranking or generation. Freezing the ranked list lets a reviewer evaluate relevance separately from phrasing, and lets a writer upgrade preserve the selection baseline.

    Offline ranking metrics also need careful interpretation. Relevance labels describe the judgment policy and candidate set used in evaluation. Clicks add behavioral evidence, but position, headlines, and exposure affect them. A high-ranked item receives more opportunities to be clicked. A proposed learned ranker therefore needs an explicit training signal and an evaluation design that distinguishes actual preference from the consequences of the old ordering.

    The ranking equation exposes what personalization actually uses

    _features produces followed-team/player indicators, exp(−max(age_days,0)/7), clipped magnitude, and an upcoming indicator. score_item computes sigmoid(b + w·x); rank_items rounds scores to four decimals before sorting. The weight loader is cached once per process and falls back to heuristic-v1 if the JSON file is absent or invalid. The checked repository tree does not contain that weight file.

    Training concepts: distillation, LoRA and what proves deployment

    Fine-tuning continues training a pretrained model on a narrower task. The model’s numerical settings are adjusted so it becomes better at the desired output style or structure. This is separate from merely putting task instructions in a prompt.

    Distillation uses a stronger teacher model to create training examples for a student model. For sports writing, the teacher receives verified facts and produces a draft. The student learns to produce similar outputs from similar inputs. Teacher mistakes can enter the training set, so filtering is part of the learning pipeline, not an optional final polish.

    Collect game facts and retain source identifiers.

    Separate games into training, validation and final test groups.

    Generate teacher drafts for training examples.

    Reject drafts with unsupported names, numbers or malformed structure.

    Train the student or its adapters.

    Evaluate on untouched games against a template and general-model baseline.

    Deploy the chosen artifact, then log which checkpoint actually serves requests.

    LoRA and QLoRA, without the shorthand

    A large model has many weights. Updating every weight during training requires memory for the weights and additional training information. Low-rank adaptation (LoRA) trains smaller added matrices while keeping the original weights fixed. The smaller matrices describe a constrained adjustment to selected computations.

    QLoRA also stores the frozen base model using a compressed numerical representation. This can reduce training memory further. It does not remove the need to load a model, process examples, validate output or evaluate whether the adaptation helped.

    A checkpoint is a saved model state. An adapter checkpoint contains the learned adjustments. Training scripts establish that a workflow is available; a checkpoint establishes that weights were saved; configuration establishes a serving path; request logs establish which model actually ran. These are different evidence levels.

    Why splitting by paragraph is misleading

    If one game’s recap is in training and another paragraph about the same game is in testing, the student may already have seen the result and key players. Split by game ID and time so related material stays together. Use validation data to choose settings, then leave the final test untouched.

    What LoRA changes in one matrix multiplication

    A dense linear layer maps an input x through a matrix W. LoRA keeps the base matrix frozen and learns an update B A, where A compresses into a small rank r and B expands back to the output width. The adapted layer computes W x plus a scaled B A x. The low rank limits the family of updates, which saves trainable parameters but can also restrict how much the layer can change.

    For a square 4,096-by-4,096 matrix, full tuning exposes 16,777,216 parameters in that matrix. A rank-16 adapter uses 16×4,096 plus 4,096×16 = 131,072 parameters, about 0.78% as many. This is illustrative per-matrix arithmetic; the total model has many layers and may adapt only selected modules. The base weights still exist and still consume memory.

    Supervised fine-tuning minimizes prediction error on target tokens from example conversations. A teacher-generated target is a training label, not independent ground truth. If the teacher invents a statistic and a weak filter accepts it, the student is trained to reproduce that error. Distillation therefore needs source-grounded targets and a held-out factual evaluation, not merely a decreasing training loss.

    The deployed request path adds another contract. A compatible base revision, adapter, tokenizer, prompt format, and generation configuration must be loaded together. A successful training script or saved directory does not prove that the endpoint uses that artifact. To establish deployment, retain a traced test request with route and revision information; to establish improvement, compare against the baseline on the same frozen game snapshots.

It does not make every tensor four-bit: gradients, optimizer states for trainable parameters, activations, and temporary workspaces still occupy memory. The script’s single-GPU fit comments are recipe claims for particular circumstances, not a verified capacity guarantee for every base model or sequence length.

    The code passes a held-out dataset to the trainer, but the shown configuration does not explicitly set an evaluation cadence or a best-model selection policy. It also provides one serialized conversation text rather than showing an explicit assistant-only loss mask. Those details can depend on the installed training-library version. Before describing exactly which tokens receive loss or which checkpoint is best, inspect the pinned dependencies and training logs. Saving an adapter proves an artifact was written only after the run itself succeeds; this article has not executed that run.

    Deployment is a further step. The serving endpoint needs the compatible base model, adapter revision, tokenizer and prompt template, and the application’s configured model name. A health response is weaker evidence than a traced test request showing that the intended adapter generated the output. The general-model fallback can keep the product usable while hiding a broken trained route unless route choice and failure reason are logged per request.

    A trained writer does not solve identity or shared-state problems. Those become especially visible in prediction games, where a repeated update can alter a leaderboard.

    Identity, Redis and the double-points problem

    The documented browser creates an anonymous UUID, a long identifier intended to be unique, and saves it in local storage. It sends that identifier in the X-Device-Id request header. A header is metadata attached to a request. The backend can use the identifier as a key for fan state.

    Local storage persists values in one browser. Clearing it or switching browsers can create a different identity. A client-supplied device ID is not strong authentication: knowing or copying an identifier is different from proving account ownership.

    Redis is a fast data store. A hash stores named fields, such as a fan’s counters. A sorted set stores members with numerical scores and supports ranking them. Replays uses these structures for picks, points and leaderboards when Redis is configured.

    The checked README says storage operations become no-ops when REDIS_URL is absent. The interface may still load, but that is not proof that points are being persisted. Durability also depends on the actual Redis service and configuration, not just the library being imported.

    The race condition, step by step

    A race condition occurs when the result depends on the timing of overlapping operations. The source-linked account identifies a read-check-write pattern in pick resolution that can double-award points:

    TimeRequest ARequest B
    1Reads “pick unresolved.”
    2Also reads “pick unresolved.”
    3Marks it resolved and adds 10 points.
    4Acts on its earlier read and adds another 10.

    Idempotency means repeated processing of the same logical pick should not change the final award after the first successful resolution. Checking a flag is insufficient if the check and update can be separated by another request.

    An atomic operation happens as one indivisible state change relative to other competing operations. A Redis script or properly designed transaction can check unresolved status, mark resolution and award points together. With an optimistic transaction, a conflicting change must cause a retry rather than letting stale assumptions proceed.

    This is a proposed strengthening of the documented design. It should be verified with simultaneous requests and a failure between writes, not just by clicking the button twice slowly.

    Exactly-once effects require a complete state transition

    There are two failure directions in the current read-check-write pattern. Concurrent requests can both see an unresolved pick and award twice. A crash after writing the resolved flag but before updating the leaderboard can award nothing, because the retry sees an already resolved pick. Moving the flag before or after the counter merely changes which failure window is exposed.

    A proposed atomic script would inspect the pick, compute the award, update its terminal state, and adjust all required counters as one operation on the chosen store. The script still needs a clear business rule for corrections: if the game result changes later, should the award be reversed, versioned, or manually reconciled? Atomicity protects concurrency; it does not choose the policy.

    An alternative is an immutable award ledger keyed by a logical event ID, with derived counters rebuilt or reconciled from that ledger. This creates more storage and operational work, but provides an audit trail and a way to repair aggregates. It also distinguishes the idempotency key of an award from the HTTP request ID, since retries of one logical action can arrive as different requests.

    Identity remains separate. A device UUID can consistently group state from one browser without proving who controls it. Stronger authentication becomes relevant when the application needs account ownership or cross-device continuity. The present identifier should therefore be described as a client bucket, with persistence and authorization evaluated separately from the correctness of the points calculation.

    Read-check-write is not an atomic award

    mark_resolved reads a pick from a Redis hash, returns if already resolved, writes the resolved record, then separately increments profile counters and the leaderboard sorted set. Serial retries often return zero, but concurrent requests can both read unresolved before either writes. A crash after the resolved marker but before the counters creates the opposite failure: a retry sees resolved and may never finish awarding the points.

    Evaluation: check the whole product, one layer at a time

    A demo shows an example. Evaluation measures behavior across a defined collection of cases. Each component needs a reference answer and an appropriate metric.

    ComponentUseful checkWhat the result tells you
    Data adapterMissing fields, duplicate IDs, source timestamps, known response fixtures.Whether downstream facts are complete, fresh and correctly parsed.
    Play classificationHuman labels, precision and recall for each play type.Which categories are wrongly added or missed.

    Precision is the share of predictions that are correct. Recall is the share of true cases found. In an illustrative test with 20 true scoring plays, finding 18 while wrongly flagging 2 non-scoring plays gives 18/20 = 90% for both. The denominators happen to match in this example; they need not match generally.

    NDCG, normalized discounted cumulative gain, evaluates a ranked list using graded relevance. Relevant items near the top earn more credit than the same items much lower down. The score is compared with the best ordering for those relevance labels. It is meaningful only when the judgments and candidate set are defined.

    For generation, check factual claims rather than only whether names and numbers appear somewhere in the input. A sentence can contain allowed names and numbers but assign one player’s statistic to another. Human review is valuable for those relationship errors.

    The source-linked account did not establish a production factuality rate, learned-ranker uplift, cache hit rate or p95 latency benchmark. The checked README describes intended grounding and labeled fallbacks; those descriptions are not a completed blind quality study.

    An adversarial example should change a relationship, not just a word

    Suppose the fact sheet says Player A scored 30 points and Player B scored 12. The sentence “Player B scored 30” contains only known tokens and numbers. A vocabulary-membership filter can accept it even though the relationship is false. A useful adversarial test deliberately swaps subjects while preserving the token set, exposing the gap between lexical grounding and entailment.

    Other fixtures should change temporal relations: a tying basket becomes a winning basket, a first-half lead becomes a final lead, or a scheduled matchup becomes a completed game. These errors can survive basic name and score checks. Human labels should specify which assertion is unsupported and why, allowing automated checks to be evaluated against a consistent reference.

    Report both false acceptance and false rejection. A filter that blocks every story has no accepted fabrications but is unusable. A filter that accepts everything has full coverage but provides no protection. Precision and recall of the filter, output coverage, and quality among accepted stories describe the tradeoff together.

    Keep the same game snapshots and selected evidence when comparing template, general-model, and adapted-model outputs. Otherwise, different input completeness can dominate the apparent model improvement. A complete evaluation also records fallback route and latency: the product's delivered quality includes degraded paths, not just its best successful generation examples.

    The filter tests vocabulary membership, not factual entailment

    The filter extracts all digit strings from serialized facts and allows matching numbers in target prose. It checks a simple capitalized two-word name pattern against available tokens. A sentence assigning player A's 30 points to player B can pass if both names and 30 occur in the facts. A fabricated 12-point statistic is ignored by the numeric threshold, and one unsupported large number can still pass because the function tolerates one reason.

    Scaling: what happens when many fans arrive together?

    A bottleneck is the stage limiting throughput, the amount of work completed per unit time. The likely candidates in this design are upstream data calls, uncached model generation, shared-store operations and client media playback. These are hypotheses until measured.

    Latency is one request’s duration. p95 latency is the duration at or below which roughly 95% of measured requests finish. Measure cold cache misses separately from warm hits: a combined average can hide slow first-time experiences.

    Backpressure prevents the system from accepting or launching work faster than a dependency can handle. Examples include limiting simultaneous model calls and queuing refreshes. Without limits, a slow dependency can create more waiting requests, retries and memory use.

    Collapse duplicate work. Many fans opening one game should reuse a common source fetch and eligible recap.

    Separate freshness policies. Live scores, final recaps and preference-specific newsletters have different cache needs.

    Bound retries. Wait progressively longer between transient retries and add a small random delay so clients do not all retry together. Stop after a defined limit.

    Protect state changes. Resolve picks atomically and avoid duplicate awards after uncertain responses.

    Record failures visibly. Distinguish an empty valid dataset, unavailable supplier, model fallback and disabled persistence.

    A relational database such as PostgreSQL could be useful for long-term history, joins and richer transactional reporting. But a proposed ingestion architecture with millions of permanent event rows should not be described as the current live-fetch implementation unless its code and operating evidence are available.

    Similarly, the application calls hosted writers. Buying GPUs is not automatically the first optimization when repeated supplier requests or cache misses dominate. First measure the time spent fetching, selecting, writing and storing.

    A burst turns latency into a capacity problem

    If uncached generation takes ten seconds and arrivals average two new uncached jobs per second, a stable system has roughly twenty jobs in progress on average under those illustrative conditions. This follows from average work in the system equaling arrival rate times average time in the system. It is a capacity intuition, not a measured Replays benchmark.

    If a provider can sustain only one such job per second, the queue grows unless the application reduces admissions, deduplicates requests, or serves a bounded fallback. Adding backend replicas can increase the rate at which the quota is exhausted. More application processes do not create more provider capacity, and they also create additional process-local caches.

    Blocking calls inside an asynchronous handler are another bottleneck. An event loop can coordinate many waiting operations when those operations yield control. A direct synchronous network call can occupy that loop until completion. Moving it to a suitable thread or asynchronous client changes scheduling behavior, but still requires concurrency limits to avoid overwhelming dependencies.

    A useful load experiment separates same-game bursts from many-game bursts. Same-game traffic tests deduplication and cache reuse; many-game traffic tests actual provider and writer throughput. Record queue time separately from service time and identify the fallback path for every result. Those observations show whether the next improvement should target repeated work, blocking execution, or admission control.

    Concurrency and cache consistency define the scaling work

    Both source-fetch and recap caches guard their dictionary operations, but their expensive work happens outside the lock. This avoids serializing every request behind one network call; it also permits a cache stampede on a popular uncached game. The general-model helper stores the last error in a module-level variable, which can mix concurrent request diagnostics. The async generation endpoint directly calls the synchronous recap function.

    Scale the repeated work you can identify

    When many fans open the same game, the first question is which work is duplicated: upstream fetching, evidence selection, writer inference, or serialization. Source caching and recap caching address different costs. A shared result cache does not prevent simultaneous misses; a queue does not automatically make writes idempotent; adding application replicas does not raise a provider’s quota. The architecture should assign one owner to expensive work for a given fact version and let other requests observe that job.

    Useful request telemetry includes game ID, source-fetch time, fact fingerprint, cache layer and hit status, selected-event count, writer route, model and prompt revision, latency, and degraded-result reason. These fields explain whether a slow request waited on sports data or model inference and whether an apparently fast response served stale facts. Keep provider errors in the request’s context; the module-level last-error variable can otherwise describe another request’s failure.

    A production-quality evaluation should replay corrected scores, missing leaders, invalid clocks, duplicate events, a provider timeout, a malformed generated turn, and overlapping requests. Those cases exercise the architecture’s promises. They do not require claiming that a larger model, another agent role, or a new GPU will fix failures whose cause is ordering, identity, or stale state.

    What the implementation establishes

    Replays AI is a pipeline for preserving, selecting, and presenting sports evidence. The strongest design decisions make those responsibilities explicit: one adapter for provider formats, shared fact sheets for writing, route labels for degraded generation, and a separate ranking stage for personalization. The most consequential weaknesses are equally concrete: mutable source facts under stable cache keys, late evidence lost by a final slice, request-local events represented by shared state, and training claims that need deployed-artifact evidence.

    What a convincing end-to-end demonstration would preserve

    A strong demonstration starts with a frozen game snapshot, records which events were selected, identifies the writer route, and returns a story with explicit source provenance. It then repeats the request under a cache hit, a provider timeout, a corrected score, and concurrent demand. These cases test the product's promises more directly than generating a second polished paragraph.

    The important architectural lesson is that generation sits downstream of identity, normalization, selection, and freshness. Improvements to those stages can make an unchanged writer more reliable. A stronger writer becomes meaningfully better only when it is compared on the same evidence and the delivered fallback behavior is included in the evaluation.

    A useful improvement sequence begins with event identity and source provenance, then selection invariants, then validated output structure and request-level tracing. A stronger writer can improve the prose, but the system will only know what that improvement means when the underlying facts, selected events, and fallback path are held constant.
