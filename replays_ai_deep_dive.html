    Replays AI: from a game record to a story

    Replays AI turns live sports data into recaps, broadcasts, and personalized feeds. The interesting decisions happen before and after the writer: which plays survive selection, when a recap can be reused, and how failures reach the fan.

    Here is how the implementation works, where its shortcuts become visible, and what I would change next. The code and diagrams follow the request from ESPN data to the final experience.

    Two-page cheatsheet · All three cheatsheets

    Source revision: a867fdab. Rationale is engineering analysis unless explicitly documented; proposed improvements are not claimed as implemented. No model training, deployment benchmark, or scientific experiment was rerun.

    Where the engineering happens

    The hard part of a sports recap is deciding what the writer gets to see. A game can contain hundreds of plays, incomplete player statistics, and a status field that disagrees with the score. Replays AI has to turn that record into a small, usable account of the game before a language model writes a sentence.

    The architecture separates fetching, normalization, selection, and writing. That separation gives a practical way to investigate a bad recap. A wrong score points toward the adapter or stale data. An omitted final play points toward selection. An invented statistic points toward the writer and its checks.

    This article follows those boundaries through the pinned implementation. The Owls–Foxes game used below is invented. Source excerpts describe existing behavior; the final chapter collects changes I would make next. The rationale is my engineering assessment, rather than a claim about undocumented decisions or production incidents.

    01

    One source, several products

    Replays uses a React frontend and a FastAPI backend. The backend reads ESPN data on demand, normalizes the response, and prepares facts for several outputs: game recaps, narrated reels, two-host broadcasts, and personalized newsletters. Redis provides shared storage when configured. Prediction games use it for picks and leaderboard state.

    These products share inputs, but they do not share every constraint. A recap needs a coherent account of one game. A newsletter first needs to choose games relevant to a fan. A reel also needs an available clip and enough time to speak its narration. A broadcast needs structured turns that the player can render.

    Fan chooses teams and players
  → browser requests a feed or game
  → backend obtains ESPN data
  → adapter converts it into consistent fields
  → rules select and analyze important events
  → writer or template produces a story
  → interface displays facts, media and source labels

    This division keeps the model away from provider-specific parsing. It also lets the system return useful output when a writing service fails. The recap route can use deterministic prose, while newsletter and broadcast routes can fall through from a configured trained writer to a general model and then a template.

    The tradeoff is coordination. An update to the score can affect several outputs. A preference change affects newsletter selection without changing the game itself. A removed clip affects the reel even when the text remains accurate. Each product has its own dependencies, so a single cache policy cannot describe all of them.

    The README supports conditional trained-model paths. It does not establish that a trained checkpoint handled a particular live request. I treat routing code, trained artifacts, and measured results as separate evidence throughout this account.

    The practical benefit of this staged design is that a change can be tested at one boundary. Fixing event identity should alter duplicate selection without requiring a new writer. Changing a prompt should preserve the normalized game facts. Those expectations provide useful regression checks.

    02

    Following one recap request

    Suppose the Harbor Owls beat the Valley Foxes 104–101. A fan opens the game page. The browser sends the game ID, and the backend looks for a reusable recap in its local memo and shared cache.

    On a miss, it fetches the game and summary. The adapter extracts teams, scores, status, and identifiers from ESPN’s nested response. The recap builder then extracts plays and leaders, selects a smaller set of events, and builds the writer’s fact sheet.

    {
  "game_id": "illustrative-game",
  "status": "final",
  "home_team": "Harbor Owls",
  "away_team": "Valley Foxes",
  "home_score": 104,
  "away_score": 101
}

    This simplified record illustrates the data flow; it is not the production response schema. In the actual route, the fact sheet also carries selected plays and available statistics. Suppose it includes a late three-pointer and the final defensive stop. Those events give the writer a basis for explaining the finish. The score alone does not.

    The writer can produce a narrative from that fact sheet. If generation fails, the template can still report the known result. The response identifies which route produced the text, and cache eligibility is checked separately.

    Three failures can look similar on the page. If ESPN never supplied the final stop, ingestion lacks the event. If the selector removed it, the writer never received it. If a cached recap predates a correction, the original generation may have been faithful to an obsolete snapshot. Keeping those cases distinct matters more than adding another instruction to the prompt.

    The same boundary governs factual claims. “The Owls won 104–101” follows from a verified final result. “The Owls won in overtime” requires period information. “The final stop secured the win” requires the event sequence. Fluent wording cannot supply the missing relationship.

    03

    Normalizing ESPN data without losing its meaning

    The adapter in api/espn_public.py contains the provider-specific structure. Most reads happen on demand rather than through a permanent event warehouse. This keeps the application relatively small, but makes its behavior depend on the provider response available at request time.

    _event_to_game rejects records without a competition, both competitors, or an event ID. It then emits a consistent record with sport, date, status, team fields, and nullable scores. The rest of the application can consume that shape without understanding ESPN’s nesting.

    api/espn_public.py · lines 143–171 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def _event_to_game(event: dict, sport: str) -> dict | None:
    competitions = event.get("competitions") or []
    if not competitions:
        return None
    competitors = competitions[0].get("competitors") or []
    home = next((c for c in competitors if c.get("homeAway") == "home"), None)
    away = next((c for c in competitors if c.get("homeAway") == "away"), None)
    if not home or not away:
        return None

    event_id = str(event.get("id") or "")
    if not event_id:
        return None

    home_team = _team_from_competitor(home, sport)
    away_team = _team_from_competitor(away, sport)
    return {
        "id": int(event_id),
        "external_id": event_id,
        "sport": sport.upper(),
        "status": _status_from_event(event),
        "game_date": _parse_espn_datetime(event.get("date")),
        "home_team": {"id": home_team["id"], "name": home_team["name"], "abbreviation": home_team["abbreviation"]},
        "away_team": {"id": away_team["id"], "name": away_team["name"], "abbreviation": away_team["abbreviation"]},
        "home_score": _score_value(home.get("score")),
        "away_score": _score_value(away.get("score")),
        "video_url": None,
    }

    The score conversion is an important detail. _score_value returns None for absent or invalid values, while preserving a real zero. That lets later code distinguish an unplayed or incomplete record from a team that has scored no points.

    The record also retains the provider identifier as external_id, while converting id to an integer. That conversion assumes the provider continues to return numeric IDs. A nonnumeric identifier would fail here, before any writing service becomes involved.

    The fetch helper uses a URL-and-query cache key, a 12-second HTTP timeout, and raise_for_status. Parsed JSON is stored under a lock. These choices bound waiting and reduce repeat calls, but they do not validate every nested field. A successful HTTP response can still contain an incompatible shape.

    Why score presence became a generation gate

    A comment in the recap builder records a specific provider problem: a finished game can arrive labeled “scheduled.” The implementation works around that by checking whether both scores exist before attempting a full model recap.

    This is a pragmatic accommodation, but played is broader than “finished.” A live game can have two scores. The cache adds a separate exclusion for the explicit live status, so generation eligibility and cache eligibility are related but different checks.

    If the provider mislabels a live game, both checks can still make the wrong decision. The response’s ready state describes the recap artifact; it cannot resolve uncertainty about the game’s status. This is a limitation of the normalized record, not a language-model problem.

    There is a similar distinction between an empty result and an unavailable result. No matching games is a valid answer. A timeout means the application could not obtain an answer. The current helpers and route checks do not preserve every such distinction, which can make upstream failures resemble missing games.

    How the adapter narrows a failure

    The early returns in _event_to_game keep structurally incomplete events out of downstream processing. They also mean that a missing competitor is represented by no normalized game, rather than a partial record explaining which competitor was absent. That simplifies callers, but loses diagnostic detail at the boundary.

    Consider an event with a valid ID and one missing team object. Returning it unchanged would force every consumer to defend against the same nested-field failure. Rejecting it centrally avoids that duplication. A structured rejection reason would preserve the benefit while making it possible to distinguish a malformed provider record from an unknown game ID. The current excerpt implements the rejection, not that richer error contract.

    04

    What the recap cache actually guarantees

    The recap route checks an in-process memo, then Redis, under recap:v2:{game_id}. A hit avoids fetching and generation. A miss resolves the game and summary, builds a recap, and decides whether to save it.

    api/recaps.py · lines 382–406 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def get_recap(game_id: int):
    cache_key = f"recap:v2:{game_id}"
    cached = _memo_get(cache_key) or cache_get(cache_key)
    if cached:
        return cached

    resolved_game = fetch_espn_game_by_id(game_id)
    resolved_summary = fetch_espn_summary_by_id(game_id)
    if not resolved_game or not resolved_summary:
        raise HTTPException(status_code=404, detail="Game not found")
    sport, game = resolved_game
    _, summary = resolved_summary

    result = _build_recap(game_id, sport, game, summary)
    settings = get_settings()
    llm_configured = bool(settings.anthropic_api_key or settings.openai_api_key)
    played = game.get("away_score") is not None and game.get("home_score") is not None
    # Cache played games (final/mislabeled), but not obviously-live ones whose
    # numbers keep changing. Never cache a fallback recap when an LLM is
    # configured — a transient provider error would pin the lesser recap.
    if played and game.get("status") != "live" and (result["generated_by"] == "llm" or not llm_configured):
        _memo_set(cache_key, result)
        cache_set(cache_key, result)
    return result

    The write condition requires both scores and a status other than live. It also checks the generation route. When a general LLM is configured but fails, the data fallback is returned without being stored as the preferred recap. A later request can try the writer again.

    That is a useful quality tradeoff. Caching every fallback would make a short provider outage visible for much longer. Refusing to cache it avoids that problem, but sustained failure can trigger repeated generation attempts. The current condition favors recovery of writing quality over suppression of retry traffic.

    The local memo lasts six hours. It belongs to one Python process, so another process cannot see it. Redis can share results across processes; without it, each process may repeat the work. The memo also clears the whole dictionary once its size guard is exceeded. It is not a least-recently-used eviction policy.

    Two misses can still call the writer twice

    The lock covers dictionary reads and writes, not the interval between them. Request A can read a miss and release the lock. Request B can then read the same miss. Both perform the network and generation work before either stores a result.

    This arrangement avoids holding a global lock across a slow provider call. Unrelated requests can progress. The cost is duplicate computation for the same game. Thread-safe storage and one generation per game are different guarantees.

    A final score can still be corrected

    Consider the first request for the illustrative 104–101 result. It misses both caches, generates successfully, and stores the recap. A second request reuses it. Now suppose ESPN corrects the score. The key still contains the same game ID and format version, so it gives no indication that the underlying facts changed.

    The six-hour TTL limits reuse time; it does not validate the source snapshot. Adding a digest of the facts would identify the exact input used for a story, but discovering a newer digest would still require a fetch or an invalidation signal. Cache identity and freshness are separate design problems.

    The present cache therefore offers inexpensive reuse with a bounded local lifetime and a deliberate fallback policy. It does not offer correction-aware invalidation or coordination of concurrent misses. Those changes belong in the improvement plan, rather than in a description of what this revision already does.

    05

    Play analysis is a set of explicit rules

    The inspected play parser reads structured summaries and text cues such as “3pt,” “dunk,” “sack,” and “touchdown.” It does not classify video frames. The Scout, Stat, Ref, and Predict roles organize deterministic calculations behind a common analyze(ctx) → AgentRead interface.

    PlayContext supplies current and previous scores, clock, period, description, and optional kick distance. This makes the modules cheap to run and easy to inspect. It also limits what they can know: a description of a made shot does not reveal whether the defender rotated late.

    api/play_analysis.py · lines 64–98 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    

# ── Transparent statistical proxies (heuristics, not learned) ───────────────────
def fg_make_probability(distance: Optional[int]) -> float:
    """Logistic approximation of NFL field-goal make rate by distance. Heuristic
    eyeballed to public make-rate curves (~99% at 20y, ~80% at 45y, ~50% at 53y)."""
    if not distance:
        return 0.0
    return 1.0 / (1.0 + math.exp((distance - 53.5) / 6.5))


def seconds_remaining(period: int, clock: Optional[str], sport: str) -> int:
    quarter = 15 * 60 if sport.upper() == "NFL" else 12 * 60
    in_quarter = 0
    if clock and ":" in clock:
        try:
            mm, ss = (int(x) for x in clock.split(":")[:2])
            in_quarter = mm * 60 + ss
        except ValueError:
            in_quarter = 0
    return max(0, (4 - min(period, 4)) * quarter + in_quarter)


def win_probability(margin: int, secs_left: int, sport: str) -> float:
    """Time-decayed logistic on score margin — a WP *proxy*, not a trained model.
    Margin matters more as time runs out."""
    total = (4 * 15 * 60) if sport.upper() == "NFL" else (4 * 12 * 60)
    frac_left = max(0.02, secs_left / total)
    scale = 7.0 * math.sqrt(frac_left)
    return 1.0 / (1.0 + math.exp(-margin / max(0.5, scale)))


_POINTS = {"touchdown": 7, "field_goal": 3, "safety": 2}

    Reading the probability formulas

    The field-goal proxy is a logistic curve with midpoint 53.5 yards and scale 6.5. At 53.5 yards, the exponent is zero and the output is 0.5. At 45 yards, it is about 0.787; at 20 yards, about 0.994. These are calculated outputs of hand-set constants, not measured make rates.

    Multiplying the 45-yard value by a three-point reward gives approximately 2.36 points. That calculation describes only the kick reward under the proxy. It omits field position after a miss, blocked returns, penalties, and strategic alternatives. It is not a complete possession-value model.

    The win proxy applies a sigmoid to score margin divided by a time-dependent scale. As time runs out, the scale shrinks and the same lead produces a more extreme output. A three-point lead with the full seven-point scale gives about 0.606. At one percent of regulation time remaining, the two-percent floor gives a scale near 0.990 and an output near 0.954.

    This encodes an understandable intuition: a late lead matters more. It excludes possession, team strength, timeouts, and a separately learned overtime model. A value of 0.8 therefore cannot be interpreted as an empirically calibrated 80% chance of winning.

    Repeatable prose can still overstate the evidence

    Some Scout templates describe a defender arriving late or a rush winning a matchup without visual evidence. StatAgent can substitute a default two- or three-point value when the observed score change is zero. That deserves scrutiny on missed-shot descriptions. Missing kick distance also returns 0.0, conflating an unknown probability with an impossible outcome.

    These issues are visible in the rules themselves. Replacing the modules with learned models would introduce new data and evaluation requirements without automatically fixing them. The common interface makes replacement possible, but the immediate question is whether each output is justified by the fields in its context.

    The clock changes the proxy as much as the margin

    seconds_remaining uses 15-minute quarters for NFL and 12-minute quarters otherwise. It adds the current clock to the remaining regulation quarters. For example, an NFL third quarter with 5:00 remaining becomes 1,200 seconds: five minutes in the current quarter plus fifteen in the fourth.

    A malformed clock falls back to zero within the quarter. At the same score, that can make the win proxy more confident because it appears that less time remains. Periods beyond four are clamped in the regulation calculation, so an overtime clock is not being interpreted through a separate overtime model. These assumptions explain why the clock parser and probability function need to be read together.

    06

    The selector decides what the writer can know

    The recap builder extracts up to 300 plays, collects leaders, and constructs a fact sheet. Before writing, _key_plays compresses the event list. It favors classified events, assigns category weights, and penalizes descriptions containing “miss.” Touchdowns receive weight 10, dunks 9, and three-pointers 8.

    This reduces prompt length and gives the writer a manageable sequence. The editorial tradeoff is that spectacular plays are not always decisive plays. A routine final stop may explain the result better than an early dunk.

    api/recaps.py · lines 180–189 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def _key_plays(plays: list[dict], limit: int = 16) -> list[dict]:
    interesting = [play for play in plays if play.get("play_type") not in (None, "other")]
    if not interesting:
        interesting = [play for play in plays if play.get("description")]
    if len(interesting) <= limit:
        return interesting
    late = interesting[-max(4, limit // 3):]
    best = sorted(interesting, key=lambda play: (-_play_weight(play), play.get("id") or 0))[:limit]
    selected = {id(play): play for play in best + late}
    return sorted(selected.values(), key=lambda play: play.get("id") or 0)[:limit]

    The final slice undoes the late-play selection

    The selector combines the highest-weight plays with a tail of late plays. It deduplicates that union using Python object identity, sorts by event ID, and takes the first limit entries.

    With a limit of 16, the late set contains five plays. Suppose the top 16 weighted plays all happened earlier and the five late plays are distinct. The union contains 21 entries. If IDs increase with time, the final sort and slice retain the early 16 and discard all five late plays.

    The code explicitly tries to preserve the finish, yet its final operation can remove it. This counterexample follows from the selection logic; it is not a measured error rate from production. A more detailed prompt cannot restore evidence that never reaches the writer.

    The diagram separates membership from presentation. Its required-event policy is a proposed replacement: choose the evidence set first, then restore chronology. The existing implementation mixes those decisions through its final ID sort and size limit.

    Object identity introduces another limitation. Two separately parsed dictionaries describing the same provider event have different Python identities. They can both survive deduplication. Sorting by ID also assumes the ID order matches the game sequence.

    Writing and fallback

    _game_facts packages scores, period totals, lead changes, selected plays, and available leaders. The general-model path tries configured Anthropic models and can then try OpenAI. If no usable text is returned, deterministic prose provides the fallback.

    The generated_by field records the successful route. This is useful both for debugging and for comparing outputs: a template response during a provider failure should not be counted as an adapted model’s writing quality.

    The fact sheet places a ceiling on the story. If the selected events include the final three-pointer but omit the following possession, the writer can report the shot and score change. Whether it “secured the win” depends on what followed. This is the relationship-level distinction introduced in the request walkthrough.

    The response field cv_classifications counts selected key plays in this route. Despite the name, it does not demonstrate that computer vision watched the clips. The executable path uses structured summaries and text classification.

    07

    A broadcast needs a playable structure

    Reels attach existing video URLs and scene metadata to the story. They do not generate the original sports footage. Broadcasts add alternating hosts and a turn sequence. The browser uses speech synthesis for narration; speech recognition serves the separate task of spoken follow-up input.

    The broadcast tiers request 12, 26, or 44 turns for two-, five-, and ten-minute programs. Each turn carries a host, text, scene type, and duration hint. This gives the player something more useful than an unstructured paragraph.

    Illustrative turn:
{
  "host": "play",
  "text": "The Owls finish with a 104–101 win.",
  "scene_type": "title",
  "duration_hint": 8
}

    The example is illustrative. A duration hint is a scheduling estimate, not a measured audio length. At 150 words per minute, a 45-word turn needs about 18 seconds. An eight-second clip cannot contain it without shortening speech, extending the visuals, or choosing another presentation.

    Recovering partial model output

    _extract_turns first attempts to parse a bracketed JSON array. If parsing fails, it uses a regular expression to salvage complete flat objects. _clean_turns then normalizes host and scene values, truncates text to 400 characters, and clamps duration hints to 4–20 seconds.

    api/broadcast.py · lines 136–158 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def _clean_turns(raw: str) -> list[dict] | None:
    """Parse and normalize the model's turn array into the player's DTO shape."""
    turns = _extract_turns(raw)
    if not turns:
        return None
    cleaned = []
    for t in turns:
        if not isinstance(t, dict):
            continue
        host = str(t.get("host", "play"))
        if host not in ("play", "analyst"):
            host = "play"
        scene = str(t.get("scene_type", "moment"))
        if scene not in ("title", "moment", "stat", "run", "verdict"):
            scene = "moment"
        cleaned.append({
            "host": host,
            "text": str(t.get("text", ""))[:400],
            "scene_type": scene,
            "duration_hint": max(4, min(20, int(t.get("duration_hint", 8)))),
        })
    return cleaned if cleaned else None

    Salvage preserves usable turns when a long generation stops early. The cost is accepting partial output whose structure and meaning still need scrutiny. Nested objects and braces inside strings complicate regex recovery. An invalid duration can fail during int conversion. A 400-character cut can remove the end of a sentence or its qualification.

    Even a valid array can contain empty speech or an unsupported tactical explanation. The analyst prompt asks for causal commentary, while the supplied evidence may contain only event descriptions. Two hosts reading the same fact sheet do not provide independent corroboration.

    The routes run sequentially

    The endpoint submits the trained-writer call to a one-worker executor and immediately waits for its result. If that produces no usable turns, it does the same for the general model. The deterministic template is last.

    08

    Rank the stories before writing the newsletter

    The newsletter separates relevance from prose. Its scorer receives candidate items, assigns scores, and returns an ordered list. The writer then works from the chosen facts. This makes it possible to change writing style without silently changing which games the fan sees.

    The features are followed-team and followed-player indicators, recency, clipped magnitude, and an upcoming-event indicator. A weighted sum plus bias is passed through a sigmoid. The weight loader is cached once per process and falls back to heuristic-v1 when its JSON file is absent or invalid.

    api/curation.py · lines 60–82 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def _features(item: dict) -> dict:
    recency_days = float(item.get("recency_days", 3.0))
    return {
        "followed_team": 1.0 if item.get("followed_team") else 0.0,
        "followed_player": 1.0 if item.get("followed_player") else 0.0,
        "recency": math.exp(-max(0.0, recency_days) / 7.0),  # 1.0 today, decays weekly
        "magnitude": min(1.0, max(0.0, float(item.get("magnitude", 0.0)))),
        "upcoming": 1.0 if item.get("upcoming") else 0.0,
    }


def score_item(item: dict) -> float:
    w = _weights()
    feats = _features(item)
    z = float(w.get("bias", 0.0)) + sum(w["weights"].get(k, 0.0) * v for k, v in feats.items())
    return 1.0 / (1.0 + math.exp(-z))


def rank_items(items: list[dict], limit: int | None = None) -> list[dict]:
    """Return items sorted by learned relevance, each annotated with `_score`."""
    scored = [{**it, "_score": round(score_item(it), 4)} for it in items]
    scored.sort(key=lambda it: it["_score"], reverse=True)
    return scored[:limit] if limit else scored

    The reviewed source tree did not include the exported weight file. The loader supports a trained artifact, but that support alone does not establish what a deployed instance loaded. The model label is derived from a version string; it is not a training record.

    What the score means

    Take a simplified example with bias −1 and weights 2 for followed team, 1 for recency, and 1 for importance. A recent, important Owls story with features 1, 1, and 1 has a raw score of 3. An old unrelated item with features 0, 0, and 0.2 scores −0.8. The first ranks higher. These weights illustrate the mechanism; they are not the project’s fitted parameters.

    The sigmoid preserves that ordering while mapping the values into 0–1. It does not establish a click probability. Such an interpretation would need outcome data and calibration checks.

    The actual recency feature is exp(−max(age_days, 0)/7). It equals 1 today and about 0.368 at seven days. Seven days is the decay time constant, not the half-life; the half-life is about 4.85 days. Future dates are clamped to age zero, with upcoming status represented separately.

    A small linear scorer is cheap and interpretable. Its limitations are also visible. rank_items rounds to four decimal places before sorting, which can create ties and preserve input order. Candidate coverage remains an upstream limit: no weight adjustment can rank an Owls game that never entered the candidate list.

    Learning from clicks would introduce another complication. The old ranking determines which items get exposure, so a heavily clicked item may simply have been shown more often. Synthetic labels generated from hand-set weights would only teach those same preferences back to a model.

    Saved newsletter issues can use expiring share tokens. That stored artifact is distinct from a new personalized request. Its identity should remain tied to the selected issue, rather than being confused with the current viewer’s preferences.

    Small implementation choices affect ordering

    The magnitude feature is clamped to the interval from zero to one. This prevents an unusually large raw value from dominating the weighted sum, but also makes every value above one indistinguishable. Its usefulness depends on how candidate construction assigns magnitude before the scorer sees it.

    Missing recency defaults to three days. That keeps the function runnable, but assigns a particular freshness value to an item whose age may be unknown. Meanwhile, the once-per-process weight cache means a changed file is not necessarily reflected by an already running process. Reproducible ranking therefore depends on both feature preparation and the loaded weight version, not just the equation printed in the scorer.

    Where the memory savings come from

    For a weight matrix W, LoRA freezes the base and learns an update ΔW = (α/r)BA. A maps the input into rank r; B expands it to the output width. This constrains the update while reducing the number of trainable parameters.

    A 4,096-by-4,096 matrix contains 16,777,216 parameters. With rank 16, its adapter contains 16×4,096 + 4,096×16 = 131,072 parameters, about 0.78% as many. The base matrix is still present. This is per-matrix arithmetic, not a claim that total training memory falls by the same percentage.

    The recipe sets rank 16, alpha 32, and dropout 0.05. The usual alpha/r multiplier is therefore 2. It targets attention projections and MLP projections, allowing changes to both information mixing and per-token transformations. Those module names must exist in the selected base architecture.

    Defaults include three epochs, learning rate 2e−4, a microbatch of one, 16 accumulation steps, a 4,096-token cap, bf16, and gradient checkpointing. On one device, the nominal effective batch is 16 examples per optimizer update, apart from partial final accumulation.

    Accumulation limits how many examples’ activations coexist. It does not solve the memory cost of one long example. Checkpointing addresses that cost differently: it stores fewer intermediate activations and recomputes them during backward passes, trading compute for memory.

    The optional QLoRA path loads frozen base weights in four-bit NF4 with double quantization and bf16 compute. It does not make every tensor four-bit. Adapter gradients, optimizer state, activations, and temporary workspaces still consume memory. A capacity claim therefore depends on the actual base model and sequence lengths.

    What the split and trainer configuration establish

    The random 95/5 split is reproducible at the record level. It does not group by game. Multiple drafts of the same game can land on both sides, allowing validation to reward familiarity with facts that training already exposed.

    The trainer receives a held-out dataset, but the shown configuration does not explicitly select an evaluation cadence or best-model policy. It also supplies a serialized conversation without showing an explicit assistant-only loss mask. The exact behavior of those details depends on the training-library version and configuration; the excerpt alone does not settle them.

    The 4,096-token limit creates another practical question: does the full target answer survive truncation? A long source fact sheet can consume the available sequence before the useful writing target ends. Dataset formatting and length checks are therefore part of the training behavior, not just preprocessing convenience.

    The script saves the adapter and tokenizer after training and prints deployment instructions. That is a recipe for producing an artifact, not evidence that this article executed it. A deployed writer additionally needs a compatible base revision, adapter, tokenizer, prompt format, and application configuration.

    A traced request is the strongest way to distinguish a successful trained route from a silent general-model fallback. Improvement requires a separate comparison on the same held-out games. Neither a saved directory nor a responsive endpoint supplies that comparison.

    Adaptation has a scope as well as a parameter count

    The low-rank update can change only a constrained family of transformations for each adapted matrix. A small rank makes optimization and storage cheaper, but it can limit the changes available to the task. Increasing rank adds capacity and trainable state; it does not independently improve the quality of teacher targets or eliminate leakage.

    Targeting both attention and MLP projections gives this recipe more places to adapt than targeting attention alone. It also adds adapter parameters across more matrices. The 0.78% example is useful for understanding one matrix, while an actual memory budget must count every targeted layer, optimizer state, activations, and the frozen base.

    Chat formatting matters for a different reason. The model sees role separators and special tokens alongside the sports facts. A serving prompt that uses different formatting can present a task unlike the training examples. Keeping tokenizer and prompt conventions compatible is part of deploying the adapter, even when its weights load successfully.

    Individual atomic commands do not make an atomic award

    Two overlapping requests can both read an unresolved pick. Each can then mark it resolved and award points. Serial retries usually return early, but that does not protect the interval between the initial read and the write.

    A crash creates the opposite failure. If it occurs after the resolved marker but before the counter updates, a retry sees the marker and returns without completing the award. Moving the marker after the counters would merely exchange this failure window for another duplication risk.

    The docstring’s “exactly once” language is stronger than the code. There is no enclosing transaction or Lua script in the excerpt. The race and crash windows are source-level findings; no production incident was reproduced for this article.

    Broad exception handling returns zero, which can make failed persistence look like a legitimate no-op. That complicates reconciliation: the caller may not know whether no points were due, the pick was already resolved, or storage failed.

    Redis’s structures are a good fit for compact state and score ranking. The missing guarantee concerns the complete logical transition across those structures. Authentication is a separate concern: even a perfectly atomic award would not prove that a client-supplied identifier belongs to the person presenting it.

    The grounding filter checks vocabulary, not relationships

    The training filter compares names and numbers in a draft with tokens extracted from serialized facts. It is an inexpensive screen for obvious inventions. Its implementation also shows exactly what can pass.

    training/grounding.py · lines 41–62 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def check(facts: dict, target: str) -> tuple[bool, list[str]]:
    blob = _blob(facts)
    ok_numbers = _facts_numbers(blob)
    ok_tokens = _facts_tokens(blob)
    reasons: list[str] = []

    for num in _NUM.findall(target):
        n = int(num)
        if n < 13:              # small counts, quarters, list markers: ignore
            continue
        if 1900 <= n <= 2099:   # a year, not a stat
            continue
        if num not in ok_numbers:
            reasons.append(f"invented number {num}")

    for first, last in _NAME.findall(target):
        # A person reference is grounded if the surname appears in the facts.
        if last.lower() not in ok_tokens and first.lower() not in ok_tokens:
            reasons.append(f"invented name {first} {last}")

    # Allow a tiny amount of noise (e.g. an idiom that reads like a name).
    return (len(reasons) <= 1, reasons)

    Numbers below 13 and values in the year range are ignored. A detected two-word name passes if either token appears in the available token set. The function accepts a draft with up to one detected violation.

    Suppose the facts say Player A scored 30 and Player B scored 12. “Player B scored 30” uses known names and a known number, yet assigns the statistic to the wrong person. Vocabulary membership cannot catch that relationship error. A fabricated 12-point statistic bypasses the numeric threshold altogether.

    The filter is therefore a weak prefilter for teacher drafts, not a factuality guarantee. A false acceptance can enter the training set. A false rejection can remove a useful example. Measuring only the fraction of drafts accepted tells us neither error rate.

    Separate the questions being measured

    Selection quality asks whether the important events reached the fact sheet. Writing quality asks whether the output accurately expresses that sheet. Ranking quality asks whether relevant items appear near the top. Playback quality asks whether the right media and speech appear together. Persistence correctness asks whether the same logical award changes state once.

    For event selection, precision and recall can distinguish irrelevant inclusions from missed moments. In a toy case with 20 true scoring plays, finding 18 and adding two false positives produces 90% for both metrics. Their denominators happen to match in this example; they answer different questions.

    For ranked feeds, NDCG rewards relevant items near the top relative to the best ordering of the same labeled candidates. A result is only interpretable alongside its candidate set and relevance judgments. It does not independently prove user satisfaction.

    For generated text, adversarial cases can preserve every name and number while swapping their relationships. Temporal substitutions are equally useful: a tying basket becomes a winning basket, or a halftime lead becomes the final result. These expose errors that lexical checks miss.

    The source inspection did not establish a production factuality rate, learned-ranker uplift, cache hit rate, or p95 latency. Those remain measurement tasks. The existing checks describe mechanisms and limitations, not benchmark results.

    A useful comparison holds the evidence fixed

    Imagine evaluating a base writer on a sparse fact sheet and an adapted writer on a later, more complete provider response. Better coverage in the second output could come entirely from the extra evidence. Freezing the game snapshot and selected events removes that confound. The remaining comparison can focus on how each writer uses the same input.

    Fallbacks also belong in the result. Reporting only successful model generations excludes the requests that fans experience when a provider fails or returns unusable structure. A product-level report needs the frequency and quality of each delivered route, alongside conditional quality when a particular writer succeeds.

    Why more API workers do not solve every bottleneck

    The backend coordinates upstream sports requests, hosted writing calls, cache operations, and shared state. Adding application replicas increases its ability to initiate work, but does not increase the sports provider’s quota or the writer’s serving capacity.

    The local recap helpers show the narrow scope of their locks. They protect cache access and eviction. Expensive generation happens elsewhere, which leaves the concurrent-miss behavior described in the cache chapter.

    More workers also mean more independent local caches. Redis can share completed results, but simultaneous misses still need coordination. This distinction matters most when many fans open the same newly finished game.

    Blocking work inside an asynchronous route

    The async generation endpoint directly calls the synchronous recap function. While that function performs blocking network or model calls, it can occupy the event loop. The route’s async declaration alone does not make the work yield to other requests.

    The general-model helper also stores its last error in a module-level variable. Overlapping requests can overwrite that value before a fallback response reads it. The resulting diagnostic may describe another request’s failure.

    Both are concrete risks in the implementation. Neither establishes an observed latency distribution or failure rate. They identify what a load test should distinguish.

    A burst makes service time a capacity problem

    For an illustrative stable system, two uncached arrivals per second and ten seconds of average time in the system imply roughly 20 concurrent jobs. If a dependency can complete only one job per second, that arrival rate cannot remain stable: the queue grows unless work is deduplicated, delayed, rejected, or replaced by a fallback.

    Same-game and many-game bursts exercise different limits. The first tests reuse and duplicate work. The second tests provider and writer throughput. Combining them into one average response time would hide the cause of the slowdown.

    The current application calls hosted writers, so buying a GPU is not automatically the next optimization. Repeated source calls, a blocking event loop, or slow sequential fallback may dominate. The architecture needs timing by stage before a serving redesign can be justified.

    Latency breakdowns also determine whether a cache improvement is meaningful. A warm recap hit may bypass both ESPN and the writer, while a source-cache hit can still require a full model call. Treating both as simply “cached” hides very different costs. Queue time, source-fetch time, and generation time need separate attribution.

    Likewise, a sequential fallback can make a successful final response unusually slow. Its total time includes failed earlier attempts. Measuring only the provider that eventually returned text would miss that delay and point optimization at the wrong stage.

    What I would change next

    The existing boundaries are useful: provider parsing stays in one adapter, selection precedes writing, and fallback routes keep the product usable. I would keep that structure. The next work is to make its guarantees explicit and testable. The changes below are proposals, not features implemented by this article rewrite.

    Preserve a reproducible input

    I would retain provider event IDs, source timestamps, and a normalized fact revision with each generated artifact. Status would carry completion indicators and source disagreement rather than relying only on score presence. Fetch failures would remain distinguishable from valid empty results.

    Frozen provider fixtures would cover missing scores, malformed IDs, corrected results, duplicate events, and status disagreement. They would make it possible to reproduce a content bug after the live endpoint changes.

    Fix selection before changing the writer

    I would reserve slots for required late events, remove their stable IDs from the remaining pool, and fill the rest by relevance. Only the final chosen set would be sorted by period and clock. Tests would assert both the size limit and retention of required moments after every transformation.

    I would also remove unsupported tactical statements from deterministic templates and represent missing kick distance as unknown. A learned probability model would only replace the proxies after a held-out calibration comparison.

    Make cache reuse follow the input

    Output identity would include a fact fingerprint, prompt revision, and output kind, plus preference revision where relevant. This adds bookkeeping and still requires a way to discover corrections, but makes stale reuse explainable.

    A per-key in-flight future could collapse misses within one process. Shared leases or a job service would handle multiple processes. I would give temporary failures a short-lived state or circuit breaker instead of either hammering a failing writer or retaining degraded content for hours.

    Validate the broadcast and own its playback

    I would use schema-constrained generation where supported, followed by explicit validation of durations, speakers, and nonempty turns. Evidence IDs would connect speech to its event and clip. Actual audio completion would drive playback rather than a guessed duration alone.

    Each playback session would own its callbacks. An interruption would cancel the old narration and prevent a delayed callback from restarting the previous visual sequence. Provider routes would share a total deadline, with separate budgets for each attempted writer.

    Make one pick resolution one state transition

    A Redis atomic script or correctly designed optimistic transaction would check and award together. An alternative is an immutable award ledger with derived counters and reconciliation. The ledger costs more operational work, but makes corrections and repairs easier to audit.

    I would test simultaneous resolutions and inject failures at write boundaries. Corrected game results would need an explicit reversal or versioning policy. Storage failures would be visible to the caller, and valuable entitlements would require account authentication rather than a copied device identifier.

    Compare models on the same games

    Training splits would be grouped by game and separated in time. I would audit the teacher filter with relation-swapped examples, then compare template, base-model, and adapted-model output on the same frozen facts. Factuality, accepted-output coverage, structure, latency, and cost would be reported separately.

    The ranker would sort full-precision scores and round only for display. A learned version would be compared against recency and popularity baselines using an explicit relevance signal. Training logs would record the data split, loss behavior, adapter revision, and serving compatibility.

    Measure the work that remains

    I would move blocking calls off the event loop, return errors as request-local values, and bound concurrency to dependency capacity. Request traces would record source-fetch time, selected event IDs, cache layer, writer route, model revision, and fallback reason.

    Those records would answer a practical question: did a bad experience come from missing data, selection, writing, stale reuse, or delivery? Once that is measurable, a stronger model can be evaluated as one targeted change rather than treated as a cure for the whole system.
