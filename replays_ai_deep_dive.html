    Replays AI: building the story around the game

    I wanted a fan to understand the game they missed, not just read its score. Following one request through Replays shows how selection, writing, and delivery shape that story.

    Two-page cheatsheet · All three cheatsheets

    I start with the game the fan missed

    The score is 104–101. That tells me who won. It does not tell me why the final minute mattered.

    For Replays AI, I want to close that gap: take the record of a game and turn it into something a fan can catch up on, whether that is a recap, a short broadcast, or a personalized feed. The natural place to start seems to be the writer. Give a language model the data and ask for a good story.

    But imagine the fact sheet contains an early dunk and omits the final defensive stop. The model can write beautifully about the dunk. It cannot explain the finish from evidence it never received. The first editorial decision has already happened in the code that selected the plays.

    That is the thread I follow through Replays. I begin with the provider’s record, turn it into consistent fields, decide which moments survive, and only then ask a writer to narrate them. Afterward, I still need to reuse the result safely and deliver it in a form the fan can actually watch or read.

    The Owls–Foxes game in this article is invented so I can follow one example across those boundaries. I use first person as a retrospective walkthrough of the implementation and its tradeoffs, not as an invented development diary. Source-level counterexamples are distinguished from measured incidents, and proposed changes remain in the closing section.

    01

    One game becomes several different products

    I do not want a new interpretation of the game every time I change the presentation. A recap, a newsletter, and a broadcast should begin with the same teams, scores, events, and available statistics.

    The implementation puts a React frontend in front of a FastAPI backend. The backend reads ESPN data on demand, normalizes it, and prepares facts for recaps, narrated reels, two-host broadcasts, and newsletters. Redis supplies shared storage when configured, including picks and leaderboard state.

    Fan chooses teams and players
  → browser requests a feed or game
  → backend obtains ESPN data
  → adapter converts it into consistent fields
  → rules select and analyze important events
  → writer or template produces a story
  → interface displays facts, media and source labels

    The outputs diverge after that shared beginning. A recap needs a coherent account of one game. A newsletter first needs to decide which games matter to this fan. A reel needs an existing clip and enough time to speak over it. A broadcast needs turns that a player can schedule.

    That distinction is why I keep selection separate from writing. Changing the prose should not silently change which games enter a feed. Changing a provider parser should not require rewriting every prompt. If the score is wrong in several views, the common adapter is a more useful starting point than four separate generation calls.

    The staged design also gives the product a fallback. A known result can still become deterministic prose if a writer fails. Newsletter and broadcast routes can try a configured trained writer, then a general model, then a template.

    There is a cost to sharing the inputs: updates have several consequences. A corrected score can invalidate a recap and a broadcast. A preference change affects a newsletter without changing the game. A missing video breaks a reel even if its text remains accurate. I cannot describe all of these with one undifferentiated cache policy.

    The README documents conditional trained-model routes. I keep that separate from proof that a trained checkpoint handled a particular request. As I follow the example, the selected route matters just as much as the architecture diagram: it tells me what actually produced the fan’s experience.

    02

    I follow the first request for a finished game

    Suppose a fan opens the Harbor Owls’ 104–101 win over the Valley Foxes. The browser sends the game ID. Before generating anything, the backend checks its local memo and shared recap cache.

    For this first request, assume both miss. The backend fetches the game and summary, then extracts teams, scores, status, and identifiers from the provider’s nested response. Here is a deliberately simplified record for the example, not the full production response schema.

    {
  "game_id": "illustrative-game",
  "status": "final",
  "home_team": "Harbor Owls",
  "away_team": "Valley Foxes",
  "home_score": 104,
  "away_score": 101
}

    Now I need the story inside that score. The recap builder extracts plays and leaders, selects a smaller event set, and packages a fact sheet. If that sheet includes the late three-pointer and the final stop, the writer has evidence for describing the finish. If it contains only the final score, the writer can report the result but has much less basis for explaining it.

    Generation can still fail. The template can then return the known facts, and the response records which route supplied the text. Whether the result should be cached is a separate decision from whether it can be displayed.

    This gives me three different ways to investigate a missing final stop. Perhaps ESPN did not supply it. Perhaps my selector discarded it. Perhaps the fan received a cached recap from an earlier snapshot. Those can produce similar-looking omissions on the page while requiring completely different fixes.

    The same distinction applies to the language. “The Owls won 104–101” follows from a verified final score. “They won in overtime” needs period information. “The final stop secured the win” needs the event sequence. I want the example to keep those requirements visible as the fact sheet moves through the system.

    To make that possible, I first need to understand exactly what the adapter preserves—and what it discards before the writer gets involved.

    03

    The provider record is not yet my game record

    The adapter in api/espn_public.py is where I contain ESPN-specific structure. Most reads happen on demand rather than through a permanent event warehouse. That keeps the application smaller, but it also means a recap depends on the response available when the fan requests it.

    _event_to_game rejects an event without a competition, both competitors, or an ID. For an accepted event, it emits consistent sport, date, status, team, and score fields. Every downstream consumer can use that shape instead of repeatedly navigating the provider’s nesting.

    A small conversion is doing important work: _score_value preserves a real zero and returns None for absent or invalid values. If I turned every missing score into zero, an incomplete record could look like a played game in which one team scored nothing.

    The adapter retains the provider identifier as external_id while converting id to an integer. That assumes numeric provider IDs. A nonnumeric value would fail here, before any prompt or model could matter.

    The fetch helper keys its cache by URL and query, uses a 12-second HTTP timeout, calls raise_for_status, and stores parsed JSON under a lock. Those choices bound waiting and reduce repeated calls. A successful HTTP response still does not validate every nested field.

    One source comment explains a particularly useful workaround: ESPN’s by-ID response can label a finished game “scheduled.” The recap builder therefore checks whether both scores exist before attempting a full model recap.

    I can see the immediate problem this solves. The Owls’ result should not be suppressed merely because the status string is wrong. But the workaround broadens the meaning of played: a live game also has two scores. The cache separately excludes an explicit live status. If the provider mislabels that too, neither check independently proves completion.

    The response’s ready state describes the recap artifact. It cannot repair uncertainty about whether the game has finished. That distinction needs to survive normalization.

    Rejecting malformed records centrally is also a tradeoff. If one competitor is missing, the rest of the application avoids repeatedly defending against that shape. But returning no normalized game loses the reason for rejection. An unknown ID, a malformed record, a valid empty result, and an upstream timeout are different outcomes that the present helpers do not always preserve distinctly.

    For the example, I now have a usable record. Before I turn it into a story, I need to explain the optimization that can bypass all this work on the next request: the cache.

    04

    The second fan should not pay for the first fan’s work

    Once the Owls recap exists, generating it again for every fan would waste time and provider capacity. The route checks an in-process memo and then Redis under recap:v2:{game_id}. A hit returns before fetching or writing.

    api/recaps.py · lines 382–406 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def get_recap(game_id: int):
    cache_key = f"recap:v2:{game_id}"
    cached = _memo_get(cache_key) or cache_get(cache_key)
    if cached:
        return cached

    resolved_game = fetch_espn_game_by_id(game_id)
    resolved_summary = fetch_espn_summary_by_id(game_id)
    if not resolved_game or not resolved_summary:
        raise HTTPException(status_code=404, detail="Game not found")
    sport, game = resolved_game
    _, summary = resolved_summary

    result = _build_recap(game_id, sport, game, summary)
    settings = get_settings()
    llm_configured = bool(settings.anthropic_api_key or settings.openai_api_key)
    played = game.get("away_score") is not None and game.get("home_score") is not None
    # Cache played games (final/mislabeled), but not obviously-live ones whose
    # numbers keep changing. Never cache a fallback recap when an LLM is
    # configured — a transient provider error would pin the lesser recap.
    if played and game.get("status") != "live" and (result["generated_by"] == "llm" or not llm_configured):
        _memo_set(cache_key, result)
        cache_set(cache_key, result)
    return result

    The write condition is more selective than “cache every response.” Both scores must exist and status must not be live. If a general model is configured, the result must actually come from that model. A temporary provider failure can return a template without pinning that lower-quality fallback as the preferred recap.

    That is a choice I would preserve: let the next request try to recover the better route. The cost is repeated attempts during a sustained outage. Avoiding a stale fallback and limiting retry traffic are separate concerns.

    The local memo lasts six hours and belongs to one Python process. Redis can share completed results across processes. The local size guard clears the dictionary once exceeded; it is not least-recently-used eviction.

    Now imagine two fans arrive just after the game ends. Request A checks the memo and misses. Before A finishes generation, request B checks and also misses. Both can call the writer.

    The lock protects individual dictionary operations, not the complete miss-to-generation interval. That avoids holding a global lock during a slow network call, which would delay unrelated games. It does not promise one generation for this game. I need per-key ownership of in-flight work for that stronger guarantee.

    There is a second problem even when reuse works perfectly. Suppose the first request stores the 104–101 recap, and the provider later corrects the result. The key still contains the same game ID and format version. It says nothing about which snapshot produced the text.

    The six-hour lifetime bounds local reuse; it does not verify freshness. A fingerprint of the facts would identify the input behind an artifact, but I would still need a fetch or invalidation signal to discover a correction. Cache identity and correction discovery cannot substitute for each other.

    So the implemented cache saves completed work and deliberately avoids retaining certain fallbacks. It does not yet coordinate simultaneous misses or invalidate output by source revision. With that boundary clear, I can return to the uncached request and inspect how the plays become evidence.

    05

    I make the play rules visible before calling them intelligence

    The event parser reads structured summaries and text cues such as “3pt,” “dunk,” “sack,” and “touchdown.” It does not watch the footage. That matters when I explain what Replays knows about the Owls’ late basket.

    Scout, Stat, Ref, and Predict are deterministic modules behind an analyze(ctx) → AgentRead interface. PlayContext contains current and previous scores, period, clock, description, and optional kick distance. Those inputs support useful calculations, but a made-shot description does not reveal whether a defender rotated late.

    The probability helpers make that scope particularly clear.

    api/play_analysis.py · lines 64–98 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    

# ── Transparent statistical proxies (heuristics, not learned) ───────────────────
def fg_make_probability(distance: Optional[int]) -> float:
    """Logistic approximation of NFL field-goal make rate by distance. Heuristic
    eyeballed to public make-rate curves (~99% at 20y, ~80% at 45y, ~50% at 53y)."""
    if not distance:
        return 0.0
    return 1.0 / (1.0 + math.exp((distance - 53.5) / 6.5))


def seconds_remaining(period: int, clock: Optional[str], sport: str) -> int:
    quarter = 15 * 60 if sport.upper() == "NFL" else 12 * 60
    in_quarter = 0
    if clock and ":" in clock:
        try:
            mm, ss = (int(x) for x in clock.split(":")[:2])
            in_quarter = mm * 60 + ss
        except ValueError:
            in_quarter = 0
    return max(0, (4 - min(period, 4)) * quarter + in_quarter)


def win_probability(margin: int, secs_left: int, sport: str) -> float:
    """Time-decayed logistic on score margin — a WP *proxy*, not a trained model.
    Margin matters more as time runs out."""
    total = (4 * 15 * 60) if sport.upper() == "NFL" else (4 * 12 * 60)
    frac_left = max(0.02, secs_left / total)
    scale = 7.0 * math.sqrt(frac_left)
    return 1.0 / (1.0 + math.exp(-margin / max(0.5, scale)))


_POINTS = {"touchdown": 7, "field_goal": 3, "safety": 2}

    For a field goal, the chosen curve has midpoint 53.5 yards and scale 6.5. At the midpoint the exponent is zero, so the output is 0.5. At 45 yards it is about 0.787; at 20 yards about 0.994. These are outputs of hand-set constants, not observed frequencies from an evaluation.

    Multiplying the 45-yard value by three gives about 2.36 points. That is only the kick reward under this proxy. It leaves out the field position after a miss, returns, penalties, and the alternatives to kicking. I cannot turn it into a complete strategic value by giving the number a more confident label.

    The win proxy encodes another understandable idea: the same lead matters more when less time remains. It divides score margin by a scale that shrinks with the square root of remaining regulation time. A three-point lead at scale seven gives about 0.606. Near the end, the two-percent time floor gives a scale around 0.990 and an output around 0.954.

    Possession, team strength, and timeouts are absent. The function also has no separately learned overtime model. A displayed 0.8 is therefore a proxy score, not an empirically calibrated 80% winning chance.

    Even the clock parser participates in that result. It uses 15-minute NFL quarters and 12 minutes otherwise. An NFL third quarter at 5:00 becomes 1,200 seconds remaining in regulation. A malformed clock falls back to zero within the quarter, making the same lead appear more secure. Periods beyond four are clamped in the regulation calculation.

    Some deterministic prose goes further than its inputs justify. Scout templates can describe a late defender or a winning rush matchup without visual evidence. StatAgent can substitute two or three points when the observed score change is zero, which deserves scrutiny for misses. Missing kick distance returns 0.0, collapsing “unknown” into “impossible.”

    I do not need a larger model to see these failures. I can compare each output with the fields available to the rule. The common interface makes future replacement possible; first I want the present calculations and claims to mean what they say. The next stage introduces a different kind of judgment: which of these events deserves space in the recap.

    06

    The final slice can erase the finish

    The recap builder extracts up to 300 plays, gathers leaders, and prepares a smaller fact sheet. I cannot send every event indiscriminately and expect a compact story, so _key_plays selects a subset.

    The weights encode an editorial preference: touchdowns receive 10, dunks 9, and three-pointers 8, while descriptions containing “miss” are penalized. This favors recognizable highlights. The awkward case is our final stop—a routine event can explain the result better than an early spectacular play.

    The implementation tries to account for the finish by adding late events to the highest-weight set.

    api/recaps.py · lines 180–189 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def _key_plays(plays: list[dict], limit: int = 16) -> list[dict]:
    interesting = [play for play in plays if play.get("play_type") not in (None, "other")]
    if not interesting:
        interesting = [play for play in plays if play.get("description")]
    if len(interesting) <= limit:
        return interesting
    late = interesting[-max(4, limit // 3):]
    best = sorted(interesting, key=lambda play: (-_play_weight(play), play.get("id") or 0))[:limit]
    selected = {id(play): play for play in best + late}
    return sorted(selected.values(), key=lambda play: play.get("id") or 0)[:limit]

    Here is the counterexample I use to read that code. With a limit of 16, the late set contains five plays. Suppose the best 16 weighted plays all occurred earlier, and none overlaps the late five. The union has 21 entries. If IDs increase with time, sorting by ID and taking the first 16 drops all five late plays.

    The intention to preserve the finish is visible in late. The final slice can undo it. This is a code-level failure case, not a measured production frequency. It also explains why a better prompt cannot solve every incomplete recap: the missing stop never reaches the writer.

    The diagram shows the separation I would introduce: choose membership, then order the chosen set for presentation. Its reserved-event policy is a proposed replacement, not the current algorithm.

    Two smaller details matter. Deduplication uses Python object identity, so separately parsed dictionaries for the same provider event can both survive. Sorting by event ID also assumes that ID order matches chronology. Stable provider identity and period/clock order would express different properties more directly.

    After selection, _game_facts packages scores, period totals, lead changes, key plays, and available leaders. The general-model route tries configured Anthropic models and can then try OpenAI. If it obtains no usable text, deterministic prose supplies the fallback. generated_by records the successful route.

    That label keeps the evaluation honest. A template delivered during a provider failure belongs to the product experience, but it is not a sample of an adapted writer’s output. Similarly, cv_classifications counts selected plays in this route; its name does not establish that computer vision inspected clips.

    Return to the Owls’ late three-pointer. If the fact sheet includes the shot but omits the following possession, I can support the score change. I cannot automatically support “the shot secured the win.” The selector determines that limit before the writer chooses a single word. Once I have a defensible story, turning it into a broadcast creates another set of constraints.

    07

    A good paragraph still needs a playback plan

    A fan watching a reel needs more than the recap read aloud. Replays attaches existing video URLs and scene metadata; it does not generate the original sports footage. Broadcasts add alternating hosts and a sequence of turns. Browser speech synthesis narrates them, while speech recognition is used separately for follow-up input.

    The requested tiers use 12, 26, or 44 turns for two-, five-, and ten-minute programs. Each turn has a host, text, scene type, and duration hint. That gives the player something it can schedule.

    Illustrative turn:
{
  "host": "play",
  "text": "The Owls finish with a 104–101 win.",
  "scene_type": "title",
  "duration_hint": 8
}

    The hint is where writing meets time. At 150 words per minute, a 45-word turn needs about 18 seconds. An eight-second clip cannot hold it without shorter narration, longer visuals, or a different scene. A valid sentence can therefore be a bad playback unit.

    The parser tries to recover useful work from imperfect generation. _extract_turns first parses a bracketed JSON array, then attempts to salvage complete flat objects with a regular expression. _clean_turns normalizes host and scene values, cuts text to 400 characters, and clamps duration hints to 4–20 seconds.

    api/broadcast.py · lines 136–158 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def _clean_turns(raw: str) -> list[dict] | None:
    """Parse and normalize the model's turn array into the player's DTO shape."""
    turns = _extract_turns(raw)
    if not turns:
        return None
    cleaned = []
    for t in turns:
        if not isinstance(t, dict):
            continue
        host = str(t.get("host", "play"))
        if host not in ("play", "analyst"):
            host = "play"
        scene = str(t.get("scene_type", "moment"))
        if scene not in ("title", "moment", "stat", "run", "verdict"):
            scene = "moment"
        cleaned.append({
            "host": host,
            "text": str(t.get("text", ""))[:400],
            "scene_type": scene,
            "duration_hint": max(4, min(20, int(t.get("duration_hint", 8)))),
        })
    return cleaned if cleaned else None

    Salvage can preserve finished turns when a long response stops early. It also leaves new failure modes. Nested objects and braces inside strings complicate regex parsing. An invalid duration can fail during integer conversion. A character cut can remove a sentence ending—or the qualification that made the sentence accurate.

    Even well-formed turns can contain empty speech or tactical claims unsupported by the fact sheet. An analyst voice does not gain evidence merely by having a different role. Two hosts sharing one record are still drawing from the same source.

    The fallback chain is sequential. The endpoint submits the trained-writer call to a one-worker executor and immediately waits. Only if that fails to produce usable turns does it try the general model, followed by the template.

    For a single game, I can now see the path from facts to playback. A personalized newsletter adds a question that comes even earlier: why did this game make the list?

    08

    Before writing the newsletter, I choose what belongs in it

    The Owls’ win may be the most important item for one fan and irrelevant to another. I want that choice to be inspectable before it becomes prose, so the newsletter ranks candidate items separately from writing them.

    The scorer uses followed-team and followed-player indicators, recency, clipped magnitude, and an upcoming-event flag. It adds weighted features to a bias and applies sigmoid. The weight loader is cached once per process and falls back to heuristic-v1 if the JSON artifact is absent or invalid.

    api/curation.py · lines 60–82 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def _features(item: dict) -> dict:
    recency_days = float(item.get("recency_days", 3.0))
    return {
        "followed_team": 1.0 if item.get("followed_team") else 0.0,
        "followed_player": 1.0 if item.get("followed_player") else 0.0,
        "recency": math.exp(-max(0.0, recency_days) / 7.0),  # 1.0 today, decays weekly
        "magnitude": min(1.0, max(0.0, float(item.get("magnitude", 0.0)))),
        "upcoming": 1.0 if item.get("upcoming") else 0.0,
    }


def score_item(item: dict) -> float:
    w = _weights()
    feats = _features(item)
    z = float(w.get("bias", 0.0)) + sum(w["weights"].get(k, 0.0) * v for k, v in feats.items())
    return 1.0 / (1.0 + math.exp(-z))


def rank_items(items: list[dict], limit: int | None = None) -> list[dict]:
    """Return items sorted by learned relevance, each annotated with `_score`."""
    scored = [{**it, "_score": round(score_item(it), 4)} for it in items]
    scored.sort(key=lambda it: it["_score"], reverse=True)
    return scored[:limit] if limit else scored

    A toy example makes the ranking concrete. With bias −1 and weights 2 for followed team, 1 for recency, and 1 for importance, a recent, important Owls item with all three features set to one scores 3 before sigmoid. An old, unrelated item with importance 0.2 scores −0.8. The ordering is easy to explain. These illustrative weights are not claimed as fitted project parameters.

    Sigmoid preserves that order while putting scores between zero and one. It does not establish a click probability. I would need outcome data and calibration before giving it that interpretation.

    The recency feature is exp(−max(age_days, 0)/7). Today it is one; at seven days it is about 0.368. Seven is the decay time constant, not the half-life, which is about 4.85 days. Future dates are treated as age zero, while the separate upcoming flag distinguishes their status.

    Small defaults shape the final order. Unknown recency becomes three days. Magnitude is clipped to zero through one, preventing an extreme value from dominating but collapsing every value above one. The once-per-process weight cache also means a changed artifact is not necessarily loaded by a running process.

    There is a particularly avoidable loss of information in rank_items: it rounds scores to four decimal places before sorting. Close scores can become ties that preserve input order. I would sort with full precision and round for display.

    The inspected source tree did not include the exported weights. Support for a trained file and a version-derived model label do not establish what a deployed instance loaded. That is why I keep the feature equation, loaded artifact, and training evidence separate.

    Learning from clicks would bring another complication: the previous ranking decides which items receive exposure. More clicks may reflect more opportunities to click. Synthetic labels generated from hand-set weights would simply teach the same preferences back to a model.

    Finally, no ranking function can promote an Owls game missing from the candidate set. Saved newsletter issues, including those with expiring share tokens, are also distinct artifacts from a freshly personalized request. The story the fan receives depends on candidate construction, ranking, and saved-issue identity before a writer gets involved. Only after those inputs are stable does it make sense to ask whether adapting the writer improves its output.

    09

    I can adapt the writer without training every weight

    The repository includes a training path for a smaller writer using teacher-generated drafts paired with game facts. The appeal is to move repeated task behavior into an adapted model. The risk is equally direct: any accepted teacher error becomes part of what the student is asked to imitate.

    The script serializes system, user, and assistant messages with the base tokenizer’s chat template, reserves five percent of records using seed 7, and configures supervised training with LoRA.

    LoRA freezes a base matrix W and learns ΔW = (α/r)BA. Instead of updating every entry, A maps into a low-dimensional rank and B maps back to the output width.

    For a 4,096-by-4,096 matrix, full weights number 16,777,216. At rank 16, the two adapter matrices contain 16×4,096 + 4,096×16 = 131,072 parameters, about 0.78% as many. I still need the base matrix in memory. That percentage describes one matrix’s trainable update, not the reduction in total GPU memory.

    The recipe uses rank 16, alpha 32, and dropout 0.05, giving the usual alpha/r multiplier of two. It targets attention projections and MLP projections, so adaptation can affect both information mixing and per-token transformations. Those module names must exist in the selected base architecture.

    The defaults are three epochs, learning rate 2e−4, microbatch one, 16 accumulation steps, a 4,096-token cap, bf16, and gradient checkpointing. On one device, the nominal effective batch is 16 examples per optimizer update, aside from a partial final accumulation.

    These settings address different memory costs. Accumulation avoids holding activations for the whole effective batch at once. It does not make one very long example fit. Checkpointing saves fewer intermediate activations and recomputes them during backward passes, trading more work for less storage.

    The optional QLoRA path stores frozen base weights in four-bit NF4 with double quantization and bf16 compute. Adapter gradients, optimizer state, activations, and workspaces are not all four-bit. I would budget those separately before making a capacity claim.

    The data split is the more consequential limitation for deciding whether the recipe works. A random record-level 95/5 split can place two drafts of the same game on opposite sides. A validation improvement can then reflect familiarity with game facts. I would want game-grouped, time-separated data for a stronger comparison.

    The trainer receives a held-out dataset, but the excerpt does not explicitly configure an evaluation cadence or best-model policy. It also does not show an explicit assistant-only loss mask. I would inspect the installed library behavior and configuration before claiming either. The sequence cap needs inspection too: a long fact sheet can consume the available space before the target answer ends.

    After training, the script saves the adapter and tokenizer and prints deployment instructions. That is a reproducible recipe, not proof that this article ran it or that the deployed application used the artifact. Serving also requires a compatible base revision, tokenizer, chat format, and route configuration.

    Increasing rank gives the adapter more capacity, but cannot fix teacher mistakes or split leakage. To judge the adapted writer, I would freeze the facts and compare it with the template and base writer on the same games. Before that comparison, I need to inspect the filter that decides which teacher drafts enter training.

    The fan’s prediction introduces a different kind of correctness

    Writing is not the only stateful part of Replays. A fan can make a pick, and the final result can change profile counters and a leaderboard. Here the question is no longer whether the recap sounds right. It is whether one resolved pick produces one award.

    The browser stores an anonymous UUID and sends it as X-Device-Id. That provides continuity for a browser, not proof of account ownership. Clearing storage or switching browsers can create another identity.

    When Redis is configured, hashes hold picks and profile counters, and a sorted set holds leaderboard scores. The README describes storage operations as no-ops without REDIS_URL. Seeing a working page does not by itself prove persistence.

    The critical function reads a pick, checks its resolved marker, writes the resolved state, then updates counters and points.

    Imagine two requests resolving the same correct Owls pick. Both read it before either writes the marker. Both see “unresolved.” Both can then award points. Each Redis increment is atomic, but the logical operation spanning the read, check, and writes is not.

    Now consider a crash after the resolved marker is written but before points are incremented. A retry reads “resolved” and returns. The points can be lost. Moving the marker after the counters merely creates a different window for duplication.

    This is why I do not equate a comment promising “exactly once” with an implementation guarantee. The excerpt has no enclosing transaction or Lua script. The race and crash windows follow from the sequence of operations; I am not claiming a reproduced production incident.

    Broad exception handling returns zero, which introduces ambiguity for the caller. Zero can mean no award was due, the pick was already resolved, or persistence failed. That makes repair harder because the response no longer identifies the state transition that failed.

    Redis remains a reasonable fit for compact fan state and ranked scores. The missing guarantee is about the complete award across those structures. Authentication is separate again: making an award atomic would not prove that the person presenting a device ID owns it.

    This part of the product sharpened the distinction I use throughout the article. A component can work locally—an atomic increment, a valid code, a fluent sentence—while the larger transition remains wrong. The training filter shows the same issue in another form.

    A draft can use every right number and still be wrong

    Before a teacher draft becomes a training example, training/grounding.py compares its names and numbers with tokens from the serialized facts. That is a cheap way to catch some obvious inventions. I need to read the acceptance rule to know what it actually excludes.

    training/grounding.py · lines 41–62 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

    def check(facts: dict, target: str) -> tuple[bool, list[str]]:
    blob = _blob(facts)
    ok_numbers = _facts_numbers(blob)
    ok_tokens = _facts_tokens(blob)
    reasons: list[str] = []

    for num in _NUM.findall(target):
        n = int(num)
        if n < 13:              # small counts, quarters, list markers: ignore
            continue
        if 1900 <= n <= 2099:   # a year, not a stat
            continue
        if num not in ok_numbers:
            reasons.append(f"invented number {num}")

    for first, last in _NAME.findall(target):
        # A person reference is grounded if the surname appears in the facts.
        if last.lower() not in ok_tokens and first.lower() not in ok_tokens:
            reasons.append(f"invented name {first} {last}")

    # Allow a tiny amount of noise (e.g. an idiom that reads like a name).
    return (len(reasons) <= 1, reasons)

    Numbers below 13 and values in the year range are ignored. A detected two-word name passes if either token appears in the facts. The function accepts up to one detected violation.

    Now give it facts saying Player A scored 30 and Player B scored 12. “Player B scored 30” contains an available player and an available number, but attaches them incorrectly. A fabricated 12-point statistic can bypass the numeric threshold entirely. Vocabulary membership is not relationship validation.

    That makes this a prefilter for teacher drafts, not a factuality guarantee. A false acceptance teaches the student an error. A false rejection removes useful material. The fraction accepted cannot tell me either rate without labeled inspection.

    I would also separate the questions asked of each stage. Event selection needs to retain important moments without filling the sheet with irrelevant ones. In a toy case with 20 true scoring plays, retrieving 18 plus two false positives gives 90% precision and 90% recall. Their equality here is incidental; one asks about selected items, the other about required items.

    Feed ranking needs relevance judgments and a defined candidate set. NDCG rewards relevant items appearing early relative to the ideal order of those candidates. It does not directly establish user satisfaction.

    Writing needs adversarial examples that keep the vocabulary but change the claim. Swapping player-stat relationships, changing a tying basket to a winning basket, or presenting a halftime lead as final would expose weaknesses that the current lexical screen misses. Playback and points persistence require their own checks rather than being folded into a writing score.

    The comparison also needs fixed evidence. If I give the base writer an early sparse snapshot and the adapted writer a later complete one, better coverage may come from the extra facts. Freezing the game and selected events lets me isolate how each writer uses the same input.

    Fallbacks belong in the product-level result. Measuring only successful generations omits the requests that delivered templates or failed structure. I would report route frequency alongside quality conditional on each route.

    The source inspection does not establish a production factuality rate, learned-ranker uplift, cache hit rate, or p95 latency. Those are still measurement tasks. The mechanisms tell me where to look; they do not supply results that were never collected. The last technical boundary is whether the serving path can keep delivering those mechanisms under load.

    More workers can repeat the same bottleneck

    Suppose many fans open the Owls game just after the final buzzer. Adding API workers sounds like the obvious capacity fix. But those workers still share the sports provider’s quota and the hosted writer’s capacity, and each has its own local memo.

    The cache helpers show the scope of coordination precisely.

    api/recaps.py · lines 24–36 · inspected revision a867fdab · selected excerpt; follow the source for surrounding code

        _recap_cache[key] = (time.monotonic(), value)

    The locks protect dictionary access. They do not span generation, so a burst can repeat the same uncached job across workers. Redis shares completed results, but does not by itself assign ownership while a result is still being built.

    The request path has another constraint: the async endpoint directly calls a synchronous recap function. Blocking network or model calls inside it can occupy the event loop. Writing async on the route does not make that work yield.

    Diagnostics have a related concurrency risk. The general-model helper keeps its last error in a module-level variable. Another request can overwrite it before a fallback response reads it. I could end up explaining the Owls fallback with an error from an unrelated game.

    These are code-level risks rather than measured latency claims. They tell me what to separate in a load test. Same-game bursts exercise duplicate work and reuse; many-game bursts exercise aggregate upstream throughput.

    For scale, consider an illustrative stable system receiving two uncached jobs per second with ten seconds of average time in the system. Little’s law implies about 20 concurrent jobs. If a dependency completes only one per second, that arrival rate cannot remain stable. Work must be delayed, rejected, deduplicated, or served through another route.

    “Cached” is too broad a measurement here. A warm recap hit can bypass both ESPN and writing. A source-cache hit can still incur a full generation call. Queue time, fetch time, and writer time need separate attribution.

    Sequential fallback adds another source of delay. A successful template or second provider may arrive only after earlier attempts timed out. Timing just the successful provider would hide much of what the fan waited for.

    The current architecture calls hosted writers, so buying a GPU is not automatically the next useful change. A blocking event loop, repeated source calls, or duplicated same-game jobs may dominate first. I would instrument those boundaries before redesigning serving around a bottleneck I have not measured.

    13

    What I would change after following the whole request

    The Owls example starts with a score and ends with much more than generated prose: selected events, a reusable recap, a playable broadcast, a ranked feed, and possibly an award. Following that path tells me where I would spend the next engineering effort.

    I would begin with reproducible inputs. Provider event IDs, source timestamps, and a normalized fact revision would travel with each artifact. Completion indicators and status disagreements would remain explicit. Frozen fixtures would cover corrected scores, malformed IDs, missing competitors, duplicates, and fetch failures so I could reproduce a bug after the live endpoint changed.

    Next I would repair selection before changing the writer. Required late events would receive reserved slots. Their stable IDs would be removed from the remaining pool, which would fill by relevance. Only the final set would be sorted by period and clock. Tests would assert the size limit and required-event retention after every transformation.

    I would also remove unsupported tactical language from deterministic templates and represent missing kick distance as unknown. A learned probability model would need a held-out calibration comparison before replacing the proxies.

    Cache reuse would follow the input revision, prompt revision, output kind, and preferences where relevant. I would separately define how corrections are discovered. Per-key in-flight work would collapse local misses; shared leases or a job service would handle multiple processes. Temporary failures would receive a short-lived state or circuit breaker so quality recovery did not require hammering a failing writer.

    For broadcasts, I would validate speaker, duration, and nonempty-turn structure explicitly. Evidence IDs would connect speech with an event and clip. Playback would use actual audio completion, and each session would own its callbacks so an old callback could not restart an interrupted sequence. Provider attempts would share a total deadline.

    Pick resolution would become one atomic transition, using a Redis script or a correctly designed optimistic transaction. An immutable award ledger with derived counters is another option if repair and correction justify the added machinery. I would test simultaneous resolutions and inject failures at write boundaries. Corrected results would need a reversal or versioning policy, and valuable entitlements would need account authentication.

    For training, I would group by game and separate in time. Relation-swapped examples would audit the teacher filter. Template, base, and adapted writers would receive the same frozen facts, with factuality, coverage, structure, latency, and cost reported separately. The ranker would sort full-precision scores and be compared with recency and popularity baselines using an explicit relevance signal.

    Finally, I would move blocking calls off the event loop, make errors request-local, and bound concurrency to dependency capacity. Traces would retain selected event IDs, cache layer, writer route, model revision, and fallback reason. Training records would identify the split, loss behavior, adapter, and serving format.

    These are proposed changes, not features added by this article. They all serve the original idea: help a fan understand the game they missed. A stronger writer may help, but I can only judge that improvement after the right events reach it and the resulting story survives the rest of the system.
