    Note 01

    The problem: useful sports stories from changing facts

    Question: How can a sports application give each fan a useful summary without inventing what happened?

    Raw sports data can contain scores, schedules, player statistics, hundreds of plays and links to clips. A fan usually wants a smaller answer: what happened, which moments mattered, and what is relevant to the teams they follow. Replays AI separates collecting facts, selecting relevant material and writing an explanation.

    An API is a defined way for programs to request information from another program. Replays reads sports data from ESPN endpoints. An endpoint is a particular address serving a particular kind of request, such as a game summary. These responses are structured data; they are not a language model’s recollection of a game.

    The frontend is the browser interface built with React. The backend is the Python application built with FastAPI that handles requests and organizes data. Redis is used when configured to store shared information and reusable results. Writing services turn selected facts into prose.

    Fan chooses teams and players
  → browser requests a feed or game
  → backend obtains ESPN data
  → adapter converts it into consistent fields
  → rules select and analyze important events
  → writer or template produces a story
  → interface displays facts, media and source labels

    The product has several outputs: a single-game recap, a narrated reel using real clips, a two-host broadcast, a personalized newsletter and prediction-game leaderboards. They share factual inputs but have different output requirements.

    Evidence boundary

    The checked project README describes live ESPN access, optional Redis and conditional trained-writer paths. It explicitly says general models, templates and heuristic ranking are used until trained models are available and configured. A supported path is not proof that a trained checkpoint served a particular request.

    Remember

    Sports facts come from the data source. The application selects and transforms them. A generated story must be evaluated for how faithfully it uses those facts.

    Note 02

    A complete recap request, using one imaginary game

    Illustration — invented teams, score and events

    A fan follows the Harbor Owls. The Owls finish a game against the Valley Foxes, winning 104–101. The fan opens the game page and requests a recap.

    1. Identify the request. The browser sends the game identifier. A game ID is a stable reference to that event; the backend should not guess the game from a team name alone.
    2. Look for reusable work. If an eligible, sufficiently fresh recap is already saved, the backend can return it. If not, it obtains the source facts.
    3. Read the source response. The backend requests teams, scores, status, plays and available leaders. A missing score means unknown, not zero.
    4. Normalize the data. Regardless of how the supplier nested its fields, the application produces an internal record with named fields such as home team, away team, score and game status.
    5. Select important moments. Suppose the event list contains a late three-pointer and a final defensive stop. Rules can choose these events for the recap while keeping their original descriptions and order.
    6. Build the fact sheet. The writer receives the final score, selected plays and any available player lines. It must not infer a player’s statistics if those statistics are missing.
    7. Write or fall back. A configured language model may write the recap. If it is unavailable, a deterministic template can state the known result and selected events.
    8. Return the story and its source. The response indicates which path generated the text. An eligible final-game result may be cached for later requests.
    {
  "game_id": "illustrative-game",
  "status": "final",
  "home_team": "Harbor Owls",
  "away_team": "Valley Foxes",
  "home_score": 104,
  "away_score": 101
}

    This is illustrative JSON: a text format with named keys and values. The quotation marks identify text values; the scores are numbers. This record is not a copy of the production API schema.

    If the writer says “The Owls won in overtime,” that is a factual claim requiring evidence. A close final score alone does not show overtime. Good writing is not a substitute for a supported fact sheet.

    Remember

    Follow the data through each boundary: request → source facts → normalized record → selected evidence → story. The first boundary where a fact changes unexpectedly is where debugging should begin.

    Note 03

    Ingestion and normalization: making outside data usable

    Question: Why not let every screen call ESPN and read its own fields?

    Because external formats can vary by sport and endpoint, and they can change. A data adapter sits between the supplier and the rest of the application. It translates source-specific responses into a consistent internal shape. When a supplier changes a field, the repair can be concentrated in one place.

    Ingestion means bringing external data into the system. It does not always mean permanently inserting it into a database. In the documented Replays path, many reads happen on demand: a request triggers a fetch, normalization and a response, with caches reducing repeated work.

    A schema specifies expected fields and types. For example, a score might be a number or explicitly absent; a game status should be one of the supported states. Checking the schema prevents an unexpected string or missing nested object from silently flowing into later arithmetic.

    Source situationCorrect interpretationDangerous shortcut
    Score is absentScore is unknown or not yet available.Replace it with zero and describe a shutout.
    Request times outThe data could not be obtained in time.Tell the fan that no games occurred.
    Valid empty scheduleNo matching scheduled games were returned.Assume the provider is down.
    Duplicate event IDInvestigate or deduplicate according to a defined rule.Count the same scoring play twice.

    A timeout stops waiting after a defined period. An HTTP 429 response means the service is limiting request volume. A successful HTTP response still needs content checks: the response might lack a score or contain a changed format.

    The original guide describes a 12-second upstream timeout, a short process-local cache and typed helper functions in api/espn_public.py. These implementation details explain the intended behavior; they are not measurements of supplier reliability.

    Keep enough provenance to trace an error

    Provenance means where information came from. Preserve the game ID, play ID when available, source description, game clock, period and fetch time. If the final score is corrected later, provenance helps identify which derived recaps need refreshing.

    Remember

    Normalization should make the format predictable while preserving uncertainty. It must not make missing facts look complete.

    Alternative and test. Add typed validation, explicit unavailable-versus-empty responses, provenance timestamps, and provider contract fixtures. Coalesce in-flight requests per key. If historical reproducibility matters, store immutable source snapshots rather than assuming live endpoints will return the same facts later.

    Note 04

    Caching: faster responses without pretending old data is new

    Question: Why save a result, and when should it expire?

    A cache keeps a reusable answer so the system can avoid repeating an expensive fetch or generation. A cache hit means a suitable stored answer was found. A cache miss means fresh work is needed.

    A time to live (TTL) is how long an entry remains eligible for reuse. The documented source-data cache uses a short lifetime, while the original guide describes a six-hour local recap memo for eligible completed games. Different information needs different freshness policies: a live score can change within seconds; a finished game’s summary changes less often but can still require correction.

    Two storage locations, two guarantees

    A process-local cache exists inside one running backend process. It is quick to access, but another process cannot automatically see it. When that process stops, its memory disappears. A shared cache in Redis can be consulted by multiple processes, which helps them reuse the same work.

    Serverless hosting starts and reuses managed processes as demand changes. A warm process may have cached results; a new process may not. Therefore, one successful local cache hit does not establish consistent caching across every user request.

    Illustration

    One hundred fans request the same finished game. If all requests see an empty cache at once, all may try to fetch and generate. This is a cache stampede. A proposed “singleflight” mechanism lets one request do the work while the others wait for that same result.

    A cache key identifies the saved answer. It should include the inputs that determine the answer: game, sport, content version, and personalization when relevant. Saving a personalized Owls recap under a generic game-only key could give another fan the wrong perspective.

    The original recap description includes an important fallback rule: if an LLM is configured but temporarily fails, do not freeze its template fallback in a long-lived cache as though that were the preferred final output. A temporary outage should not unnecessarily affect hours of later requests.

    Stale-while-revalidate is a possible design in which a labeled older answer is returned while a background job refreshes it. It helps availability but requires an explicit freshness contract. It is an improvement option here, not proof of an implemented production feature.

    Remember

    Cache hit rate measures reuse, not truth or freshness. A high hit rate can mean the system is efficiently serving outdated information.

    Note 05

    Play analysis: rules, features and the meaning of “agent”

    Question: Is assigning a play type necessarily machine learning?

    No. Classification means choosing a category. A programmer can write a rule that labels a description containing “interception” as an interception. A trained classifier learns decision settings from examples. Both classify; only the second requires learning.

    The original guide describes the play parser as text rules checking cues such as “3pt,” “dunk,” “sack” and “touchdown.” This is not the same as a computer-vision model reading video frames. It is also not proof that a historical vision-based system never existed; those are separate implementations requiring separate evidence.

    A feature is a usable value derived from input: score margin, time remaining, play type or whether a review was mentioned. A heuristic is a deliberately chosen rule of thumb. A heuristic can be sensible and useful without having been fitted to labeled examples.

    The Scout, Stat, Ref and Predict roles described in api/play_analysis.py are deterministic calculations. “Agent” names organize the outputs. They do not demonstrate four independently trained neural networks.

    Illustration

    A description contains “three-point shot,” and the home score rises from 101 to 104. A rule can assign a three-pointer category, calculate a three-point change and describe the score impact. It cannot conclude that the shot was unusually difficult unless that information is supplied or separately analyzed.

    A plausible probability is not a calibrated probability

    A heuristic can map lead and time remaining into a smooth number between 0 and 1. It may rise when a team leads late, which feels plausible. But calling 0.8 an 80% win probability requires testing whether similar historical cases actually win about 80% of the time.

    The original notes identify the displayed win-probability calculation as a proxy. That label matters. A chosen formula is not automatically a trained predictive model, and an attractive visualization is not an evaluation.

    When would learning be justified?

    Collect real descriptions with human-assigned play labels, identify where rules fail, and compare alternatives on games excluded from training. If a simple word-based classifier reliably fixes enough costly errors, it may justify the extra training and maintenance. The decision should follow evidence rather than the desire to use a more elaborate model.

# ── Transparent statistical proxies (heuristics, not learned) ───────────────────
def fg_make_probability(distance: Optional[int]) -> float:
    """Logistic approximation of NFL field-goal make rate by distance. Heuristic
    eyeballed to public make-rate curves (~99% at 20y, ~80% at 45y, ~50% at 53y)."""
    if not distance:
        return 0.0
    return 1.0 / (1.0 + math.exp((distance - 53.5) / 6.5))


def seconds_remaining(period: int, clock: Optional[str], sport: str) -> int:
    quarter = 15 * 60 if sport.upper() == "NFL" else 12 * 60
    in_quarter = 0
    if clock and ":" in clock:
        try:
            mm, ss = (int(x) for x in clock.split(":")[:2])
            in_quarter = mm * 60 + ss
        except ValueError:
            in_quarter = 0
    return max(0, (4 - min(period, 4)) * quarter + in_quarter)


def win_probability(margin: int, secs_left: int, sport: str) -> float:
    """Time-decayed logistic on score margin — a WP *proxy*, not a trained model.
    Margin matters more as time runs out."""
    total = (4 * 15 * 60) if sport.upper() == "NFL" else (4 * 12 * 60)
    frac_left = max(0.02, secs_left / total)
    scale = 7.0 * math.sqrt(frac_left)
    return 1.0 / (1.0 + math.exp(-margin / max(0.5, scale)))


_POINTS = {"touchdown": 7, "field_goal": 3, "safety": 2}

    Alternative and test. Return explicit unknown values; separate observed facts from tactical hypotheses. Add missed-shot, overtime, malformed-clock, and missing-distance fixtures.     Note 06

    Selecting evidence and generating the recap

    Question: Why not send every play to the writer?

    A long game record contains repeated and low-value information. Sending all of it increases input length and may distract from the events a recap should explain. Selection creates a smaller evidence set. Ranking orders candidates by a score, whether that score comes from rules or a learned model.

    A key-play selector may favor scoring events, lead changes or late-game moments. After selection, chronological order helps the writer explain the sequence accurately. A high-scoring event is not necessarily the decisive event, so selection quality should be compared with human editorial judgments.

    A prompt gives the language model its instructions and facts. Inference is the act of running an already trained model. The model converts the prompt into tokens—pieces of text—processes them, then generates more tokens. No new sports knowledge is validated merely because the next sentence sounds natural.

    What belongs in the fact sheet?

    • Teams, game status and verified scores.
    • Relevant period information and selected source play descriptions.
    • Player statistics only when those values were actually obtained.
    • Explicitly missing fields, rather than guessed replacements.

    The documented recap path tries configured Anthropic models, may try OpenAI, and can fall back to a deterministic data-based recap. Newsletter and broadcast paths have an additional conditional trained-model route. These paths should not be collapsed into a claim that every output uses the same engine.

    A deterministic template inserts supplied values into a known structure. For the imaginary game, it could say “The Harbor Owls defeated the Valley Foxes 104–101.” The prose is limited, but it can still deliver useful known facts when a writer is unavailable.

    A response field such as generated_by or source records which path ran. These labels help diagnose behavior and compare quality. A fallback should be honestly labeled even when its output reads well.

    Failure to test

    Remove a player’s points total from the input. If the generated recap still supplies a number, inspect whether it came from another valid source or was invented. Prompt instructions alone do not demonstrate factual reliability.

    Remember

    Selection errors remove important evidence before writing starts. Generation errors misuse or add to the selected evidence. Test both stages separately.

    def _key_plays(plays: list[dict], limit: int = 16) -> list[dict]:
    interesting = [play for play in plays if play.get("play_type") not in (None, "other")]
    if not interesting:
        interesting = [play for play in plays if play.get("description")]
    if len(interesting) <= limit:
        return interesting
    late = interesting[-max(4, limit // 3):]
    best = sorted(interesting, key=lambda play: (-_play_weight(play), play.get("id") or 0))[:limit]
    selected = {id(play): play for play in best + late}
    return sorted(selected.values(), key=lambda play: play.get("id") or 0)[:limit]

    Why this structure is useful. Compressing events lowers prompt length and gives the writer a manageable evidence set. Chronological presentation makes the story easier to follow. But selecting by entertainment weights is not the same as selecting by importance to the outcome.

    What the code reveals. The final sort-and-slice can discard the late plays the earlier step tried to retain when the union exceeds the limit. Sorting by ID assumes IDs track time.     Alternative and test. Reserve slots for late decisive moments before filling the remaining budget; use stable event IDs and explicit period/clock ordering.     Note 07

    Reels and broadcasts: connecting facts, clips and speech

    Question: What does the system generate, and what comes from existing media?

    The documented reels use real clip URLs obtained through the data source. The application selects clips, organizes scenes and produces narration or overlays. It is not generating the original game footage. Availability through an endpoint also does not by itself establish unrestricted rights to reuse a clip.

    An overlay is information drawn over a video, such as a score label. A timeline determines when scenes and narration appear. A correct number shown at the wrong moment can still mislead—for example, displaying the final score as if it were already known halfway through the game.

    Text to speech (TTS) turns written narration into audio. The described browser uses speech synthesis. Speech recognition converts spoken input into text for follow-up questions. These are different tasks, and browser support, interruption and playback timing need handling.

    Why broadcast output needs structure

    A two-host broadcast needs more than a paragraph. Each turn must identify who speaks, what they say and which scene it accompanies. JSON provides a machine-readable list that the player can follow.

    Illustrative turn:
{
  "host": "play",
  "text": "The Owls finish with a 104–101 win.",
  "scene_type": "title",
  "duration_hint": 8
}

    The original guide describes target turn counts of 12, 26 and 44 for two-, five- and ten-minute tiers. A turn count is a planning device; it does not guarantee exact audio duration because voices and speaking rates vary.

    A long model response can stop before its JSON is complete. The documented parser attempts to recover complete objects. Recovery should still validate required fields and factual content. Syntactically recovered text is not automatically a coherent or correct broadcast.

    • For missing media, show an honest unavailable state rather than inventing a clip.
    • For duplicate clips, avoid repeatedly showing the same moment as different events.
    • For interrupted speech, stop stale narration before starting the next answer.
    • For missing score context, omit the overlay rather than manufacture a value.
    Remember

    Media existence, factual grounding, JSON structure and playback synchronization are four separate checks.

    Note 08

    Personalization: ranking first, writing second

    Question: How does the system decide what matters to one fan?

    A personalized newsletter has two jobs. First, choose and order relevant events. Second, write a readable digest from those events. A good writer cannot repair a selection process that ignored the fan’s teams or omitted the week’s important games.

    The ranking features described in the original guide include followed-team match, followed-player match, recency, event importance and whether the event is upcoming. Each is a number. The scorer multiplies each feature by a weight, adds the contributions and a starting offset, then transforms the result.

    Illustrative ranking calculation — simplified weights

    Give a followed-team match weight 2, recency weight 1 and importance weight 1, with starting offset −1. For a recent important followed-team event, values of 1, 1 and 1 yield −1 + 2 + 1 + 1 = 3. An old unrelated event with values 0, 0 and 0.2 yields −0.8. The first ranks above the second.

    A sigmoid maps those raw scores into the interval from 0 to 1 while preserving their order. It does not magically turn chosen weights into learned weights or a calibrated probability that the fan will click.

    Heuristic weights are selected by the developer. Learned weights are fitted using examples and target labels. The checked README explicitly allows heuristic ranking until the trained artifact is supplied. The original guide reported that the reviewed repository did not contain the exported curation weights; deployment-specific files still require separate verification.

    Recency and cold starts

    A recency feature decreases as an item becomes older. Exponential decay makes the value shrink smoothly rather than abruptly disappear at a cutoff. The decay speed is a design choice that should reflect the product’s purpose.

    A cold-start fan has little or no preference history. The system needs a defined default rather than inventing preferences. A fan who follows many teams also has more candidates, so deduplicating game IDs prevents the same game from appearing multiple times.

    The newsletter writer then receives the ranked facts. A shared newsletter issue may be stored under a share token with an expiration. A token identifies a saved issue; it should not silently cause a different fan’s preferences to be used when that issue is opened.

        "recency": math.exp(-max(0.0, recency_days) / 7.0),  # 1.0 today, decays weekly
        "magnitude": min(1.0, max(0.0, float(item.get("magnitude", 0.0)))),
        "upcoming": 1.0 if item.get("upcoming") else 0.0,
    }


def score_item(item: dict) -> float:
    w = _weights()
    feats = _features(item)
    z = float(w.get("bias", 0.0)) + sum(w["weights"].get(k, 0.0) * v for k, v in feats.items())
    return 1.0 / (1.0 + math.exp(-z))


def rank_items(items: list[dict], limit: int | None = None) -> list[dict]:
    """Return items sorted by learned relevance, each annotated with `_score`."""
    scored = [{**it, "_score": round(score_item(it), 4)} for it in items]
    scored.sort(key=lambda it: it["_score"], reverse=True)
    return scored[:limit] if limit else scored

    _features produces followed-team/player indicators, exp(−max(age_days,0)/7), clipped magnitude, and an upcoming indicator. score_item computes sigmoid(b + w·x); rank_items rounds scores to four decimals before sorting. The weight loader is cached once per process and falls back to heuristic-v1 if the JSON file is absent or invalid. The checked repository tree does not contain that weight file.

    Why this structure is useful. A small linear scorer is interpretable and cheap enough for serverless inference. Recency decays smoothly: at seven days it is e⁻¹≈0.368, so seven days is a decay time constant, not a half-life (the half-life is about 4.85 days). Ranking and writing stay independently testable.

    What the code reveals. The output's 0–1 range is not evidence of click-probability calibration. model_label uses the version string to label trained versus heuristic; a label alone does not establish training provenance. Rounding before sorting can create ties that preserve input ordering.

    Alternative and test. Sort full-precision scores and round only for display. Pin weight version and feature order in logs. Evaluate NDCG against a popularity/recency baseline and use time-separated interaction data; synthetic labels generated from hand-set weights only teach those assumptions back to the model.

    Note 09

    Training concepts: distillation, LoRA and what proves deployment

    Question: What would it take to replace a general writer with a specialized smaller model?

    Fine-tuning continues training a pretrained model on a narrower task. The model’s numerical settings are adjusted so it becomes better at the desired output style or structure. This is separate from merely putting task instructions in a prompt.

    Distillation uses a stronger teacher model to create training examples for a student model. For sports writing, the teacher receives verified facts and produces a draft. The student learns to produce similar outputs from similar inputs. Teacher mistakes can enter the training set, so filtering is part of the learning pipeline, not an optional final polish.

    1. Collect game facts and retain source identifiers.
    2. Separate games into training, validation and final test groups.
    3. Generate teacher drafts for training examples.
    4. Reject drafts with unsupported names, numbers or malformed structure.
    5. Train the student or its adapters.
    6. Evaluate on untouched games against a template and general-model baseline.
    7. Deploy the chosen artifact, then log which checkpoint actually serves requests.

    LoRA and QLoRA, without the shorthand

    A large model has many weights. Updating every weight during training requires memory for the weights and additional training information. Low-rank adaptation (LoRA) trains smaller added matrices while keeping the original weights fixed. The smaller matrices describe a constrained adjustment to selected computations.

    QLoRA also stores the frozen base model using a compressed numerical representation. This can reduce training memory further. It does not remove the need to load a model, process examples, validate output or evaluate whether the adaptation helped.

    A checkpoint is a saved model state. An adapter checkpoint contains the learned adjustments. Training scripts establish that a workflow is available; a checkpoint establishes that weights were saved; configuration establishes a serving path; request logs establish which model actually ran. These are different evidence levels.

    Why splitting by paragraph is misleading

    If one game’s recap is in training and another paragraph about the same game is in testing, the student may already have seen the result and key players. Split by game ID and time so related material stays together. Use validation data to choose settings, then leave the final test untouched.

    Remember

    A training directory is not a completed training run. A completed run is not proof of deployment. A deployed model is not proof of improved quality.

    Note 10

    Identity, Redis and the double-points problem

    Question: How does a login-free application remember a fan’s picks and points?

    The documented browser creates an anonymous UUID, a long identifier intended to be unique, and saves it in local storage. It sends that identifier in the X-Device-Id request header. A header is metadata attached to a request. The backend can use the identifier as a key for fan state.

    Local storage persists values in one browser. Clearing it or switching browsers can create a different identity. A client-supplied device ID is not strong authentication: knowing or copying an identifier is different from proving account ownership.

    Redis is a fast data store. A hash stores named fields, such as a fan’s counters. A sorted set stores members with numerical scores and supports ranking them. Replays uses these structures for picks, points and leaderboards when Redis is configured.

    The checked README says storage operations become no-ops when REDIS_URL is absent. The interface may still load, but that is not proof that points are being persisted. Durability also depends on the actual Redis service and configuration, not just the library being imported.

    The race condition, step by step

    A race condition occurs when the result depends on the timing of overlapping operations. The original guide identifies a read-check-write pattern in pick resolution that can double-award points:

    TimeRequest ARequest B
    1Reads “pick unresolved.”
    2Also reads “pick unresolved.”
    3Marks it resolved and adds 10 points.
    4Acts on its earlier read and adds another 10.

    Idempotency means repeated processing of the same logical pick should not change the final award after the first successful resolution. Checking a flag is insufficient if the check and update can be separated by another request.

    An atomic operation happens as one indivisible state change relative to other competing operations. A Redis script or properly designed transaction can check unresolved status, mark resolution and award points together. With an optimistic transaction, a conflicting change must cause a retry rather than letting stale assumptions proceed.

    This is a proposed strengthening of the documented design. It should be verified with simultaneous requests and a failure between writes, not just by clicking the button twice slowly.

    Remember

    A device ID identifies a storage bucket; it does not prove identity. A retry check reduces some duplicates; atomic state handling is needed for concurrent correctness.

    mark_resolved reads a pick from a Redis hash, returns if already resolved, writes the resolved record, then separately increments profile counters and the leaderboard sorted set. A crash after the resolved marker but before the counters creates the opposite failure: a retry sees resolved and may never finish awarding the points.

    Why this structure is useful. Hashes naturally store per-fan picks; sorted sets provide ranking by score. A device UUID identifies a client bucket rather than authenticating a person.

    What the code reveals. The docstring says “exactly once,” while the function contains no transaction or Lua script enclosing the check and updates. Broad exception handling returns zero, so unavailable storage can resemble a legitimate no-op. The inspected code supports a race risk; no concurrent production incident was reproduced here.

    Alternative and test. Implement a single atomic check-and-award operation or an idempotent award ledger with reconciliation. Test two simultaneous requests and injected failure after every write boundary. Make disabled storage and failed persistence explicit, and establish account authentication before trusting client IDs for valuable entitlements.

    Note 11

    Evaluation: check the whole product, one layer at a time

    Question: What does “the app works” need to mean beyond one good demo?

    A demo shows an example. Evaluation measures behavior across a defined collection of cases. Each component needs a reference answer and an appropriate metric.

    ComponentUseful checkWhat the result tells you
    Data adapterMissing fields, duplicate IDs, source timestamps, known response fixtures.Whether downstream facts are complete, fresh and correctly parsed.
    Play classificationHuman labels, precision and recall for each play type.Which categories are wrongly added or missed.
    Key-play selectionExpert judgments of top selected moments.Whether the evidence set captures the story.
    RecapSupported claims divided by checked claims; score and name consistency.Whether prose stays grounded, beyond grammatical quality.
    BroadcastValid JSON, valid scenes, timing and factual checks.Whether the player can use the output and the narration is trustworthy.
    PersonalizationHuman relevance grades, ranking metrics and later user behavior.Whether important material appears early for the intended fan.
    StateReload, concurrent resolution and failure-recovery checks.Whether picks and points survive and are awarded correctly.

    Precision is the share of predictions that are correct. Recall is the share of true cases found. In an illustrative test with 20 true scoring plays, finding 18 while wrongly flagging 2 non-scoring plays gives 18/20 = 90% for both. The denominators happen to match in this example; they need not match generally.

    NDCG, normalized discounted cumulative gain, evaluates a ranked list using graded relevance. Relevant items near the top earn more credit than the same items much lower down. The score is compared with the best ordering for those relevance labels. It is meaningful only when the judgments and candidate set are defined.

    For generation, check factual claims rather than only whether names and numbers appear somewhere in the input. A sentence can contain allowed names and numbers but assign one player’s statistic to another. Human review is valuable for those relationship errors.

    The original guide did not establish a production factuality rate, learned-ranker uplift, cache hit rate or p95 latency benchmark. The checked README describes intended grounding and labeled fallbacks; those descriptions are not a completed blind quality study.

    Remember

    Report results with the dataset, sample count, source labels and failure types. A general LLM, a trained adapter and a template should not be merged into one unexplained quality number.

    The filter tests vocabulary membership, not factual entailment

    def check(facts: dict, target: str) -> tuple[bool, list[str]]:
    blob = _blob(facts)
    ok_numbers = _facts_numbers(blob)
    ok_tokens = _facts_tokens(blob)
    reasons: list[str] = []

    for num in _NUM.findall(target):
        n = int(num)
        if n < 13:              # small counts, quarters, list markers: ignore
            continue
        if 1900 <= n <= 2099:   # a year, not a stat
            continue
        if num not in ok_numbers:
            reasons.append(f"invented number {num}")

    for first, last in _NAME.findall(target):
        # A person reference is grounded if the surname appears in the facts.
        if last.lower() not in ok_tokens and first.lower() not in ok_tokens:
            reasons.append(f"invented name {first} {last}")

    # Allow a tiny amount of noise (e.g. an idiom that reads like a name).
    return (len(reasons) <= 1, reasons)

    The filter extracts all digit strings from serialized facts and allows matching numbers in target prose. It checks a simple capitalized two-word name pattern against available tokens. A sentence assigning player A's 30 points to player B can pass if both names and 30 occur in the facts. A fabricated 12-point statistic is ignored by the numeric threshold, and one unsupported large number can still pass because the function tolerates one reason.

    Why this structure is useful. This filter is fast enough to screen teacher-generated pairs and catch some blatant inventions. It reduces manual load, but should be treated as a weak prefilter whose false negatives are measured, not as an end-to-end faithfulness verifier.

    What the code reveals. Source selection, claim support, structure, media availability, timing, relevance, and persistence are distinct evaluation axes. The repository inspection provides implementation evidence; it does not supply a blind production factuality score, trained-ranker uplift, or measured p95.

    Alternative and test. Create relation-level adversarial cases, adjudicate a held-out sample, and report precision/recall of the filter itself. Track false acceptance separately from over-rejection. Keep a baseline matrix across template, base LLM, and adapter so quality gains are not confused with different data or easier examples.

    Note 12

    Scaling: what happens when many fans arrive together?

    Question: Where does the system slow down first?

    A bottleneck is the stage limiting throughput, the amount of work completed per unit time. The likely candidates in this design are upstream data calls, uncached model generation, shared-store operations and client media playback. These are hypotheses until measured.

    Latency is one request’s duration. p95 latency is the duration at or below which roughly 95% of measured requests finish. Measure cold cache misses separately from warm hits: a combined average can hide slow first-time experiences.

    Backpressure prevents the system from accepting or launching work faster than a dependency can handle. Examples include limiting simultaneous model calls and queuing refreshes. Without limits, a slow dependency can create more waiting requests, retries and memory use.

    1. Collapse duplicate work. Many fans opening one game should reuse a common source fetch and eligible recap.
    2. Separate freshness policies. Live scores, final recaps and preference-specific newsletters have different cache needs.
    3. Bound retries. Wait progressively longer between transient retries and add a small random delay so clients do not all retry together. Stop after a defined limit.
    4. Protect state changes. Resolve picks atomically and avoid duplicate awards after uncertain responses.
    5. Record failures visibly. Distinguish an empty valid dataset, unavailable supplier, model fallback and disabled persistence.

    A relational database such as PostgreSQL could be useful for long-term history, joins and richer transactional reporting. But a proposed ingestion architecture with millions of permanent event rows should not be described as the current live-fetch implementation unless its code and operating evidence are available.

    Similarly, the application calls hosted writers. Buying GPUs is not automatically the first optimization when repeated supplier requests or cache misses dominate. First measure the time spent fetching, selecting, writing and storing.

    Remember

    Scale the limiting resource, not the most impressive component in the diagram. Better reuse and correct state handling can matter more than a larger model.

    Note 13

    Revision sheet and self-test

    Facts → normalization → selection → prose
    Each transformation needs a visible contract. The writer is the last explanatory layer, not the authority on the score.
    Rule versus learned model
    Both can classify or rank. The distinction is whether settings were specified or learned from examples.
    Cache versus persistent state
    A cache stores reusable answers with freshness rules. Fan picks and points need explicit persistence and consistency guarantees.
    Structure versus truth
    A valid JSON broadcast can still contain false claims or poor timing.
    Code versus outcome evidence
    A feature path does not prove training, deployment, traffic volume or measured quality.
    Why is a missing score not the same as a score of zero?

    Zero is a known value. Missing means the value is unknown or unavailable. Replacing missing with zero invents a fact and can produce an incorrect winner or recap.

    Why can the cache make a temporary model outage last longer?

    A long-lived fallback could prolong a temporary outage. The inspected get_recap implementation already avoids caching data fallbacks when an LLM is configured. Remaining risks include corrected source facts and concurrent cache misses; see the cache code walkthrough.

    Why does JSON validation not prove a broadcast is correct?

    It checks how fields are arranged, not whether their claims are supported, their speakers are consistent or their timing matches the scene.

    Why do two “unresolved?” checks still allow double points?

    Both can read unresolved before either update becomes visible. The check and award need to be one concurrency-safe operation.

    How would you describe the system without buzzwords?

    “The application fetches real game data, converts it into consistent records, chooses useful moments and turns those facts into stories. It labels model and template outputs, caches suitable work and uses Redis for fan state when configured. Its quality needs testing at the data, selection, writing and persistence layers.”
