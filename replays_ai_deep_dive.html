How to think like the person who built the system

When an interviewer asks about a tool, do not start with the tool name. Start with the input, output, error cost, baseline, trade-off, and evidence. This gives you six points of control in any technical discussion.

1 · Contract

What went in and what had to come out?

“An unstructured note went in. A validated encounter and four stakeholder reports came out.” Or: “ESPN plays went in; a grounded recap came out.”

2 · Decision

Where was uncertainty handled?

Identify every probabilistic decision, confidence threshold, fallback, verification rule, and escalation path.

3 · Evidence

How would I prove it works?

Know the baseline, the held-out examples, the exact denominator, the metric, the failure cases, and what was not measured.

4 · Operations

What would fail first in production?

Know latency, provider quotas, cache keys, concurrency, input drift, retries, downstream side effects, and safe degradation.

1. Architecture and product contract

Product contract: fans pick teams and players; the system fetches authentic NBA/NFL scores, plays, box scores, news, and licensed/public clips through ESPN public endpoints; then it produces recaps, stories, highlight reels, two-host broadcasts, personalized digests and pick'em results. Facts come from sports data; prose may be model-generated, with the engine label surfaced to the UI.

Beginner

ESPN is the scoreboard and events supplier. FastAPI is the kitchen that converts many different ESPN fields into the same format. The AI writer is a sports journalist given a facts sheet. Redis remembers fans' picks and keeps frequently requested information fast. React draws the app.

Engineer

app.py composes route modules, api/espn_public.py is the typed sports-data adapter, a 60-second process-local TTL cache reduces repeat ESPN calls, optional Redis stores shared cache and durable fan state, and api/recaps.py composes real-score fact bundles and selects Anthropic/OpenAI or deterministic rendering. Reels and broadcasts are dedicated routers; TanStack Query owns server state, while localStorage stores anonymous fan selections.

Current-code reality check

The current repo README explicitly says data are derived live from ESPN and the durable store is Redis. It does not establish that the current code writes 5M+ events into PostgreSQL or runs a self-hosted multi-GPU inference system. If those were part of an earlier system, present them as a separately verifiable phase, not part of today's request path.

2. Data ingestion, normalization, freshness and caching

Ingestion does not always mean inserting rows into a database. Here, the verified path is on-demand API ingestion: pull ESPN's structured JSON when a fan requests a screen, then normalize it into a stable internal shape so downstream routes do not care whether the NBA and NFL JSON schemas differ.

Beginner

One supplier might call a field “homeScore,” another might nest it under a “competition.” The adapter converts both into home_score with one meaning. This prevents the rest of the application from having to learn every source format.

Engineer

_get_json() uses HTTP requests with a 12-second timeout and a process-local dict protected by a lock; the TTL is 60 seconds, with a 256-entry cap and stale-item eviction. Provider functions like fetch_espn_scoreboard, fetch_espn_team_schedule, fetch_espn_game_summary, and extract_summary_plays produce normalized game/score/period/clock fields. Caching is best effort on serverless warm instances, not guaranteed global consistency.

# Teaching-level normalization sketch, inspired by the current ESPN adapter
raw = get_json("/sports/basketball/nba/summary", params={"event": game_id})
plays = [
  {"period": p["period"]["number"],
   "clock": p["clock"]["displayValue"],
   "description": p.get("text") or p.get("description"),
   "home_score": parse_score(p.get("homeScore")),
   "away_score": parse_score(p.get("awayScore"))}
  for p in raw.get("plays", [])
]
# Deduplicate and verify event IDs before any downstream replay.

Freshness: live scores are changing data; a 60s TTL can be too stale for a game-ending moment. Use state-specific TTLs (live shorter, final longer) and cache keys that include sport, game ID, and freshness/version semantics. Failure: a 429 or timeout from ESPN should not masquerade as “no games happened.” Distinguish upstream unavailable from empty valid results.

Backpressure: when 1,000 fans refresh the same game, avoid 1,000 simultaneous upstream requests. At high traffic use shared Redis cache, per-key singleflight locking, bounded concurrency, and possibly a worker that materializes frequently requested live games. This is an improvement proposal, not a claim about the shipped route.

3. Play classification: rules, features, and actual models

A key engineering distinction: the current play classifier is rules-based, not a trained computer-vision model. classify_play_description() checks text such as “touchdown,” “interception,” “3pt,” “sack,” “dunk” and returns a category. Another module, play_analysis.py, explicitly says its four named “agents” are deterministic calculations, with no training loop or model checkpoint.

Beginner

Classifying a play means putting it into a bucket. If a play description says “interception,” the simplest classifier can label it immediately without asking an LLM. A trained classifier becomes useful when descriptions get ambiguous or many different phrases express the same event.

Engineer

classify_play_description is a fixed priority of string tests on ESPN description text. The ScoutAgent, StatAgent, RefAgent, and PredictAgent use normalized context and heuristics; the win-probability read is a time-decayed logistic proxy, not a probability trained and calibrated on real win outcomes. A learned classifier would require labels for play types, train/test grouping by game, model artifacts and metrics that do not appear in this code path.

When to switch from rules to ML: when an error analysis shows the rule library missing enough hard-to-parse events to outweigh a trained model's complexity. A good baseline is deterministic rules; a next model might be TF-IDF + logistic regression on descriptions; a stronger model could use sequence context or video frames if licensed data and labels support it.

Vision is a separate modality. A phrase in an older profile mentions “Claude Vision play classification,” but the current verified espn_public.py play types come from text descriptions. Do not call the current deterministic parser a vision model.

4. Model inference: how the recap actually gets written

Beginner

Think of the recap writer as getting a sports box score, a list of the important moments, and instructions to avoid making things up. If the writing service fails, it can still print a facts-only recap. Fans can tell which version they received.

Engineer

llm_text() attempts configured Anthropic models, then an optional OpenAI endpoint. _build_recap() formats scores, period transitions, and key play descriptions into a prompt. get_recap() consults an in-process six-hour memo and optional Redis cache. It avoids caching an obvious live game, and does not persist a deterministic fallback if an LLM is configured but temporarily failed, so a transient error doesn't poison the cache for hours.

Model latency: a hosted LLM request has network time, prompt prefill, output decoding, and service queue time. In this implementation you can optimize prompt size, caching, and number of calls, but you cannot tune the provider's GPU scheduler. Provider fallbacks: they improve availability but can cause output-format variation; include generated_by in the API contract and trace which provider ran.

Play selection is a ranking problem: weight scoring events, late-game context, lead changes, and interesting plays. It does not automatically become a trained ranker just because it assigns weights.

5. Reels and broadcast: reuse real clips, synchronize generated audio

The reel surface selects real video clips exposed through ESPN, distributes them across a 2-, 5-, or 10-minute story, attaches narration and typed overlays, and lets the browser speak narration. It does not synthesize the underlying video. The broadcast creates a two-host script with a play-by-play voice and an analyst voice, timed to the story UI.

Beginner

The reel editor picks a few meaningful moments from the real game. The narrator explains them. The broadcast writes a back-and-forth conversation. If the model cannot deliver valid narration, the UI should have a simpler, sourced description to play instead.

Engineer

reels.py scores clips heuristically, spreads selections over game time, adds scorebug/statline/win-probability overlays, and returns narration. broadcast.py defines 12/26/44 turns for 2/5/10-minute tiers, produces JSON with host/scene/text semantics, and even salvages complete JSON objects when a model response is truncated. Browser speechSynthesis/SpeechRecognition handle voice playback and questions. The displayed win-probability overlay is illustrative, not a calibrated probabilistic model.

What can go wrong? A clip may have no valid URL; timestamp mappings may not align with narration; ESPN fields can be missing; a model may invent game details; a long script may truncate to malformed JSON. Defensive engineering means verifying clip existence, exposing provenance, bounding output length, recovering valid turns, and falling back without inventing a clip.

6. Personalization, curation, training and inference: no buzzwords required

The newsletter pipeline has two different ML problems: ranking which facts matter to a fan and writing an engaging newsletter from those facts. Ranking can be a tiny linear model. Writing can use a larger text model or a fine-tuned adapter.

Beginner

If you follow the Warriors, a Warriors win probably matters more than an unrelated NHL story. A ranker assigns a relevance score using team match, player match, recency, and drama. After ordering the facts, the writer turns them into a digest.

Engineer

api/curation.py computes sigmoid(b + w·features) over followed-team, followed-player, exponentially decaying recency, event magnitude, and upcoming-status features. Without an exported curation_weights.json it uses clearly labeled heuristic weights (2.2, 2.0, 1.3, 1.1, 0.6 respectively, bias −0.5). The public repo currently lacks that weights file, so do not assert this instance serves a learned curation ranker.

Offline training design in training/: build real ESPN fact records → have a teacher model draft groundable newsletter or broadcast targets → filter any target with unsupported names/numbers → fine-tune smaller writer models via LoRA/QLoRA → deploy adapters behind an OpenAI-compatible endpoint → evaluate held-out grounding, format, and JSON validity. These are training scripts and deployment hooks; their existence does not prove adapters were trained, launched, or used on a live request.

LoRA explained: instead of updating every weight of a 7B model, train small low-rank matrices injected into selected layers. This cuts trainable parameters and optimizer memory. QLoRA additionally uses a quantized base model to reduce training VRAM. Distillation means a strong “teacher” produces targets for a smaller student to learn from. Model provenance means returning “trained”, “LLM”, or “deterministic” rather than implying the same engine ran every time.

7. Identity, Redis, leaderboard, idempotency and races

Replays is login-free. The browser generates an anonymous UUID, sends it in the X-Device-Id header, and uses that key for durable fan state when REDIS_URL is configured. Redis hashes store picks and profiles; a sorted set stores leaderboard scores; expiring keys store shareable newsletter editions.

Beginner

Redis is a fast key-value database. A hash stores a fan's fields or picks. A sorted set stores scores ordered from high to low, so top-10 and “my ranking” are fast to show.

Engineer

db/store.py stores per-device picks, resolves winners after scores become final, increments correct/total/streak counters, and calls ZINCRBY on a leaderboard sorted set. It checks resolved to avoid repeat awards, but the read-check-write and score increment are separate Redis operations; under simultaneous requests a race can double-award. A Lua script or Redis transaction with atomic compare-and-set would give a stronger idempotency guarantee.

Important failure behavior: without REDIS_URL the demo can still run, but picks/profile persistence is a no-op. Silent exceptions in store helpers preserve UI availability but need observability: you cannot claim persistence when the data store is disabled or failing.

Anonymous identity is not security: a client-controlled device ID can be spoofed. For competitive rewards or financially valuable prizes, add signed session identity and server-side authorization, not only a UUID header.

8. Serving and 10× traffic: where it really hurts

Replays currently runs a Vite/React frontend, FastAPI behind Vercel-style serverless entrypoints, public ESPN calls, hosted language models where configured, and optional Redis. An architecture diagram is not a throughput benchmark: the README alone cannot verify “sub-second p95”, “85% Redis hit rate”, or a specific 5M-event pipeline.

What if you did have a 5M-event ingestion system? The proper design would likely use upstream polling/stream readers, an append-only event log or queue, idempotent upserts into a durable relational store, bounded inference workers, Redis for hot keys, and API serving with explicit freshness guarantees. That is an excellent alternative architecture to defend—but the current public repo does not verify it was deployed.

10× answer

“The first bottleneck is upstream ESPN availability under many concurrent fans, followed by uncached LLM generation. I would collapse duplicate fetches, separate live and final cache TTLs, materialize hot events, and ensure pick scoring is atomic before adding any GPU infrastructure.”

Contamination avoidance: split sports training by game/event date and game ID, not by random recap paragraph. All plays from one game must stay in the same split. Don't let news articles or teacher-written text about a test game slip into training. For personalized ranking, group by fan and time. Evaluate generation on untouched future games with real scoreboard facts, not only prompts that look like training examples.

Provenance: actual scores and clips are from ESPN; the source label distinguishes trained writer, generic LLM and deterministic template. The training README describes an evaluation workflow, not a published current metric for model quality. Avoid inventing a measured uplift.

Study handbook · core ML and backend concepts

Learn the fundamentals until you can explain them without a prompt

Use the Beginner/Engineer switch at the top. Definitions below are deliberately operational: they say when to use the concept, which project uses it, and how it fails.

Binary classification

One of two labels, e.g. “field present / absent.” A sigmoid gives a score; a threshold maps it to a decision. Synthure: missing-documentation fields.

Multiclass classification

Exactly one label out of several, e.g. note type = SOAP, ER, discharge, etc. Typical output uses softmax. Synthure: note-type model.

Multilabel classification

Many labels can be simultaneously true, e.g. a note can mention diabetes, hypertension and arthritis. Use separate per-label scores, not one softmax. Would apply to document diagnosis tagging.

NER

Named entity recognition: locate spans and assign types (DISEASE, DRUG, PERSON). BIO labels represent Begin/Inside/Outside. Errors include span boundaries and false positives under negation. Synthure: OpenMed token classifiers.

Regex / rule engine

Pattern matching, no learning required. Great for explicit formats, source IDs and known play phrases; weak on semantic ambiguity. Synthure abbreviations; Replays play types.

TF-IDF

Word frequency weighted down for common words across documents. Sparse features feed simple classifiers or keyword retrieval. Synthure note-type classification.

Logistic regression

Weighted feature sum passed through sigmoid for a score. Fast, simple, interpretable; doesn't directly understand long contextual dependencies. Synthure missing fields + reranker; Replays curation.

Gradient-boosted trees

Many small decision trees sequentially correct predecessor errors. Strong for tabular and structured features. Can overfit synthetic labeling rules. Synthure readiness.

Embeddings

Dense numeric vectors representing tokens, phrases or documents. Similar meanings may be near in vector space. They are not proof of factual equivalence. Optional Synthure trained coder; older policy-RAG design.

RAG

Retrieve sources at query time and condition a model on them. Helps with changing knowledge and citations; adds retrieval errors. Older Synthure policy narrative; distinguish from ICD linking.

Bi-encoder vs cross-encoder

Bi-encoder embeds query and item separately so search is fast; cross-encoder reads both together to score relevance more accurately but is costly on many candidates. Synthure optional trained ICD coder.

IVFFlat / HNSW

Approximate nearest-neighbor vector indexes. IVF searches selected clusters; HNSW navigates a neighborhood graph. Trade recall, speed, RAM and build costs. Know theory; not verified deployed in current Synthure.

Model inference

Run a trained model on an input. For a text LLM: tokenize, prefill context, decode output. Latency depends on context length, generated tokens and queueing. Synthure writers; Replays recap.

GPU + KV cache

GPU parallelism accelerates matrix ops; KV cache stores attention keys/values for earlier tokens. Long prompts and many concurrent streams consume VRAM. Relevant to self-hosted inference, not directly controlled by current hosted APIs.

LoRA / QLoRA

Efficient fine-tuning with small trainable adapters; QLoRA quantizes the frozen base. Saves training VRAM but still needs datasets and evals. Replays offline training scripts.

Distillation

Teacher-generated supervision trains a smaller student. Caveat: teacher mistakes and leakage become student training data. Replays newsletter and broadcast training design.

Calibration

Does a predicted 0.8 correspond to ~80% positives across similar predictions? Check reliability and ECE; recalibrate using held-out validation. Synthure readiness isotonic mapping.

Precision vs recall

Precision = share of predictions that are right. Recall = share of actual positives recovered. In high-stakes extraction, false negatives vs false positives have different downstream costs. Both systems: NER/play detection.

MRR / Recall@K / NDCG

Retrieval ranking metrics: first correct rank, any correct in top K, and graded rank quality. Don't claim model performance without exact gold set. Synthure ICD linking; Replays curation.

Data contamination

Test labels or near-duplicate examples leak into training, prompts, retrieval artifacts or tuning loops. Prevent with grouped temporal splits and frozen holdout. Synthure synthetic generator; Replays same-game splits.

SSE / WebSocket

SSE is server→client event streaming over HTTP; WebSocket supports bidirectional communication. Streaming stages is not the same as durable cross-device synchronization. Synthure SSE route.

Redis TTL + sorted set

TTL expires cache keys; sorted set supports ranked leaderboards. Watch cache staleness and concurrent increments. Replays caches, points and rankings.

Idempotency

The same request retried twice must not cause duplicate side effects. Use stable IDs and atomic state transitions, not only a read-then-write check. Replays pick resolution; future Synthure claims.

p95 and tail latency

95th-percentile request duration, more revealing than an average for slow users. Parallel stages make naive sums misleading. Both applications' serving design.

Abstention / human-in-the-loop

The system withholds automation when evidence or confidence is insufficient. Track both the error rate on automated cases and coverage. Synthure 0.60 extraction confidence gate.

Active recall: try answering before opening each solution

Why is NER a different problem from note-type classification?

NER predicts typed spans and their positions, possibly many per document. Note-type classification predicts a single document-level label. They need different labels and error metrics.

If recall@5 is 90% but generation accuracy is 70%, where do you look?

Inspect whether the relevant evidence actually survived reranking and prompt assembly; then check citations and model interpretation. Also verify the remaining 10% retrieval misses aren't concentrated in high-risk cases.

Why can a 0.9 model score be unsafe?

Raw scores are not necessarily calibrated and may be out of distribution. A high score can coexist with missing information; validation and safety checks still apply.

What is the difference between a cache and a database?

A cache stores temporary reusable results with invalidation/freshness semantics. A database preserves source-of-truth state and transactional consistency. Redis can serve as either for certain data, depending on durability and write guarantees.

Why is “four agents” not necessarily “four models”?

Different prompts, deterministic roles or functions may execute on the same base model or no trained model at all. An agent is an orchestration boundary, not proof of independently trained weights.

Why might an ANN index return wrong candidates even when the vector is good?

Approximate search skips parts of the space. Index hyperparameters, filters, stale vectors, and reranking can all affect recall; compare with exact nearest-neighbor search.

How can a Redis pick be awarded twice despite checking “resolved”?

Two requests both read the unresolved state before either writes. Make compare-and-update and points award one atomic Redis operation.

What is one thing you should never invent in an AI systems interview?

A latency, benchmark denominator, fine-tuning run, model deployment, dataset provenance, user count, partner contract, or production architecture that you cannot verify. Explain your design decisions and known limitations instead.
